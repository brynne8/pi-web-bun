# Listing background runs

`list_bg_runs` answers "what background work does this session have?" for both subsystems at once: the commands it handed to the background and the subagents it delegated. The tool was `list_subagent_runs` and listed subagents only, while `get_result` had already become the fetch tool for both ([get-result.md](get-result.md)); a listing split by subsystem left a background command with no way to be found once its card scrolled away. One table is also what makes the `id` column mean one thing: whatever the row's kind, that id is what `get_result` fetches with.

- **Its own extension, for the reason `get_result` and `await_results` have one** (`lib/bg-runs-extension.ts`, registered in `lib/rpc-manager.ts` beside `createGetResultExtension`): the two switches are independent, and hosted inside the subagent extension the listing would vanish with built-in subagents, taking background commands' only way to be found with it. What it offers is decided per backend, and its description says only what it can do — "A row is a background command (`bash`) or a subagent run (`subagent`)." with both on, "Every row is a subagent run." with bash off, "Every row is a background command." with subagents off. With neither on it registers nothing. `lib/rpc-manager-bg-tasks.integration.test.mjs` pins the case the old shape got wrong: a real session whose built-in subagents are off still registers the tool, for its commands.
- **Five columns, one row per run, never a task or a result** (`formatBgRunList()` and `BgRunEntry` in `lib/bg-runs.ts`): `id`, `kind`, `state`, `last_activity`, `description`. A subagent's row keeps the profile that ran it inside `description` (`subagentRunDescription()`, spelled `explore: Find the parser`) — a background command has no such attribute, and a column holding a value for one kind only would print an empty field on every command row. Whitespace in a field collapses to spaces and it is cut at 120 characters, never through a surrogate pair; an id is cut at 64. `last_activity` is the session file's `modified` for an indexed run and the live status time while it runs, and a command's own last output, or its start when it wrote nothing.
- **A state stays in its subsystem's own words, and `kind` says which vocabulary to read.** A command is `running`, `stopping`, `stopped`, `succeeded`, `failed` or `signal` (`bgTaskState()`, [background-bash.md](background-bash.md)); a subagent is `starting`, `queued`, `running`, `completed`, `failed`, `aborted` or `interrupted`. Unifying them would hide a fact: `succeeded` is an exit code, `completed` is a child that wrote its report.
- **The filter is the whole selection — no limit, no window.** The default is a process list: rows still going (live status first, then most recent activity), plus an exit that left work behind within the last hour. Everything it leaves out is counted in one note naming the filter that would include it, and every filter answers in words when it has nothing to show. `status` asks for `"active"`, `"unfinished"` (live rows and every exit that left work behind), `"completed"` (a run that got its answer out, whichever word its kind uses), or `"all"`; anything else keeps the default view. A listing never waits, starts, wakes or collects a run, so looking up a forgotten one cannot disturb the report that is still on its way.
- **The two backends do not remember alike.** A command's rows come from the in-process registry (`listBgTasks()` filtered to the calling session by `filterBgTasksBySession()`), so a finished one is listed while its log is kept (ten minutes past its last write, `BG_TASK_FINISHED_RETENTION_MS`) and nothing survives a restart. A subagent's rows come from `listAllSessions()` filtered to this parent's `relation.kind === "subagent"`, overlaid by the live run map, so a run dispatched before the catalogue cache refreshed is listed at its live status and a persisted orphan reads back `interrupted`. A resumed run reuses its session id, so the map keyed by it leaves one row.
- **A child never gets it.** The name stays in `SUBAGENT_CONTROL_TOOL_NAMES` (`lib/subagents.ts`), which `subagentToolOptions()` excludes from a child's tool list, and it is `model-only`, so pi never lets another tool reach it through `ctx.executeTool()` — a codemode script cannot decide when the parent looks. `lib/subagent-extension.integration.test.mjs` pins both.
- **The old name keeps being read, never served.** `lib/session-file-references-core.ts` lists `list_subagent_runs` beside the new name among the tools whose result text may authorize a path it mentions, so an older transcript's listing keeps the file references it had. Nothing registers the old name: a model that calls it gets pi's unknown-tool answer and the new name in its own tool list.
- **Its own row in the transcript.** `toolCallFamily()` (`lib/tool-call-runs.ts`) matches names like `list_subagent_runs` by prefix, so the listing lands in the `other` family and a `list_bg_runs` call stands as one row of its own instead of merging into a stretch of subagent cards — which is what it is: one call over two subsystems, not another subagent call.
- Files: `lib/bg-runs.ts` (the name, the row shape, the table), `lib/bg-runs-extension.ts` (the tool, per-backend rows, per-switch description), the rows' sources in `lib/bg-task-registry.ts` and `SubagentExtensionRuntime.list()` (`lib/subagent-runtime.ts`), and `lib/bg-runs.test.mjs` / `lib/bg-runs-extension.test.mjs`. The catalogue merge is pinned by `lib/subagent-runtime.test.mjs`.
