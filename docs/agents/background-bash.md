# Background bash tasks

Opt-in: `bgTasksEnabled: true` in the global settings.json, written only by `PUT /api/tools/settings` (`lib/bg-tasks-settings.ts`; absent reads as disabled). `isBgTasksEnabled()` is read synchronously where the session's `extensionFactories` are built (`lib/rpc-manager.ts`), so the switch takes effect for sessions started afterwards, not for a running one. With it off, `createProjectCommandBashExtension()` registers pi's plain bash tool and none of this exists.

## Two ways into the background
- `run_in_background: true` (`startBackgroundCommand`) returns at once, streaming straight into the log file, and notifies when the process ends. A user-typed `timeout` still applies.
- A foreground command auto-backgrounds after `FOREGROUND_AUTO_BACKGROUND_MS` (120 s, `lib/bash-bg-tasks.ts`). The tool call rejects with `bg-task-backgrounded:<logPath>`, which the registered tool turns into a text result for the model; the process keeps running and its completion notifies later. The threshold is in the tool's prompt, so the model knows it instead of discovering it.
- **An explicit `timeout` must not disable the handoff.** It used to, and the model passes one on nearly every long command (in a sample of real sessions, no call over the threshold omitted it), so the feature never fired in practice. The timeout stays the process's own hard limit — the child still dies at it — and only the model is released earlier; a `timeout` shorter than the threshold still wins and reports `timeout:N`.
- **The timeout is sanitized before it goes downstream, not just for our own timer.** pi's `resolveTimeoutMs` rejects anything that is not a finite positive number, and models write `timeout: 0` for "unlimited". Forwarding the raw value made `run_in_background` spawn nothing and report `failed (Invalid timeout: must be a finite number of seconds) in 0s` asynchronously — the tool result had already said "Command started in background", so the work silently never ran. Non-finite and non-positive values now become no timeout everywhere — including the shell card's dim `(timeout Ns)`, which prints under the same guard so it can never claim a limit the process does not get.
- Output before the handoff is buffered in memory (`PreHandoffBuffer`, 4 MiB) and dumped into the log at handoff, so the report's tail covers output the model never saw. Overflow replaces the head with `[... earlier output truncated ...]`.
- **Do not let the model end a command's output early with `| tail` or a redirect.** Those two, and only those two, are forbidden: both stop the output before the tool sees it, so pi's own truncation never runs, the full output is never saved to a file, and the dropped lines are gone. `| tail` also collides with the tool, which already returns the *last* 2000 lines / 50KB — a `| tail -30` keeps 30 lines of a 3353-line run and saves nothing. The prompt names no other shape, on purpose: naming the permitted ones (a filter into the answer, `| head`, `2>&1`) adds words the model has to read without changing what it must not do. To see less, bound the command (`git log --oneline -20`), or pass `max_output_lines`. The prohibition also rides the tool description and the `command` parameter, where it is read as the command is written. It is only on the tool when the switch is on.
- **`max_output_lines` is the model's own line budget, and going over it is a handoff, not a truncation.** It is a line count, and a foreground command that prints more than it moves to the background exactly as the 120 s rule does; the result names which trigger fired. A command that states no count runs with no line limit, and the model chooses whether to state one — the parameter's description tells it to set one by default, which is a prompt that can be measured but not enforced, and the switch-off tool is pi's own. Like the rest of the rule, it is only on the tool when the switch is on. This is what gives a command with no bound flag (`gh run view --log`) a way to say "not this much" that is not the forbidden `| tail`; nothing is dropped either way, because the handoff log keeps everything the model has not seen yet. Both triggers share one handoff in `createProjectCommandBashOperations`, which rejects with `bg-task-backgrounded:<reason>:<log path>` (`time` or `lines`). Pi's own cap still applies on top: a background command's report carries the end of its log, at 2000 lines / 50KB.
- A log is read again only by the report that names its path (and by the model following the pending index's `read("<log path>")` hint while that report waits), so `pruneBgLogs()` deletes `.log` files a day past their last write; mtime is what a task still running keeps fresh by writing. A file another process still holds (Windows refuses the unlink) is left for the next sweep; on POSIX it goes, and a task running longer than a day with no output in that window then reports `(no output)`.
- **The sweep does not wait for a task.** `pruneBgLogs()` runs from `bgLogPath()` as a task starts and once per server instance from `registerNodeInstrumentation()` (`instrumentation.ts` → `instrumentation-node.ts`). A sweep reached only from `bgLogPath()` never happens with `bgTasksEnabled` off, nor on a machine that runs no background command: one had collected 337 logs and 158 MB that way. There is still no size bound and no timer — a day of mtime is the whole rule.
- **One directory per session**: `<tmpdir>/pi-web-bg-tasks/<sessionId>/<name>.log`, handed out by `bgLogPath(sessionId)`. A flat name carrying no session id could never be traced back to what owned it, so deleting a session left its log behind with the completion report still naming the path. `deleteBgLogsForSession(sessionId)` removes that directory — its files, then the directory — and `deleteSessions()` calls it per deleted id (`lib/session-delete.ts`), after the wrapper's shutdown has aborted the writers. It refuses an id that is not a single safe path component (the same `SESSION_ID_PATTERN` the rest of the code validates session ids with), refuses the shared bucket, drops a directory that is a symlink as a link rather than following it out of the log root, and never throws: a log left behind is a leak the sweep picks up, while a throw would stop a session delete half-way.
- A session that went away takes its logs with it, so a report already in the parent's queue can name a path that no longer exists — the model's `read` of it then fails, which is honest: the session it belonged to is gone.
- A task whose session id is missing or unusable writes to `<tmpdir>/pi-web-bg-tasks/_unassigned/`, never into the log root itself. The leading `_` is a name `SESSION_ID_PATTERN` can never produce, so the bucket can neither collide with a real session's directory nor be aimed at by `deleteBgLogsForSession`; it is kept by the sweep alone.
- The sweep takes three shapes: the flat `*.log` files left in the log root by the layout that had no per-session directories (the migration path for an upgraded machine), the stale logs inside a session's directory, and a session's directory once it holds nothing. An empty directory is removed only a day past its own last change — adding a log re-stamps it, so a task that is starting cannot have its directory pulled out from under its `createWriteStream`, and a directory emptied by the sweep dies on the sweep after.

## What the model is told once the command leaves the foreground
- The auto-background result and the explicit `run_in_background` start say the same thing (`lib/project-command-env.ts`), so the model reads one instruction whichever way the command left the foreground: the result arrives on its own when it finishes; do not poll, sleep, or re-read its log; do other work that does not need it if you have any; if you have none, stop — no output, no commands — until it arrives; and stopping does not cancel the task. A third copy of it used to sit in the tool's prompt guideline too; it was the same sentence twice over, so the guideline list now carries only the no-tail rule and the two background facts.
- **The instruction has to name both branches.** These texts used to close with "do not wait or poll; continue with other work", which permitted exactly one action — other work. A model with nothing else to do was left choosing among the actions the sentence forbade, and polled: sleep, log reads, status commands, filler output. It read as "stay busy without this result", not as "you may also do nothing".
- **The word "wait" is gone even negated** — negated, it still primes the sleep it warns against — and the stop is spelled out as *no output and no commands*, because those are the two things a model reaches for when told to do nothing. The last sentence is not filler either: "stopping ends my turn, so stopping kills my build" is the belief that kept it generating in the first place.
- All of this is on the registered tool only while `bgTasksEnabled` is on; with the switch off, pi's own bash tool and its own prompt are untouched.

## Stop reaches the child, but not a survivor

A background task is also a row in the right panel's **Tasks** tab (`GET /api/bg-tasks`). The registry is `lib/bg-task-registry.ts`: one entry per command's `AbortController`, kept on `globalThis` behind a `Symbol.for` because the list, kill and output routes are bundled into another module graph than the tool (the same reason as `lib/file-watch-registry.ts`). A foreground command is tracked but hidden, and `promoteBgTask()` makes it visible at the handoff; `noteBgTaskOutput()` keeps its idle clock honest. The list keeps a finished task for ten minutes so its log can still be read, while `hasLiveBgTasks()` counts only running ones. The panel shows elapsed time, time since the last output, the task's session, and `GET /api/bg-tasks/[id]/output` polled by byte offset (base64, so a multi-byte character split across polls survives). A row names its session instead of showing a UUID, links to that session, and distinguishes success, a non-zero exit, a signal and a user stop; a failed poll retries with backoff instead of freezing the pane. The output follows a reader who is at the bottom and otherwise offers a jump-to-latest control with the unseen count.

`POST /api/bg-tasks/[id]` with `{action:"kill"}` aborts that controller. The entry stays marked `killedByUser` until its process settles, so `wasBgTaskKilled()` makes the ordinary completion report step aside, and the route leaves a visible custom message (`pi-web:bg-task-killed`) in the task's session saying a person stopped it — `buildBgTaskKilledNote()` in `lib/bg-task-notification.ts`. The note is delivered as a follow-up with `triggerTurn: false`, so it never starts a turn on its own; a wrapper that is gone is reopened by id first, the same path a settled report takes.

## The rail's activity view

`components/ActivityPanel.tsx` is the right rail's activity view — what the session on screen is doing right now — carried as its first tab (`closable: false`), with the count of everything running in it on the tab label and on the top bar's file-panel button: this session's background commands **and** its family's running subagents (`countRunningSubagents()`, `lib/session-family.ts`), since the section that lists the subagents lives here now and the button that opens the rail is the only way to it. **The commands are the current session's only**: `GET /api/bg-tasks` answers with the whole instance, and `filterBgTasksBySession()` in `lib/bg-task-filter.ts` keeps the tasks whose `sessionId` is the session the page shows, so the tab label, the panel button's badge and the grid all speak of this session, and a page with no session selected shows none. Another session's commands, and a subagent's, are not this page's work. One panel, one scroll, one palette (`--act-*`, which the read-out's `--dbg-*` resolve to, so a warning reads the same on a task card and on a stream row), one line per row, and no head of its own: the rail's tab already names the view and counts it, so a title above the sections would repeat it.

Sections stand in the order of what a reader can do about each: **Problems**, **Agents**, **Commands**, **Sessions**, **Diagnostics**. Problems appears only when `debugIssues()` has something to say — one sentence per fault, above everything, so nothing that is folded can hide a fault, and an activity view with nothing wrong says nothing about itself. Agents shows the session on screen and every subagent it delegated (see `subagents.md`), and only while there are subagents to show. Commands is the grid of task cards, the heavy content, kept under the lighter lines rather than above them. Sessions is the read-out's list of what the server holds something for (`sessions.md`, "The read-out"), which speaks of what is running and so is not folded. Diagnostics is the one fold: this page's connection meter, poll round trips, stream freshness and lease renewal, the server's totals and its connected pages — the numbers behind the faults, which nothing can act on in the moment. It starts open, so the fold is a way to clear them away rather than a door to open to see them; closing it unmounts the read-out and slows the beat to `SLOW_POLL_MS` (5 s), which is what the sessions' reap countdowns need, and opening it takes the read-out back to its own 2 s.

A card is one line — a stroke glyph, the command, a boxed word for its state — because the tooltip carries the command in full, the session it belongs to and the state a colour alone cannot. `lib/bg-task-status.ts` owns that state (`running`, `stopping`, `stopped`, `succeeded`, `failed`, `signal`), so a finished card says how the command ended rather than only that it did. Stop takes two clicks — the first arms the card for five seconds, the second stops it — rather than `window.confirm`, which no other part of the page uses.

Clicking a card opens that task's log as its own right-rail tab (`components/BgTaskOutputView.tsx`, tab id `bg:<taskId>`), like a file or a terminal: the header names the command, its session and its live state, and the pane tails the log by byte offset with backoff on a failed poll. A finished task leaves the list, so an open log tab keeps the last snapshot of its task (`parkedBgOutputTasks` in `components/AppShell.tsx`); closing the last tab of any kind falls back to the activity view, which the rail always has — and stays open: a rail with a tab in it is never folded by closing one, only by its hide control. The pane follows a reader who is already at the bottom and otherwise offers the chat's own scroll arrow (`chat-scroll-to-bottom`, reused from ChatWindow), so reading an earlier error is not interrupted by the next chunk.

The child is spawned against the wrapper's own `AbortController`, not the tool call's signal: after the handoff the tool call is already settled, and a later abort must not kill the backgrounded process. So **the tool call's signal has to be forwarded into that controller** — the abort listener belongs on both (`signal` and `execSignal`; `release()` removes both). Listening only on `execSignal` leaves Stop a no-op for *every* command while the feature is on, which is invisible until someone notices the process still running after the button.
- Once `handedOff` is set, `onAbort` skips the abort and `release()` has already dropped both listeners, so Stop cannot reach a background task at all. That is the intended split: Stop kills what is in front of the user, leaves what is not.
- `trackBgTask()` / `untrackBgTask()` keep the live controllers per session id, and `killBgTasksForSession()` aborts them from the wrapper's `onDestroy`, so a session that goes away does not orphan its processes.
- The timeout and abort paths keep pi's settle grace (`ABORT_SETTLE_GRACE_MS`): pi kills the process tree and then keeps reading until inherited stdout/stderr handles fall idle (#647).

## The completion report
`createBgTaskNotifier()` hands the report to the settled-report sink the moment the task exits — never as an interrupt: `sink.deliver()` (`lib/settled-report-note.ts`) queues it as a follow-up, which pi appends when the parent's current run ends, so the wait is one run rather than however long the parent keeps working (waiting for an idle parent is what turned a batch of finished tasks into a burst of stale reports). A session whose wrapper was released is reopened by id first. The text is built by `buildBgTaskNotification()`: status, duration, command (500 chars), log path, and the log's last 4 KiB as the tail (`(no output)` when empty).
- Every finished task is also indexed as pending until its report reaches the parent, so the parent can ask what finished while it was busy: see [pending-notifications.md](pending-notifications.md). The title is the command's first line and the fetch hint is `read("<log path>")`.
- The first paragraph (`BG_TASK_NOTIFICATION_PREFIX`) is a guard for the model: it marks the report as tool output carrying no new user intent. It must stay in the session file and must never reach the screen — which is every place the card prints the text, the collapsed header's preview included, so the strip is a function of its own (`stripBgTaskNotificationPrefix()`) that both `BgTaskNotificationView`'s fallback and `getCustomMessagePreview()` in `components/MessageView.tsx` go through. Copy is the one exception: it copies what the session file holds.
- **A busy parent is retried, never dropped.** A send can land between the sink's state check and pi's own: pi is streaming, and pi refuses a message that would start a second run (`Agent is already processing…`). Handing a batch over answers through one of two callbacks (`SettledReportHandoff` in `lib/settled-report-note.ts`): `sent()` means the parent holds it and the note stops owing it, `refused()` means nothing was taken and the note re-arms itself for the retry loop — an entry is cleared by a send that landed, never by one that was refused, or the reports that settle afterwards would be announced a second time by a batch nobody holds. The batch is then retried on a backoff — 500 ms doubling to a 30 s cap, plus up to 200 ms of jitter so a burst of reports does not retry in lockstep — the first attempt with `triggerTurn: true` (it may start the turn), every retry as a queued follow-up (`triggerTurn: false`). One initial attempt plus seven retries (`lib/settled-report-note.ts`); if the parent still will not take it, the batch is written to a dead-letter record at `<tmpdir>/pi-web-dead-letters/<notificationId>.json` — the session id, the reports, the attempt count and the error — so an undelivered report is discoverable instead of lost. The note is dropped with it, so a later report opens a fresh batch rather than append to a message that will never be sent. A failure that is not the busy race is dead-lettered at once, without retrying. The wait between retries is a sink dependency (`sleep`), which is a test seam: a suite never sleeps the schedule out.
- **A batch pi let go of, or one an idle parent will not drain, goes back.** The follow-up queue lives in the wrapper, so a queued batch is gone when that wrapper is released and the reopened parent starts with an empty queue. And pi drains a follow-up only inside a run: a turn that ends in an error or an abort, or with `finishTurn` answering `end`, returns before the queue is drained, leaving the batch in place while the parent goes idle. Either way a note still marked as queued keeps taking every later report for that parent, because a queued batch is never sent twice: the parent hears about nothing that settled afterwards. So the next report looks at the parent it resolved while that parent is idle: if the wrapper is gone, the queue no longer holds the batch (pi keeps the content array by reference, the same identity a batch grows and is withdrawn by), or the queue still holds it but no run will drain it, the batch is taken back out (when it is still readable) and sent again with the wake-up it never got. A parent with a run in flight is not judged by its queue: between draining it and appending what it drained pi holds nothing and has written nothing, and a batch read as lost there is delivered twice. A batch let go of twice is abandoned and dead-lettered rather than sent a third time; a resend whose send fails was never handed over, so it does not count and the next report tries again. This bounds the silence to one batch instead of to the life of the session.
- Both the builder and `parseBgTaskReport()` live in the client-safe `lib/bg-task-notification.ts`, not in `lib/bash-bg-tasks.ts`, which imports `node:fs` and cannot be pulled into a component. `BgTaskNotificationView` parses the report back apart and renders the fields with the shared `components/KeyValueTable.tsx` plus a `<pre>` tail (the same table a tool card uses for its flat arguments), falling back to the raw text for a report in a shape this build does not know.
- **The writer is drained before the log is read.** `drainLog()` waits on the write stream's `end()`, because a chatty command still has megabytes queued in it when the process exits: reading then returned a slice from somewhere in the middle, so the report lost the process's last lines and whatever it wrote to stderr at the end. Both paths report this way — `startBackgroundCommand` awaits the drain, and the handoff hands its stream to `reportBgTask()`, which drains before `readLogTail()`.
