# Pending background results index

A background command or subagent run settles while its parent is mid-run. The report itself reaches the parent when that run ends (pi drains its follow-up queue there — see [background-bash.md](background-bash.md) and [subagents.md](subagents.md)), so between the two moments the parent has no way to know a result exists. `lib/pending-notifications.ts` is that missing index and the `pending_notifications` tool is how the model reads it.

- The registry holds one entry per settled report, keyed by the **message** it rides in (`messageId`): a batch landing clears every report it carried at once. Delivery is `lib/settled-report-note.ts` — one message per batch, appended in place while it waits in the parent's queue (see [sessions.md](sessions.md)); this module is only the index of what has not arrived yet. — `kind`, the run's own `id`, a one-line `title`, `outcome`, `finishedAtMs`, the `parentSessionId`, the report's `customType`, a `markerId`, and a `fetchHint` spelled so the model can copy it (`get_subagent_result("…")`, `read("<log path>")`). It stores no output on purpose: the entry exists to let the model decide whether to fetch, not to pre-load the answer into another turn's context.
- **Delivery is read off the parent's transcript, never tracked here.** The report message carries `{ notificationId }` in its `details`; `pendingNotificationsFor()` filters out any entry whose marker is already in the session's entries and drops those from the registry as it goes. Tracking "sent" instead would have to guess when pi appends a queued message — it appends at the queue drain, not when the notifier resolved. The marker survives that drain: pi persists any custom message it appends through `appendCustomMessageEntry(customType, content, display, details)`, including one taken from its follow-up queue (`agent-session.js:757`).
- **Reading a result clears it without waiting for the batch.** `get_subagent_result` on a settled background run removes that report's entry (`removePendingNotification()`) as it marks the run collected, so the tool and the turn-boundary reminder stop naming a result the parent already holds — even while the batch it belonged to is still queued. The report itself is withdrawn from that batch too ([sessions.md](sessions.md)). The transcript rule above still handles the ordinary path: a report that lands without anyone collecting it is cleared by the message that carries it.
- **The entry to read is a `custom_message`, and its `details` sits at the entry's top level.** `appendCustomMessageEntry()` (`core/session-manager.js`) appends `{ type: "custom_message", customType, content, display, details, … }` and `getEntries()` hands those raw entries back, so `deliveredNotificationIds()` matches on `type === "custom_message"` and reads `entry.details`. Reading `entry.message.details` off a `"message"`-typed entry instead finds nothing: every delivered batch went on being listed as pending, with a count that overstated the backlog — the one thing this index must never do. The suite fed that function the wrong shape for exactly that reason and stayed green, so `lib/__fixtures__/settled-report-custom-message.json` is one such entry copied verbatim out of a real session file and the test reads it.
- Counts are always exact and only the lines are capped (3 listed, 120-character one-line titles, `+N more`). A model that underestimates a backlog answers differently from one that knows its size, so truncation must never touch the number.
- The report prefixes carry only the guard, never the tool name. A delivered batch already carried its reports, so the reminder is the only hint the model gets; a report from before that rule keeps an extra sentence, which every strip path removes with the rest of the guard by cutting to the first blank line.
- **The reminder is the only reason to call the tool.** Its description says so, the reminder says so, and an empty answer says not to call again until the next reminder. A model that treats the index as a checker spends a call after every turn to learn nothing; the index is only non-empty between a report settling and the batch reaching the conversation, and the reminder is what names that window.
- While results are waiting, a **reminder is steered at every turn boundary** (`pi.on("turn_end")` in `lib/pending-notifications-extension.ts`): one model-only line naming the count, the split, the tool, and that only this reminder calls for it. A report waits for the run to end, which is the whole run — a model ten tool calls into a refactor would otherwise learn about a finished build only when it stopped. The reminder is steered rather than queued so it lands before the next response; it is `display: false` because pi's `convertToLlm` (`core/messages.js:89`) replays a custom message whatever `display` says while the chat skips it, so the model always reads it and no card appears. One reminder per batch: the announced ids are remembered, a later batch is reminded about again, and a batch that has reached the conversation is not reminded about at all.
- The reminder carries its own guard prefix, for the reason the reports do: pi replays it as a `user` turn, so a compaction pass would otherwise file "there are background results waiting" under the user's goals. Its `details` deliberately holds no `notificationId` — a reminder must never be mistaken for a report and clear the index.
- The tool is `model-only` like the subagent control tools: pi never lets another tool call a `model-only` tool through `ctx.executeTool()`, so a codemode script cannot decide when the parent learns a result exists. It takes no arguments and reads the calling session off `ctx.sessionManager`.
- It is its own extension (`lib/pending-notifications-extension.ts`), not part of the subagent one. It is deliberately *not* marked `replaceable`: the index is pi-web's own state, so a user extension registering the same tool name is a real conflict to report rather than one to step aside from (unlike the bash tool, where `preferUserBashExtension` yields to the user on purpose). The two switches are independent and the subagent extension's factory registers nothing at all when built-in subagents are off — hosting the index there would take the background-command entries down with it.
- The index is in-process only: a restart loses what was pending, exactly as the notification it never delivered was lost. What the transcript already holds (the report card, the log file, the subagent session) stays readable. Nothing re-derives the index from disk.
- Registered on ordinary sessions only — a child subagent runs with a restricted resource set (`subagentResources`) and gets no index of its own, so a nested background run is listed in its own parent's index, not the grandparent's.
- Files: `lib/pending-notifications.ts`, `lib/pending-notifications-extension.ts`, `lib/settled-report-note.ts`, the recording in `lib/bash-bg-tasks.ts` and `notifyParent` in `lib/subagent-runtime.ts`, the guard in `BG_TASK_NOTIFICATION_PREFIX` and `SUBAGENT_NOTIFICATION_PREFIX`, and `lib/pending-notifications.test.mjs`.
