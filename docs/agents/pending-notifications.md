# Pending background results index

A background command or subagent run settles while its parent is mid-run. The report itself reaches the parent when that run ends (pi drains its follow-up queue there — see [background-bash.md](background-bash.md) and [subagents.md](subagents.md)), so between the two moments the parent has no way to know a result exists. `lib/pending-notifications.ts` is that missing index and the `pending_notifications` tool is how the model reads it.

- The registry holds one entry per settled report — `kind`, the run's own `id`, a one-line `title`, `outcome`, `finishedAtMs`, the `parentSessionId`, the report's `customType`, a `markerId`, and a `fetchHint` spelled so the model can copy it (`get_subagent_result("…")`, `read("<log path>")`). It stores no output on purpose: the entry exists to let the model decide whether to fetch, not to pre-load the answer into another turn's context.
- **Delivery is read off the parent's transcript, never tracked here.** The report message carries `{ notificationId }` in its `details`; `pendingNotificationsFor()` filters out any entry whose marker is already in the session's entries and drops those from the registry as it goes. Tracking "sent" instead would have to guess when pi appends a queued message — it appends at the queue drain, not when the notifier resolved. The marker survives that drain: pi persists any custom message it appends through `appendCustomMessageEntry(customType, content, display, details)`, including one taken from its follow-up queue (`agent-session.js:757`).
- Counts are always exact and only the lines are capped (3 listed, 120-character one-line titles, `+N more`). A model that underestimates a backlog answers differently from one that knows its size, so truncation must never touch the number.
- The tool is `model-only` like the subagent control tools: pi never lets another tool call a `model-only` tool through `ctx.executeTool()`, so a codemode script cannot decide when the parent learns a result exists. It takes no arguments and reads the calling session off `ctx.sessionManager`.
- It is its own extension (`lib/pending-notifications-extension.ts`), not part of the subagent one. It is deliberately *not* marked `replaceable`: the index is pi-web's own state, so a user extension registering the same tool name is a real conflict to report rather than one to step aside from (unlike the bash tool, where `preferUserBashExtension` yields to the user on purpose). The two switches are independent and the subagent extension's factory registers nothing at all when built-in subagents are off — hosting the index there would take the background-command entries down with it.
- Both report prefixes name the tool inside their own constant (`PENDING_HINT_SENTENCE` in `lib/pending-notifications.ts`), so the report is the model's first hint that siblings may exist. The sentence is part of the constant because every screen path strips by `startsWith(PREFIX)`; a dynamic per-report count inside that invisible paragraph would need a second protocol for text that must never render. So the number lives in the tool and the UI, not in the report.
- The index is in-process only: a restart loses what was pending, exactly as the notification it never delivered was lost. What the transcript already holds (the report card, the log file, the subagent session) stays readable. Nothing re-derives the index from disk.
- Registered on ordinary sessions only — a child subagent runs with a restricted resource set (`subagentResources`) and gets no index of its own, so a nested background run is listed in its own parent's index, not the grandparent's.
- Files: `lib/pending-notifications.ts`, `lib/pending-notifications-extension.ts`, `lib/settled-report-delivery.ts`, the recording in `lib/bash-bg-tasks.ts` and `notifyParent` in `lib/subagent-runtime.ts`, the hint in `BG_TASK_NOTIFICATION_PREFIX` and `SUBAGENT_NOTIFICATION_PREFIX`, and `lib/pending-notifications.test.mjs`.
