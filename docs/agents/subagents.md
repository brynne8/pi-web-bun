# Built-in subagents

## Built-in subagents
- Profiles accept `codemode: inherit | on | off` (missing means `off`). Inherit follows whether `codemode` is active in the parent session at spawn (so Always on, a project override, or the MCP extension switching it on under Automatic), not the parent's `codemode.mode` or `inlineBudget`, which the child reads from its own settings. The child loads only the codemode factory (`createSubagentCodemodeExtension()`, an inline extension because `noExtensions` drops `builtin:` ones; it reads `-builtin:codemode` itself on every load), never the normal session's MCP host or tool-search, and scripts call only the tools the child admits (see the allowlist below). The resolved choice is saved in `resourceSnapshot` (`codemode: true`, `codemode` in `tools`) for reload, resume and RPC reopen; old snapshots without the field keep their previous resource policy. Changing a profile applies to new children, not existing sessions. A Chat-only profile (no tools, skills or extensions) stays Chat only under inheritance and rejects an explicit `on`. A snapshot that cannot restore the child's resource policy is refused instead of being reopened as a normal session.
- Profiles accept `mcp: on | off` (missing means `off`; `true` reads as `on`; no `inherit`). A child with `mcp: on` loads `builtin:tool-search` and `builtin:mcp` with an `McpHost` of its own (`createSubagentMcpExtensions()`), so it connects the servers in `mcp.json` (project ones under the same trust rules) and nothing else of the normal session. They are named in `additionalExtensionPaths` (`SUBAGENT_MCP_EXTENSION_PATHS`), which loads a built-in under `noExtensions` as well and keeps the `builtin:mcp` path the host and the policies recognise; that also bypasses `-builtin:` settings, so each factory reads its switch on every load, as the child's Code mode does, and `scopeSubagentExtensions()` never drops them. Without Code mode the host registers `codemode` servers as `deferred` (`codemodeAvailable` is the child's Code mode, not the sandbox), and the allowlist adds `tool_search`. An allowlist admits MCP tools by name (`mcp__*` and the resource tools), since servers connect long after it is fixed. `createSubagentMcpPolicyExtension()` then blocks an MCP-named tool another extension registers unless the profile selected it, and, while the child's built-in tools are read-only (Explore, Plan), every MCP tool without `readOnlyHint: true`, codemode scripts included; a profile of extension tools alone is not read-only. A chat-only profile rejects `mcp: on`. The snapshot keeps `mcp: true`, so reload, resume and RPC reopen load the same; an older snapshot loads no MCP. A run prompts the SDK session directly, so `prepareChildMcp()` calls the wrapper's `prepareMcpForRun()` first: it waits for servers with `direct` tools as a sent prompt does, and abortSubagent, the parent's Stop and Stop in the child's chat all end the wait and abort the run before it starts (the wrapper's `isRunning()` is false meanwhile, so `steer_subagent` is refused). Each child connects its own servers (stdio servers start again); the wrapper disposes its host when it closes, and idle release applies. The Agents panel switches it under Resources, disabled for a chat-only draft unless it is already on (the switch can still turn it off), with a line saying why; a save that names no value keeps the file's, and a profile that never had it gets no key. `lib/subagent-mcp.integration.test.mjs` pins this against a real stdio server.
- The global `builtInEnabled` in `~/.pi/agent/agents/settings.json` is off when the file or field is absent and when the file is malformed (fail closed); writes are atomic and keep unknown fields. The inline extension factory is always present, so a reload can apply the switch, but registers no tools while off; after changing it the user must reload the session explicitly, and `Agent` dispatch re-checks the setting so a stale call cannot start a subagent. When on, only a recognized legacy `pi-subagents` extension registering a reserved tool (`Agent`, `get_subagent_result`, `steer_subagent`, `abort_subagent`) is removed, along with the conflict errors it caused; unrelated extensions stay. ADR 0003.
- The four tools register with `exposure: "model-only"`, so `ctx.executeTool()` (a codemode script) cannot start, collect, steer or stop a subagent: a script-started run would record the nested call id (`<codemode call>/<n>`) as its `parentToolCallId`, which no transcript entry carries, and the chat would lose its link to the child session. `lib/subagent-extension.integration.test.mjs` pins this against a real `AgentSession`.
- A prompt typed into a child's own chat (`POST /api/agent/[id]`) is adopted as a resumed run: `AgentSessionWrapper` calls `onPromptAccepted` once pi accepts the prompt, and the controller's `beginDirectPrompt()` writes a `running` status before the turn starts and records the result when the prompt settles. The parent is told then, as after `resume`, and `get_subagent_result` / `abort_subagent` see the run meanwhile. A `streamingBehavior` prompt joins the run already there and starts no second one; a child that already has a live run in the map is left alone. This is the way back after a restart cut a child off: without it the prompt was invisible to the run record and the file kept its old `running` status, so no result and no report ever followed. Upstream has no hook here.
- A run stays in `getSubagentRuns()` from dispatch until its result entry is written, so `get()` reports a persisted `running` / `queued` status with no result and no running wrapper as `interrupted`: its process stopped and nothing will finish it (otherwise `get_subagent_result({ wait: true })` polls forever after a restart). The session list settles it the same way (`settleOrphanedSubagentStatus()` in `mapScannedSession`): a restart used to leave the agent switcher and viewer spinner on `running` for good while the top bar's badge, which reads live wrappers, said the run had ended. The live wrapper's runtime row then overlays that status in `mergeSessionLists()`, because only it can tell a queued child from an orphan; `getRpcSessionInfos()` derives that status from a running wrapper, the live run map (`getLiveSubagentStatus()`), or the settled file. `start()` writes the child's session file at dispatch (`persistChildSession()`): pi creates one only once a user or assistant message exists, so a run stopped while queued or connecting MCP servers, or refused for missing credentials, kept its entries in memory only and was gone (from `get()`, `resume` and the sidebar) once its idle wrapper was released. `setSessionFile()` reloads the written file, so pi appends every later entry; a queued run a restart cuts off reads as `interrupted` like a running one. The file is the only record of a settled run: one kept in memory as well would outlive a deleted child, and `resume` would reopen its missing file as a new, unrestricted session in the server's cwd.
- Built-in profiles (`general-purpose`, `explore`, `plan`) are switched off by name in that file's `disabledBuiltIns`, never by copying them to a `.md` file (ADR 0005). `builtInProfiles()` stamps `enabled` onto them so the panel, the `Agent` tool description and `resolveSubagentProfile` agree. Writes are minimal edits that keep names they did not touch, including ones no built-in claims; reading fails *open* (the feature switch has already failed closed). `PATCH /api/subagents/profiles` with `scope: "builtin"` writes it; `PUT`/`DELETE` refuse that scope. A same-name file replaces the built-in outright and is switched off through its own frontmatter. Only the switch is live for a built-in; the rest of the form is read-only.
- A positive `max_turns` allows one wrap-up turn only when the SDK would otherwise continue. The limiter chains the SDK's awaited `finishTurn` hook and ends unfinished work without cancelling a completed answer. The wrap-up turn sets `steeringMode` to `all` so a steer queued earlier cannot hold the instruction back. An `end` decision alone does not stop the run: AgentSession starts another run for anything still queued, so the limiter clears the queues, lists those messages in the turn-limit error, and refuses `steer_subagent` from then on. Exhaustion is a failed run with that error and any partial output. A request that ends with `stopReason: "aborted"` is `aborted` even when the controller did not ask for it (Stop in the child's own chat); a provider error is `failed`.
- `notifyParent` skips a background run's completion notification when the parent already collected that result with `get_subagent_result`, which marks it consumed. The mark names the run (`sessionId` + `completedAt`), never just the session, since `resume` reuses the session id; `resume` keeps the mark. The notification is queued the moment the run settles: pi appends a message that arrives mid-run when that run ends, so the wait is bounded by one run. Holding it until the parent fell idle is what delivered reports forty minutes late, in a burst, and what the parent's *state* must never decide again. The one wait left is a `get_subagent_result` in flight for **that** run — the parent polled with `wait: true` and is about to receive the same text as a tool result — registered by `beginSubagentResultCollection()` and awaited (capped at `RESULT_COLLECTION_GRACE_MS`) by `awaitSubagentResultCollection()` before the mark is re-checked. The tool description keeps the model from calling it on its own: it is for a report no longer in the conversation or a user's ask, never for checking or waiting. A foreground `Agent` call already returns its result, and a background run's report arrives with its session id and the `get_subagent_result` hint, so neither needs a proactive call. Upstream's description calls it a generic result check, which invites a model to poll a run that reports itself.
- A queued report is delivered when pi's loop *would stop* (`agent-loop.js`: after the run's last tool call and any steering), so it never interrupts a tool call in flight; the collection mark is keyed by session id, so a parent collecting run A suppresses A alone and cannot hold run B's report back. Two things follow and are accepted: suppression is decided at queue time, since pi has no retract and its queue is not ours to edit, so a parent that starts polling after the run settled gets both the tool result and the notification; and the composer's recall (`clear_queue`) clears pi's low-level queue as well, which drops a queued report with it — the run's card and result stay readable, only that announcement is gone.
- A report reaching a running parent is queued through pi's follow-up queue and appended when that run ends. **The queue's mode is left alone.** A batch is one queue element that keeps growing, so N finished runs share one message and land in one turn instead of waking the parent N times, each wake waiting out the previous report's turn. Nothing here reads or writes `agent.followUpMode`: raising it to `all` only helped while the parent was already running, which is not when these tasks finish, and `AgentSession.setFollowUpMode` is not used either because it writes the settings file the pi CLI shares.
- A background run's report is handed to the settled-report sink, which batches it with whatever else is waiting for that parent ([pending-notifications.md](pending-notifications.md), and the batch itself in [sessions.md](sessions.md)). It is indexed as pending until it reaches the parent: title `description`, fetch hint `get_subagent_result("<sessionId>")`. The pending index and the collected-result mark are different things — the mark answers "the parent already holds this result", the index answers "the parent has not seen this yet", and only the second one is a list the model can query.
- The notification is a `custom` message, which pi's `convertToLlm` replays as a plain `user` turn, so `subagentNotificationText()` prefixes `SUBAGENT_NOTIFICATION_PREFIX`; otherwise compaction files the report under the user's Goal / Constraints. Keep the prefix in code, never in a profile prompt, so the model cannot drop it. A `resume`d run's notification adds a line saying it supersedes the earlier report, which it would otherwise repeat word for word. Foreground `Agent` and `get_subagent_result` results are `toolResult`s and keep the bare `subagentFinalText()`.
- **That prefix is the model's and never the reader's.** It must stay in the session file — it is what the model was given — and every screen path takes it back off with `stripSubagentNotificationPrefix()` (`lib/subagent-notification.ts`), the body and the collapsed header's preview alike. Copy is the one exception: it copies what the file holds. The constant and the strip live in their own client-safe module, next to the background command's, because `lib/subagent-extension.ts` imports the SDK and cannot be pulled into a component; a report that reaches the screen with its guard on it is a bug, not a style choice.
- Profile files (`~/.pi/agent/agents/*.md`, project `.pi/agents/*.md`) are shared with other runtimes: a save round-trips every frontmatter key outside `MANAGED_FRONTMATTER_KEYS` (`lib/subagents.ts`; e.g. `name`, `allowed_subagents`, `exclude_extensions`, `disallowed_tools`) and carries foreign `ext:` tool selectors through. The pi-subagents aliases `skills` / `extensions` are seeded on first save and kept in step with `load_skills` / `load_extensions` while they hold a boolean (or `none` / `all`); a whitelist such as `extensions: pi-advisor-flow` is never rewritten, and the flags fall back to the aliases when `load_skills` / `load_extensions` are absent.
- A `skills:` list (`[review, testing]` or `review, testing`) preloads those skills' bodies (frontmatter stripped) into the child's prompt in both prompt modes and hides the catalog, as pi-subagents does; `lib/subagent-skills.ts`. Names are looked up among the skills the SDK discovered (so trust, packages and collisions apply), never used as paths, and `disable-model-invocation` skills may be named. A missing or unreadable name becomes one line in the prompt; the rest still load. Parsing is lenient: empty and non-string items are dropped and an empty value means no list, because a profile that fails to parse disappears from the list and from `Agent`. `true` / `all` / `none` / `false` stay switch spellings, `[]` names nothing, and `load_skills: false` wins over a list. Off is pi's `noSkills`, which keeps skills an extension provides. Without a list, replace mode appends pi's catalog while `read` or `bash` is active, as pi's `--system-prompt` does, and **the same listing also goes out as its own user turn ahead of the task** (`getSkillCatalogMessage()` in `lib/subagent-skills.ts`, prompted before the delegated task in `lib/subagent-runtime.ts`). A `<skills>` section in a system prompt is routinely skipped: the agent guessed a path (`~/.agents/skills/...`) or searched the filesystem with `find /` before landing on the declared `<location>`, while the same listing in the turn immediately before the task is read and its `<location>` used verbatim (3/3 on step-5-preview, 5/6 on gpt-6.1-sol — the one loss was a transport stall). The system-prompt copy stays: dropping it would only save tokens while turning a missed injection into a total loss of the catalog. That turn is sent only when there is a catalog to send — not with skills off, and not in named mode, which already inlines each body with its `Location` — because an instruction with no catalog invites a false "there is no `<available_skills>` block" claim. The snapshot keeps the names, never bodies or paths, so resume and reopen reread current bodies; a malformed snapshot list narrows to what it names and never widens to the catalog. The Agents panel has no editor for the list: it shows it read-only under the skills switch, and a save keeps the authored spelling.
- An `extensions:` list (`[codegraph, "@team/adapter"]` or `codegraph, @team/adapter`) limits which extensions a child keeps, as pi-subagents does: `scopeSubagentExtensions()` (`lib/subagents.ts`) is an `extensionsOverride` that drops the rest after the SDK loaded them, together with the providers and models their factories queued. A dropped extension binds no handlers, tools or commands, but its factory has already run once, so this scopes the child; it is not a sandbox. Selecting paths before import would mean reaching into SDK internals on every reload (#1035). Names resolve like `ext:` selectors (directory, file or package name, case-insensitive), and a name two sources claim keeps neither. Path entries load nothing: a project profile must not load code that project trust gates. pi-web's own `<inline:…>` extensions always stay. `*` keeps every extension, `none` / `false` switch extensions off, and `load_extensions: false` wins over a list; the list parses as leniently as `skills:`. The SDK reapplies the override on every reload, and the snapshot keeps the names, so resume and RPC reopen get the same scope through `subagentExtensionLoaderOptions()`. `tools: ext:` still picks tools among the extensions that remain. The Agents panel shows the list read-only under the extensions switch, and a save keeps it as authored. `lib/subagent-extension-scope.integration.test.mjs` pins spawn, reload, resume and reopen against a real `AgentSession`.
- A child that loads extensions without `ext:` selectors (the Agents panel's extensions switch) gets no `tools` allowlist: the SDK fixes one when the session is created, so a tool an extension registers at `session_start` or later (pi's `dynamic-tools` example) would never be callable (#883). `subagentToolOptions()` (`lib/subagents.ts`) passes `noTools: "builtin"` with the profile's built-ins as `+name` entries and excludes the reserved tools and the SDK's other built-ins (`SDK_BUILTIN_TOOLS` mirrors pi's unexported list), so no extension can switch on one the profile leaves out. The snapshot's `allExtensionTools` makes reopen do the same; an older snapshot keeps its allowlist. `ext:` selectors still pass the names resolved at spawn: the SDK admits tools by name, with no source-aware hook, so a selected extension's late tools stay out. Such an allowlist also excludes every MCP tool it does not name (`mcp__*` and the resource tools): pi keeps those registered for codemode and `tool_search` unless the list names one, so a script could otherwise call an unselected extension's MCP tool; `ext:` selectors that `disallowed_tools` cancels out admit no extension tool. `lib/subagent-codemode-scope.integration.test.mjs` pins this. `lib/subagent-late-tools.integration.test.mjs` pins spawn, reload and reopen.

## Stopping a run
- `abort_subagent` (`lib/subagent-extension.ts`) hands the stop to the model that delegated. Upstream wrote the stop and left it unreachable: its `abort()` (`lib/subagent-runtime.ts`) takes a queued run out of the queue, ends `mcpWait` for one still connecting its MCP servers, and calls `inner.abort()` on a running one, and `POST /api/subagents/[id] {"action":"abort"}` serves it, but no client screen calls that route and the model had three tools that could not stop anything. A background run is deliberately outside the parent's Stop — only a foreground run listens on the tool's `signal` (`handleParentAbort`) — so before this tool the only way to end one was to delete the session family (`lib/session-delete.ts`).
- The tool reads the run before stopping it: a terminal one answers `already <status>; nothing to stop` rather than throwing, and a run that settles between that read and the abort is reported as it is, not as a failure to stop. `abort()`'s own refusals (`Subagent is not running`, `Subagent is no longer queued`) reach the model only when the run is still not terminal.
- A run the parent stopped reports nothing back. The call holds the run's completion the way an in-flight `get_subagent_result` does (`beginResultCollection()`) and marks the settled background run consumed, so `notifyParent` finds the parent already holding the outcome; the answer takes the terminal run as its own result and names `get_subagent_result` and `resume` as the way back to the transcript. The wait for that terminal status is bounded by `ABORT_SETTLE_WAIT_MS`; past it the call says the stop was requested and leaves the notification alone, which is what would have arrived anyway. Foreground runs are never marked, since they never notify.
- The name is in `SUBAGENT_CONTROL_TOOL_NAMES`, so a child never gets it (`subagentToolOptions()` excludes the control tools), `navigate_tree` keeps it active (`SESSION_TOOL_NAMES` in `lib/rpc-manager.ts`), and a script cannot call it (model-only, above). `lib/subagent-extension.test.mjs` pins the answers, the consumption and the refusals; `lib/subagent-extension.integration.test.mjs` pins that a script cannot reach it.

## Delegation policy
- The delegation policy is appended to the text of every run's system prompt as `<delegation>…</delegation>` (`SUBAGENT_DELEGATION_BLOCK`, `withSubagentDelegationPrompt()`, added by a `before_agent_start` handler that returns `systemPrompt` — the same shape `pi-l` uses). It is not the tool's `promptGuidelines`: pi appends those to the one flat `<rules>` list every tool and pi's own "be concise" share, where a subagent policy reads as generic advice and is skipped. It is not a `sections` entry either: only this handler can name a section, and pi sends a *forced* prompt in place of the structured sections as soon as any extension forces one, so a section added by a handler that runs later reached neither the model nor the panel — with `pi-l` installed, sessions silently ran without the policy. Forcing has to read `event.systemPrompt` (rendered at the call, so an earlier plugin's forced text is carried along, never replaced) and append the block to it; the block tags itself because a forced prompt is plain text and pi wraps nothing around it. Order does not cost the block: pi orders these handlers by load order, and one that forces after us reads the already-forced text from the same getter and appends to it, so our block rides along. Only an extension that composes its prompt from `systemPromptOptions` instead of reading `event.systemPrompt` loses it — there is no hook that runs last, and no way to add a section pi would still render after a force. The switch gates the handler, so an off switch forces nothing and the session keeps pi's own prompt exactly. `subagentDelegationBlock(profiles)` gives `explore` and `plan` a rule of their own while they are enabled: a question about existing code goes to `explore`, which only reads, and a multi-file change gets `plan` before any edit. Any other enabled subagent is listed by name only, under `Other subagents`, since those two already carry their own sentence and a description copied into the block was read twice. The generic "prefer a read-only profile" line this replaced named no agent, so a model had nothing to connect it to. The list comes from the same `getProfiles()` the `Agent` tool is built from, so a profile that is disabled, renamed or authored locally appears or disappears in both places together, and `SUBAGENT_DELEGATION_BLOCK` is the block with no subagents for a session whose provider returns none. The tool's prompt snippet names the inspectable subagent session, says to delegate whenever possible, and points at the delegation section for detail, so a model that only skims the tool list is still steered to the block. Upstream ships delegation advice as the tool's `promptGuidelines`, rendered as ordinary rules bullets, and has no subagent list in the prompt.

## What the model may choose when spawning a subagent
- `Agent` offers `subagent_type`, `prompt`, `description`, `run_in_background`, `resume`, `model`, and `isolation`. Everything else about the spawn is decided without the model: thinking level, turn limit, and parent-context inheritance come from the profile's `thinking`, `max_turns`, and `inherit_context` frontmatter (editable in the Agents panel), and input files are not a per-call option either — the child reads whatever the `prompt` names; the one exception is a level a call writes into its own `model` (below). A per-call value for any of them used to win over the profile while never appearing in the tool description, so a model guessing `max_turns: 8` or `thinking: "high"` silently discarded what the profile had decided. The runtime reads `thinking` (falling back to the parent's level), `max_turns`, and `inherit_context` from the profile only. pi's validator allows keys the schema does not name, so a call that still sends one is accepted and the key ignored; transcripts holding such calls render and resume as before.
- `model` resolves as `request ?? profile`: the profile decides by default, and one run may go to a different model, which the tool description informs by listing each profile's own model and thinking level. A model reference, from the call or the profile, reads as pi's `--model` does: `provider/modelId` or a bare id, optionally ending in `:<thinking level>` (#1188). The whole reference is tried first, so an id that contains a colon (`qwen3:8b`) still matches, and a suffix that is no level is refused, never dropped. The level travels with its model: a call's `model: "x:high"` sets that run's thinking over the profile's, which is how one call picks a model and its level together without a separate `thinking` parameter for a model to guess; a call naming a model without a level keeps the profile's `thinking`. Within a profile, `thinking:` wins over a level on its own `model:`, as pi's `--thinking` does over `--model x:level`. pi clamps the level to what the model supports. The Agents panel shows such a profile model as its base model (not unavailable) with the reference as written; choosing another model there drops the level, which the Thinking field sets. There is no `input_files`: the delegated task is the `prompt` alone. A per-call list used to inline whole files from the session cwd into that task even though a subagent's own tools already include `read` and `bash`, which inflated the child's context and in practice pushed a freshly opened subagent straight into compaction; name the paths in the `prompt` instead. `isolation` stays a string, not a `"worktree"` literal, so a model that fills every optional field with `""` can still start a subagent; only `"worktree"` takes effect.
- `Agent` resume retains the child's profile, model, thinking level, and context. Its continuation prompt, description, and background mode can change. Nonempty creation options (`model`, `isolation`) are rejected before dispatch; empty defaults, and the keys the schema no longer names, remain compatible with tool startup. Start a new subagent to change those options. Resume refuses a child whose cwd no longer exists (an isolated child's worktree is removed when its run ends), as the wrapper's `send()` does, since a run prompts the SDK session directly, and its error tells the model to start a new subagent instead (#1202).
- An isolated run's `subagentFinalText()` says where its worktree is, since the model reads only `content` (#1202). It goes by whether the worktree path still exists when the run's result entry is written (`recordResult()`), and the entry keeps that as `worktreeExists`, so the child read back from its file says the same. Gone: removed, its branch keeping any commits, also when the checkout was removed during the run and git's removal then failed. Still there after this run's removal was refused for uncommitted or untracked files: kept at its path and branch, for that reason. Still there otherwise: still at its path and branch, with no reason, as after any resumed run (resume removes nothing, and an interrupted run never got to). Never in git's words, which end in `use --force to delete it`. An entry written without the field gets no sentence.

## Agent switcher usage
- Each row of the agent switcher (main agent and every subagent) shows its active time, total tokens and cost, with the stats popover's breakdown in its tooltip; the header shows their sum. `POST /api/sessions/stats` reads each id as `GET /api/sessions/[id]` does (a live wrapper's entries, else the cached file) and counts like the popover (`computeSessionStats()`, `computeSessionTotalActiveMs()`), never touching an `/api/agent/` route. A summary is kept per SessionManager until its entry count or last entry changes, since the switcher polls every 3 s on a visible page while any agent in the family runs, and reads once more when a run starts or ends. The toolbar's numbers are the main session's alone; the switcher's sum is the only place subagent spend adds up.
- The top bar's Agents badge counts the family's subagents, and while any of them runs it counts only those, accent-tinted and ringed by a spinner (`getAgentsBadge()`, `lib/session-family.ts`); the button's title and label say how many run. Running means listed by the sidebar's running poll, as in the switcher's header, so the badge adds no request of its own.

## The report on screen
- A subagent's result is Markdown: the `Agent` / `get_subagent_result` result text renders through `MarkdownBody` (`MarkdownResult` in `components/MessageView.tsx`, class `markdown-tool-result`) instead of the `<pre>` every other tool's output keeps. The report is what the child wrote, and a child writes headings, lists, tables and fenced code. Only a result whose `details.kind` is `pi-web-subagent` takes this path — `isSubagentToolDetails()` — because another tool's output is raw text, where a `*` or a `#` is a character and not markup. The card keeps its 12px scale (`app/globals.css`), not the answer's 14px, and a failed run's report stays in the card's error colour.
- The background notification and the viewer tab already render Markdown (`markdown-custom-message`, and `MessageView`'s text blocks); this closes the one path that did not, so the same report reads the same wherever it is opened.

## Viewer tab
- The `Agent` card's button opens the child as a read-only tab in the right panel (`components/SubagentViewer.tsx`, tab id `agent:<sessionId>`), beside file and terminal tabs. The agent switcher above the chat opens a child as the main chat from its row; the row's side-panel button toggles this tab (accent-coloured and filled while the open panel has it, active or not; a click then closes the tab, and the panel with its last tab) and leaves the switcher open, except on phones, where the panel covers the chat. The tab reads only `GET /api/sessions/[id]` and `GET /api/sessions/[id]/context` (a running wrapper's in-memory entries, else the file), never an `/api/agent/` route, so viewing cannot start, reopen or keep alive an `AgentSession`. While the sidebar's running poll lists the child, it polls the newest page every 2 s on a visible page, one request at a time; only the active tab is mounted, so a hidden or closed tab polls nothing. It shows finished entries only, not the streaming message.
- A poll is folded into the pages already loaded (`mergeTailPage()`, `components/subagent-viewer-state.ts`): if the newest page overlaps them, the older pages stay and shown messages keep their objects; otherwise it replaces them. "Load more" asks `before` the oldest entry and prepends only while that is still the oldest (`prependOlderPage()`), so a page is never prepended twice or over a gap. Session info is refetched when the run starts or ends, so the persisted status replaces the live one. Subagent tabs are not persisted and are dropped on every project switch (`changeFileWorkspace()`), while the file tabs are parked; an active subagent tab hands the panel to the restored project's file tabs.
