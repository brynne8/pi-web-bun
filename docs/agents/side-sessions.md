# Side sessions

Why it is built this way: [ADR 0007](../adr/0007-side-sessions.md).

## Creation

- `/btw` and `/btw <prompt>` are client-side built-ins (`BUILTIN_SLASH_COMMANDS`, `case "btw"` in `hooks/useAgentSession.ts`) with `availableWhileStreaming`: nothing reaches the model, no bubble. They post `{ side: true }` to `POST /api/sessions/[id]/fork`. The prompt is stashed per session id (`sideChatPrompts` in `AppShell`) and sent by the tab's `ChatWindow` as `initialPrompt`, once.
- **The command is the only way in.** Upstream also starts one from a Side chat icon in the composer's run-control row, from New side chat on the Agents switcher's main row, and from the selected-text popover's "Ask in side chat" ([#1469](https://github.com/agegr/pi-web/pull/1469)); none of those is here. A side chat is a deliberate act, and the composer's streaming row stays the fork's own Steer/Follow-up and Stop. The selected-text popover therefore offers **Quote** alone, which puts the selection in the composer as a Markdown blockquote and a blank line, nothing else, so the same action serves a question, a correction or an instruction (#1373); `insertQuote()` starts it on a paragraph of its own, since a quote after text on the same line is no blockquote. `/btw` then carries whatever the composer holds. This replaced "Ask in new chat", which forked at the selected message and moved the main chat away; a branch to keep working on is the message's New session or the sidebar's Fork.
- `createSideSession()` (`lib/session-fork.ts`) is `forkSessionBranch()`'s copy with another name and one more step: the `pi-web:side` entry is written as the file's second line and the first copied entry is chained under it, because `readSessionRelationEntries()` reads only the first lines, and the boundary message is written last, as the leaf. Just before it goes the parent's tool pin: `readSessionToolSelection()` reads the whole file, so a pin set on another branch binds the parent but would not be in the copy, and an empty pin would be lost, which is what decides between the normal and the Chat-only path. A shell-only branch works as it does for Fork. Refusals are `SessionForkError`'s; the client maps the codes to notices.
- A copy taken mid-run holds what is on disk: finished entries, so it can end on an unanswered prompt or on tool calls with no result (pi-ai sends "No result provided"). The parent's later turns never appear.

## Tools and prompt

- `startRpcSession()` treats a side chat as a normal session, or as Chat only when the parent's pin is empty. It passes pi's `tools` allow-list as `[]`, which registers and activates no tool at all: nothing the parent had, and no extension, MCP, Code mode or subagent tool. pi reads `[]` as "all off", as it does for a Chat-only session.
- **The model is told why.** pi's tools section only says `(none)` for a side chat, which reads like a broken loadout, so `startRpcSession()` queues `SIDE_NO_TOOLS_TEXT` on the agent's steering queue as a `role: "system"` message, the same way the subagent's tool notices reach their model: it is delivered before the first request, and `lib/session-reader.ts` filters system messages out again, so no card appears. pi persists it as a message entry, so a reopened side chat that already carries it is left alone (`hasSideNoToolsNotice()`); a Chat-only side chat is not told, since pi's own prompt is already tool-less.
- pi-web's built-in extensions are not created, so no MCP server connects. Other extensions, skills and context files load as usual, so the extension's prompt additions and provider models stay. pi lists skills only behind a reader tool, so a side chat's prompt has no skill index even though its skills are loaded.
- `navigateTree()` and `set_tools` cannot bring a tool back: the empty allow-list holds for the session's life, and `setRpcSessionTools()` refuses by metadata with "A side chat never has tools". Metadata that does not parse is refused by `startRpcSession()`.
- The prompt is the parent's. pi turns the tool change into one `role: "system"` message in the transcript before the first side message; Anthropic's request places it after that message (a system message must follow a user turn), OpenAI's before.
- **The boundary is a message, not a prompt section.** `SIDE_BOUNDARY_TEXT` is a `custom_message` with `display: false`: pi's `convertToLlm` sends it as a user turn, in place, on every provider, so it says it is not the user speaking. An addendum in the prompt told the model about "the first side-chat message" with nothing marking it: on models without mid-conversation updates it folds into the head, and a fork taken mid-run reads as two user messages in a row. Compaction serializes it like any user message (`[User]: [Side chat] …`), and "Edit from here" above it leaves a branch without it.

## Panel and switcher

- `components/SessionChatPanel.tsx` renders a side chat's or subagent's tab, tab id `agent:<sessionId>`: `ChatWindow` with `panel`, which leaves the global Esc to the main chat. Only the active tab is mounted. Side tabs and the active side tab are kept per main session in this browser tab's sessionStorage; switching sessions shows only that main session's tabs, and returning to it or reloading restores them once the session catalogue is loaded. A session without side tabs keeps no entry. A fork that returns after the main chat moved to another session is added to its parent's saved tabs, not opened beside the session now shown (`appendSideTab()`). Deleted side chats are discarded; subagent tabs remain open across session switches in the same project, but still drop on project switches and reloads. A read snapshot or a task log tab never joins a side chat's restore — both are transient as before, and the panel's permanent activity tab is what a dropped side tab falls back to.
- Rows live in the right rail's activity view (`components/ActivityAgents.tsx`, [subagents.md](subagents.md#agents-in-the-activity-view)), not in a popover of their own: a click opens the side chat in the main chat (the URL holds it, a reload keeps it, the sidebar highlights the parent's row, the "Main agent" row goes back), and the row's button toggles its tab with the side-chat wording — and reopens one that was closed. Upstream keeps the family in an Agents popover with a `RowSideButton` per row; the fork has no such popover. `isHiddenRelation()` is the one test for "a family member, not a sidebar row": unread, notifications, the sound and the tool preset control follow it.
- A tab acts as the main chat does on what leaves it: bare `/mcp` opens Settings › MCP, and `/clone` or a message's New session opens the copy in the main chat. Without these callbacks `/mcp` went to the model as text and the copy appeared nowhere.
- One session, one chat: two windows would share a draft key and stream the same run twice. An effect in `AppShell` closes the tab of whatever the main chat shows.
- Deleting one is upstream's, not ours: its switcher row carries Delete (`deleteSideChat()` in `lib/side-chat-client.ts`, which this branch keeps and its test covers) behind the sidebar's inline confirmation. There is no such row here, so a side chat goes when its parent does — `deleteSessions()` reads a side chat's relation and takes it with the family — or through the sidebar's Delete on the side chat itself once the main chat shows it.
- `renderMessage()` in `ChatWindow` draws the boundary message as the line (`SIDE_BOUNDARY_MESSAGE_TYPE`, client-safe in `lib/session-family.ts`). If it is not loaded (an older page) or compacted away, there is no line.
- Names: `createSideSession()` starts with `SIDE_SESSION_NAME`, and the first prompt replaces it with its first line (`sideChatNameFrom()`, the wrapper's `prompt` command; commands name nothing), which `/name` can change. Rows and tabs show it through `sideChatTitle()` with the same family list: unnamed side chats are numbered in creation order (`Side chat 1`, `Side chat 2`), whether their tabs are open or not. `AppShell` rereads the list when a run in an open side tab starts or ends; opening or closing other tabs does not change the numbering.
- `POST /api/sessions/stats` and the toolbar's totals (`GET /api/sessions/[id]`) count `sideOwnEntries()`, what a side chat added after `createdAt`. `/session` in the main chat shows pi's own `getSessionStats()`, the whole file; a tab has no stats popover, so it answers with one line of the chat's own numbers (`formatSessionSummary()`).
