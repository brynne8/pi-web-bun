# File access, worktrees and web auth

## Worktrees and project grouping
- `lib/worktree.ts` resolves linked worktree top-levels to the main repo `projectRoot`; `listAllSessions()` attaches it to each `SessionInfo`, so a repo's worktrees group together in the sidebar. A session whose cwd is a removed worktree is inferred back into the main project, never a phantom project row. `/api/models` resolves a cwd that is gone the same way (a finished sub-agent run removes its worktree, and its session still names it) and re-checks the repo it falls back to against the allowed roots, so the fallback only ever answers for a project that was already allowed. `/api/project-trust` does not fall back: trust is per path, the repo's decision is not the removed folder's, and trusting a folder that is gone is refused, so a GET answering for the repo would only offer a Trust button that fails.
- The root is the folder holding the common git dir only when that dir is its `.git`, or a bare repo a `.git` file there points at (`project/.bare`). Any other bare clone (`parent/repo.git`) is its own root (#1049): its parent may hold other clones, whose worktrees would all fall into one project, and that parent would become an allowed file root. `addWorktree()` uses the same root, so a bare clone's new worktrees go to `repo.git-worktrees/`.
- `/api/worktrees` serves worktree operations under the same allowed-root rules as `/api/files`. New worktrees go under `<repoRoot>-worktrees/<sanitized-branch>`; an existing branch is reused, else `git worktree add -b` creates it. Removing a dirty worktree answers `409 { dirty: true }`, and the UI asks before retrying with `force`.
- Two places switch or create worktrees, one component (`components/ProjectWorktreePicker.tsx`) on the sidebar's one listing of its cwd (`GET /api/worktrees?cwd=`, refetched when the cwd moves). The files' worktree box (the section below the sessions or the Files tab, whichever the layout shows; in the head above the explorer, beside the project box below the sessions, under it in the tab) switches, creates and removes; it shows at the top of a git checkout, a disabled box says why in a subdirectory of one (its root has the worktrees), and a folder outside any repository has no worktree box at all, the project box taking the whole width (the listing's `isGit` tells the two apart). A folder the listing last found outside git shows no "checking" box while it is listed again, which would only go and widen the project box: the browser keeps the last 50 such folders (`loadNonGitCwds()` / `rememberCwdGitStatus()` in `lib/sidebar-prefs.ts`, read-modify-write so other tabs' stay; one found in git leaves), so a reload knows them before its listing answers, the default dated folder included; only a folder this browser never listed shows the box once. The bar above a fresh composer (`components/NewSessionContextBar.tsx`) shows the same list under the same rule, and removes nothing. Both create through the sidebar (`createWorktree()`, also `SessionSidebarControl.createWorktree()`: `POST` with the project root); the files' picker then moves the sidebar's cwd there, the bar starts the new session there; opening either menu refetches the listing. Removal is `DELETE` with the project root; a dirty checkout answers 409 `dirty` and the picker asks before `force`. A group's "+" asks nothing: it starts in the current worktree or another project's root. Every GET `allowFileRoot()`s each listed worktree (the in-memory grant from `addWorktree` does not survive a restart), so a worktree picked there is browsable before it has a session. Clicking a session still moves the cwd to its worktree implicitly.
- git prints POSIX-style absolute paths even on Windows: every path read from git goes through `toNativePath()` (`lib/paths.ts`) before it is compared or returned, and paths are compared with `samePath()`, never `===` (otherwise `isTopLevel` is always false on Windows and the worktree switcher hides). Branch names are not paths and keep their forward slashes. Browser code cannot apply Node path rules, so `/api/worktrees` resolves `currentWorktreePath` server-side and the sidebar uses it for highlighting and the removal fallback.

## File access allow-list
- `/api/files` is not a general filesystem browser. Allowed roots: session cwds, their resolved project roots, and roots added with `allowFileRoot()`, which `/api/cwd/validate` and `/api/worktrees` call when they make a location browsable. "Use default directory" too: `/api/default-cwd` only creates `~/pi-cwd/YYYYMMDD`, and the sidebar selects it through `/api/cwd/validate`.
- `isPathWithinRoots()` (`lib/path-security.ts`) is the single implementation behind `isFilePathAllowed()` and is the security boundary: keep it the only one. It re-resolves and case-folds both sides, so either path form authorizes; roots are stored slash-normalized only as a Set-key convention.
- `isExistingPathWithinRoots()` refuses any path with a `..` segment (`hasParentDirectorySegment()`: authorization collapses `..` before following links, the filesystem after). Query-string and body paths reach that check verbatim. In `/api/files/[...path]` URL parsing drops literal `..` segments, and the route itself refuses an encoded slash inside a segment (`link%2F..%2Fx`), because a session-referenced file skips the existing-path check.
- `/api/files/...?sessionId=` also reads (never lists) a file outside the roots when that exact path appears in the session, so a chat link opens (`lib/session-file-references-core.ts`). Never counted: transcript system messages, the codemode script store, `context_edit` replacements, and the result of any tool but pi's coding tools and the subagent tools (MCP, codemode and third-party extensions relay remote-controlled text). Such a result still authorizes its `details.fullOutputPath` and the arguments of the coding-tool calls it made through `ctx.executeTool()` (`nestedCalls`), never those of its nested MCP calls. User and assistant messages, the model's own tool-call arguments (MCP calls included) and the other entries count. Tools are matched by name: keep the list in step with `CODING_TOOL_NAMES`.
- A UNC cwd (`\\host\share\dir`) must survive the `/api/files/[...path]` round-trip: `encodeFilePathForApi()` folds the `//` root into the first segment (`%2F%2Fhost`) and `filePathFromApiSegments()` decodes it back. Never split a UNC path into segments and rejoin them: `\\host\share` becomes a relative-looking `host/share` and every allow-check answers 403.
- What `type=list` leaves out is visibility, never access: hidden entries stay readable by path. `lib/file-tree-visibility.ts` asks one `git check-ignore --no-index --stdin` per listing, then one `git ls-files` which matched names hold a tracked path; those stay listed. Never let check-ignore consult the index (one whole-index scan per name). `.git` and `.DS_Store` are always hidden. The fixed name list (`node_modules`, `dist`, `build`, …) applies only where Git has no view: outside a work tree, when git fails or times out (5 s), and inside an ignored directory with nothing tracked below it. Names go to check-ignore as `./name` and to ls-files under `--literal-pathspecs`. Both calls pass `-c core.fsmonitor=false`, or expanding a folder runs a hook the repository configured.
- The files' eye switch (the files section's header row's fifth key below the sessions, before the changes view and the search; the head's in the Files tab), "Show ignored files" (a toggle with `aria-pressed`, off by default, kept per browser in `lib/sidebar-prefs.ts` and restored after hydration like the tab), lists with `type=list&hidden=1`: the Git-ignored and name-list entries come back with `hidden: "ignored" | "excluded"` (`getFileTreeHiddenReasons()`), and the tree dims them with the reason in the name's tooltip. `.git` and `.DS_Store` stay out either way; dotfiles get no rule of their own. Inside a hidden directory Git has no answer (nothing below it is tracked), so its entries inherit the parent's reason on the client. Toggling reloads open directories and marks collapsed ones for reload. Search and `@` mentions do not follow the switch.
- A directory link (symlink or Windows junction) is authorized by where it resolves (#748): one inside a root that leads outside every root is listed but refused beneath it. Never authorize the lexical path: a link committed to a cloned repo would expose `~/.ssh` or `/`. The listing reports its target as `outsideLinkTarget`; the explorer's "Allow browsing" posts `?type=allow-link` with it. `checkLinkedDirectoryApproval()` (`lib/linked-directory.ts`) requires the link's directory to be inside the roots after resolving links and the link to still point where the operator was shown; the route then `allowFileRoot()`s the target until the server restarts — the grant `/api/cwd/validate` gives any directory, so it widens nothing a caller could not already reach. A target that contains a root or the home folder (`/`, `~`, a parent of the project) is listed with `outsideLinkEncloses`, and the explorer confirms before allowing it.

## When the file tree reloads
- No watcher and no polling: the tree (root, every open folder, git status) reloads when a run ends, at most once a second while a run's tools finish (any top-level tool but the read-only preset's `read`/`grep`/`find`/`ls`: AppShell's `handleToolEnd`, from `useAgentSession`'s `onToolEnd`), when the window gets focus (changes made in an editor or terminal), after an upload, and on the refresh button (#1144). A reload keeps the open folders and shows no spinner.
- Open folders are kept per cwd for the page's life (`lib/file-tree-expansion.ts`: a module-level LRU of 20 folders, the one left longest ago dropped first; gone on reload). A cwd change saves the outgoing folder's set and restores the incoming one's (none for a folder not kept), so picking a session in another project and coming back does not fold the tree; an explorer that unmounts saves its set too. Highlights and the upload summary, conflict and error still start over. Nothing is listed ahead: the roots unmount while the new cwd loads, so each restored folder mounts open and lists itself (`TreeNode`'s mount effect), level by level as its parents list. A folder gone since is never listed, so its path never matches and stays inert; one that fails to list shows the error in place. The set saved is the one last committed (`expandedPathsRef`, synced by an effect declared before the cwd effect), never the state a cwd-change render still holds.

## A row's own actions

- A row of the file tree, of the search results or of the changed list acts on itself through its right-click menu and through nothing else: **Insert path into chat**, **Download file** (a file only — a folder has nothing to download) and the OS file manager item (`sidebar.openInFinder` / `openInExplorer` / `openInFileManager`, the same label the project's own button picks). They used to be two absolutely-positioned buttons drawn over the row's name on hover, which is exactly where a reader aims: the name span is `flex: 1`, so its box ran under them and the row's geometric centre fell *inside* the mention button, which is how the file-panel check came to fail with a real pointer click on one engine and get through on another. The file-row bullet in [tests.md](tests.md) keeps what that did to a click.
- One handler serves every row: `FileExplorer`'s root `onContextMenu` reads the closest `[data-file-row-path]`, so the tree, the search results and the changed list say the same thing about themselves and a new kind of row is not left without a menu. A right-click outside any row (the header keys, the upload area) keeps the browser's own menu, and so does an explorer mounted without `onRowMenu`.
- The items are the sidebar's one `SidebarMenu` (state `kind: "file"`, anchor `{ kind: "point" }` at the pointer), built by `fileMenuItems()` from the `FileRowTarget` the row named: mention inserts the same `@path ` text the `@` picker types (`buildAtMentionText()`), download builds an `<a download>` at the URL the hover link used (`?type=download`), and the menu's accessible name is `files.rowActions` so it says which file it acts on. Nothing else in the row opens it: there is no ⋯ button, so a keyboard or touch reader has no path to these actions — the same as when they were hover buttons, which no finger ever produced. Adding that path (a focusable row and the ContextMenu key, or a long-press like `hooks/useGroupDrag.ts`'s 350 ms) is open work, not an oversight to re-discover.
- Reveal posts `/api/open-in-explorer` with `revealFile`; the route's `cwd` form still opens a folder and is unchanged. `open -R` on macOS and `explorer /select,` on Windows select the file, because "查看这个文件" answered with its folder alone is not an answer; no Linux file manager has a reveal-from-terminal command, so `xdg-open` opens the folder that holds it. Same loopback guard and same allowed roots as the folder button (`fileManagerCommand()` takes the view), and the item is disabled with the reason when the browser is not the server's own machine. The e2e never clicks it: raising a real Finder window on whoever is running the suite is not a test. What each platform is asked to run is pinned in `lib/open-in-file-manager.test.mjs`, and what the route refuses before spawning anything is in its own test.

## Uploads and chat drops
- The explorer's Upload button and a non-image file dropped onto the chat share one client, `uploadFiles()` (`lib/file-upload-client.ts`), and the one endpoint, `POST /api/files/<cwd>?type=upload`; never add a second write path for drops. The explorer asks `upload-check` first and lets the user replace or skip; a chat drop goes straight to `conflict=skip`, so it never replaces a file. It then inserts `@name` for every file the response lists as uploaded *or* skipped (a skipped name is a file already there, often the very file dragged out of the project) and says in a notice that the mention points to the existing file.
- Dropped images still attach to the prompt. Folders are left out with a notice: the endpoint writes flat file names only (`validateUploadFileNames()`), and the browser cannot tell where a dropped file lives on disk, so the copy always lands in the cwd root.
- The composer's attach button (#1101, for phones that cannot drop) is a drop by another route: its file input has no `accept` list (and no `capture`, so phones still offer photos and the camera), and `ChatInput` hands the whole selection to ChatWindow's `onAttachFiles`, which calls the drop handler. Images attach, other files upload and get mentioned, with the same notices; keep one path for both. A `ChatInput` without `onAttachFiles` keeps `accept="image/*"`.

## CSV/TSV files open as a table
- `.csv` / `.tsv` (matched by extension, `isDelimitedTablePath()`) open in `FileViewer`'s Preview mode as `components/DelimitedTable.tsx`, the way markdown and HTML open rendered; Source stays one click away and a restored choice wins. No server change: `/api/files ?type=read` still answers `language: "text"` for them.
- `lib/delimited-table.ts` parses RFC 4180 itself (quoted delimiters, `""`, line breaks inside quotes, LF/CRLF, BOM, blank lines skipped) and is lenient where files are not (stray quotes, ragged rows). A `.tsv` always splits on tabs; a `.csv` takes `,` unless its first records split more consistently on `;`, tab or `|` (Excel in many locales writes `;`). The first record is the header.
- The gutter is the file line each record **starts** on (counted by LF, as the source view numbers lines), not the record index, so a quoted field with line breaks does not shift later rows.
- The table also shows a **slice** of a file — a `read` tool call's result, which starts mid-file (see `sessions.md`). `parseDelimitedTable()` and `DelimitedTable` take `firstLine` (the file line the text starts on, so the gutter keeps the file's numbering) and `hasHeader` (default: only text starting at line 1 can carry a header row). A mid-file slice therefore eats no record as a header: every record is a row and the columns are `#1…#N`. A slice cut inside a quoted multi-line field mis-splits for any parser, so the caller warns above the table (the table cannot know where its text came from).
- Large files arrive in 256 KB chunks with "Load more". The table shows a loaded prefix too (`complete: false`): its last record is dropped unless a line break outside quotes ends it, so a record cut mid-field never shows; it appears once the next chunk loads. Markdown and HTML keep their preview off while truncated.
- Rows have one fixed height and only those around the viewport are rendered (`visibleRowRange()`, the SessionTree approach; no virtualization library). The table scrolls inside the viewer's own content box (`scrollRef`), so its scroll position is saved and restored like the source view's; it reads the box in a passive effect because the parent's ref is not attached yet in the child's layout effects. Column widths come from up to 500 sampled rows, clamped to 64–420 px; a cell ellipsizes and its full value is its tooltip. Gutter and header use `--bg-panel`, opaque, so columns scrolling under the sticky strips never show through.
- `FILE_CODE_STYLE` and `FILE_LINE_NUMBER_STYLE` (`components/FileViewer.tsx`) are exported and shared: the source view (highlighted and the past-the-limit plain fallback), the diff view and `components/ReadSnapshotViewer.tsx` all take their type and their gutter from that one pair, so a size change moves all of them together and no view carries its own copy.
- The gutter is `position: sticky; left: 0` against the viewer's own `overflow: auto` scroller (`.file-viewer-content`; the snapshot panel's wrapper). It only has room to travel because every row spans the widest line — `width: max-content` on the `<pre>` or wrapper plus `min-width: 100%` on each `.file-source-line`. Drop either half and a short line's number slides away behind its text again, so that coupling, not the sticky rule, is what a later edit breaks by accident (wrap mode sets `width: 100%` and never scrolls sideways, so nothing travels there).
- The gutter repeats the code line's height in px, so `fontSize` × `lineHeight` in `FILE_CODE_STYLE` and the px `lineHeight` in `FILE_LINE_NUMBER_STYLE` are one fact: 12px on a 1.6 leading means `19.2px` (the font is down from 13px, the gutter from 20.8px). `components/FileViewer.test.mjs` pins the product and the sticky pair.

## Which lines wrap

- The wrap choice (`wrapLines` in `lib/file-viewer-state.ts`) belongs to the source view and the diff view; a rendered preview (markdown, HTML, table) has no lines, so `FileViewer` offers the button in those two modes only. The diff box follows the source box's width rule (`100%` wrapped, `max-content` not), which is also the case where the sticky gutter has nothing to travel over (above).
- A file whose reader never pressed the button wraps by its kind: prose (`PROSE_EXTENSIONS` — md, markdown, mdx, mdown, mkd, rst, adoc, txt) opens wrapped and everything else does not. A long prose line is the same sentence going on, so sideways scroll only hides its end; code is read by its columns and indentation, so wrapping it breaks the cue and an editor's habit. `.txt` is on the prose side because it holds prose more often than structure; `.log` is deliberately not — a log line is a column (timestamp, level, message), and wrapping one puts the next line's timestamp where its message was. `wrapsByDefault()` and `resolveInitialWrapLines()` are the only two places knowing that list, and `getLanguage()` (`lib/file-types.ts`) is deliberately not consulted — it maps to a highlighter language, and `txt` and `text` are one value there while a prose default for them is a separate call.
- `FileViewerState.wrapLines` is optional: undefined means never chosen and keeps following the kind, a boolean either way is the reader's own and wins. So `openFileTab()` writes no wrap default at all — a tab opened straight into a diff (a Git-changes click) carries an unmade choice, and its markdown diff wraps. Setting `wrapLines: false` there would look the same on a `.ts` and silently veto the rule on a `.md`.
- A `read` card's slice (`components/ReadSnapshotViewer.tsx`) wraps by the same rule and carries the same key; see `sessions.md` for its Source / Preview switch and where its choices are kept. The table view has no lines, so its panel shows neither control.
- `components/FileViewer.test.mjs` pins both branches of the diff's wrap styles, the button's mode condition, and `lib/file-viewer-state.test.mjs` pins the kind rule (txt in, log out) and that an explicit choice beats it in either direction. The two header controls (`DisplayModeSwitch`, `WrapToggleButton`) and the row renderer (`SourceCodeRenderer`, which takes the slice's `firstLine` so a mid-file read's rows keep the file's own numbers) are exported from `components/FileViewer.tsx` for the snapshot panel to use rather than copy — `components/ReadSnapshotViewer.test.mjs` pins the shared imports.

## Web password throttling
- `lib/auth-throttle.ts` is deliberately global, not per-IP (its header says why). Failures double the delay (1 s → 60 s cap) for everyone; a success or 5 idle minutes resets it. The reset window must stay longer than the max delay, or waiting out one block restarts the burst.
- State lives on `globalThis` under `Symbol.for("pi-web:auth-throttle")`, so it survives hot reload and `proxy.ts` and the route handlers share it under both `next dev` and `next start`. Tests reset it with `recordAuthSuccess()`.
- `POST /api/web-auth` and every `Authorization: Basic` header on `/api/*` share the counter; `proxy.ts` checks Basic before its `/api/web-auth` exemption, so `GET /api/web-auth` is no unthrottled password oracle. A valid session cookie is checked first and never blocked. While blocked, Basic gets `429` even with the right password, and a Basic success never resets the counter (`proxy.ts` explains both).
