# File access, worktrees and web auth

## Worktrees and project grouping
- `lib/worktree.ts` resolves linked worktree top-levels to the main repo `projectRoot`; `listAllSessions()` attaches it to each `SessionInfo`, so a repo's worktrees group together in the sidebar. A session whose cwd is a removed worktree is inferred back into the main project, never a phantom project row. `/api/models` resolves a cwd that is gone the same way (a finished sub-agent run removes its worktree, and its session still names it) and re-checks the repo it falls back to against the allowed roots, so the fallback only ever answers for a project that was already allowed. `/api/project-trust` does not fall back: trust is per path, the repo's decision is not the removed folder's, and trusting a folder that is gone is refused, so a GET answering for the repo would only offer a Trust button that fails.
- `resolveProject()` caches each cwd's identity for a minute, then serves it stale while git runs again. A git run that never answered (a spawn out of fds, processes or memory, or git killed by the timeout) is never cached: that request alone gets the cwd as its own project, the next one asks again, and a background refresh keeps the stale identity. Whatever git itself exits with (outside a repository, at a mount point, dubious ownership, a broken `.git`), and a missing git, is the cwd's answer and cached, so a broken cwd does not spawn git and log on every session list. Classify by spawn error code and kill, never by git's message text.
- The root is the folder holding the common git dir only when that dir is its `.git`, or a bare repo a `.git` file there points at (`project/.bare`). Any other bare clone (`parent/repo.git`) is its own root (#1049): its parent may hold other clones, whose worktrees would all fall into one project, and that parent would become an allowed file root. `addWorktree()` uses the same root, so a bare clone's new worktrees go to `repo.git-worktrees/`.
- `/api/worktrees` serves worktree operations under the same allowed-root rules as `/api/files`. New worktrees go under `<repoRoot>-worktrees/<sanitized-branch>`; an existing branch is reused, else `git worktree add -b` creates it. Removing a dirty worktree answers `409 { dirty: true }`, and the UI asks before retrying with `force`.
- Two places switch or create worktrees, one component (`components/ProjectWorktreePicker.tsx`) on the sidebar's one listing of its cwd (`GET /api/worktrees?cwd=`, refetched when the cwd moves). The files' worktree box (the section below the sessions or the Files tab, whichever the layout shows; in the head above the explorer, beside the project box below the sessions, under it in the tab) switches, creates and removes; it shows at the top of a git checkout, a disabled box says why in a subdirectory of one (its root has the worktrees), and a folder outside any repository has no worktree box at all, the project box taking the whole width (the listing's `isGit` tells the two apart). A folder the listing last found outside git shows no "checking" box while it is listed again, which would only go and widen the project box: the browser keeps the last 50 such folders (`loadNonGitCwds()` / `rememberCwdGitStatus()` in `lib/sidebar-prefs.ts`, read-modify-write so other tabs' stay; one found in git leaves), so a reload knows them before its listing answers, the default dated folder included; only a folder this browser never listed shows the box once. The bar above a fresh composer (`components/NewSessionContextBar.tsx`) shows the same list under the same rule, and removes nothing. Both create through the sidebar (`createWorktree()`, also `SessionSidebarControl.createWorktree()`: `POST` with the project root); the files' picker then moves the sidebar's cwd there, the bar starts the new session there; opening either menu refetches the listing. Removal is `DELETE` with the project root; a dirty checkout answers 409 `dirty` and the picker asks before `force`. A group's "+" asks nothing: it starts in the current worktree or another project's root. Every GET `allowFileRoot()`s each listed worktree (the in-memory grant from `addWorktree` does not survive a restart), so a worktree picked there is browsable before it has a session. Clicking a session still moves the cwd to its worktree implicitly.
- The sidebar names its cwd's project with `projectForCwd()` (`lib/new-session-context.ts`): a folder it just validated, the listing of that cwd, a checkout in the listing, then the session list. The listing is still the previous cwd's for the commit after a move, and its checkouts count only when it is a checkout's (`isTopLevel`): a subdirectory's lists the repo's checkouts under the subdirectory's own key, so a click on a root session right after it gave that session the subdirectory's key, and `handleCwdChange` closed it as a project switch and rewrote the URL to `/` (#1289).
- git prints POSIX-style absolute paths even on Windows: every path read from git goes through `toNativePath()` (`lib/paths.ts`) before it is compared or returned, and paths are compared with `samePath()`, never `===` (otherwise `isTopLevel` is always false on Windows and the worktree switcher hides). Branch names are not paths and keep their forward slashes. Browser code cannot apply Node path rules, so `/api/worktrees` resolves `currentWorktreePath` server-side and the sidebar uses it for highlighting and the removal fallback.

## File access allow-list
- `/api/files` is not a general filesystem browser. Allowed roots: session cwds, their resolved project roots, and roots added with `allowFileRoot()`, which `/api/cwd/validate` and `/api/worktrees` call when they make a location browsable. "Use default directory" too: `/api/default-cwd` only creates `~/pi-cwd/YYYYMMDD`, and the sidebar selects it through `/api/cwd/validate`.
- `isPathWithinRoots()` (`lib/path-security.ts`) is the single implementation behind `isFilePathAllowed()` and is the security boundary: keep it the only one. It re-resolves and case-folds both sides, so either path form authorizes; roots are stored slash-normalized only as a Set-key convention.
- `isExistingPathWithinRoots()` refuses any path with a `..` segment (`hasParentDirectorySegment()`: authorization collapses `..` before following links, the filesystem after). Query-string and body paths reach that check verbatim. In `/api/files/[...path]` URL parsing drops literal `..` segments, and the route itself refuses an encoded slash inside a segment (`link%2F..%2Fx`), because a session-referenced file skips the existing-path check.
- `/api/files/...?sessionId=` also reads (never lists) a file outside the roots when that exact path appears in the session, so a chat link opens (`lib/session-file-references-core.ts`). Never counted: transcript system messages, the codemode script store, `context_edit` replacements, and the result of any tool but pi's coding tools and the subagent tools (MCP, codemode and third-party extensions relay remote-controlled text). Such a result still authorizes its `details.fullOutputPath` and the arguments of the coding-tool calls it made through `ctx.executeTool()` (`nestedCalls`), never those of its nested MCP calls. User and assistant messages, the model's own tool-call arguments (MCP calls included) and the other entries count. Tools are matched by name: keep the list in step with `CODING_TOOL_NAMES`.
- `proxy.ts` refuses cross-site browser requests to `/api/*` (`isApiRequestAllowed()`, `lib/request-security.ts`). The one file exception is a user-activated top-level GET (`navigate` + `document` + `Sec-Fetch-User: ?1`) of `type=read` on a `.pdf` (#1298): Android Chrome does not render a PDF in the viewer's iframe and shows a `data:` placeholder whose Open link arrives cross-site with no Origin. The route serves a `.pdf` only as `application/pdf` with nosniff, so the tab runs no script in the Pi Web origin and the opener cannot read it; never widen this to another `type` or extension (HTML, SVG, `watch`), and keep iframe/embed destinations refused.
- A UNC cwd (`\\host\share\dir`) must survive the `/api/files/[...path]` round-trip: `encodeFilePathForApi()` folds the `//` root into the first segment (`%2F%2Fhost`) and `filePathFromApiSegments()` decodes it back. Never split a UNC path into segments and rejoin them: `\\host\share` becomes a relative-looking `host/share` and every allow-check answers 403.
- What `type=list` leaves out is visibility, never access: hidden entries stay readable by path. `lib/file-tree-visibility.ts` asks one `git check-ignore --no-index --stdin` per listing, then one `git ls-files` which matched names hold a tracked path; those stay listed. Never let check-ignore consult the index (one whole-index scan per name). An answer is kept for 4 s per directory and name list (256 entries), because a restored tree asks one folder after another, and a fresh `.gitignore` still shows on the listing after a refresh. `.git` and `.DS_Store` are always hidden. The fixed name list (`node_modules`, `dist`, `build`, …) applies only where Git has no view: outside a work tree, when git fails or times out (5 s), and inside an ignored directory with nothing tracked below it. Names go to check-ignore as `./name` and to ls-files under `--literal-pathspecs`. Both calls pass `-c core.fsmonitor=false`, or expanding a folder runs a hook the repository configured.
- The files' eye switch (the files section's header row's fifth key below the sessions, before the changes view and the search; the head's in the Files tab), "Show ignored files" (a toggle with `aria-pressed`, off by default, kept per browser in `lib/sidebar-prefs.ts` and restored after hydration like the tab), lists with `type=list&hidden=1`: the Git-ignored and name-list entries come back with `hidden: "ignored" | "excluded"` (`getFileTreeHiddenReasons()`), and the tree dims them with the reason in the name's tooltip. `.git` and `.DS_Store` stay out either way; dotfiles get no rule of their own. Inside a hidden directory Git has no answer (nothing below it is tracked), so its entries inherit the parent's reason on the client. Toggling reloads open directories and marks collapsed ones for reload. Search and `@` mentions do not follow the switch.
- A directory link (symlink or Windows junction) is authorized by where it resolves (#748): one inside a root that leads outside every root is listed but refused beneath it. Never authorize the lexical path: a link committed to a cloned repo would expose `~/.ssh` or `/`. The listing reports its target as `outsideLinkTarget`; the explorer's "Allow browsing" posts `?type=allow-link` with it. `checkLinkedDirectoryApproval()` (`lib/linked-directory.ts`) requires the link's directory to be inside the roots after resolving links and the link to still point where the operator was shown; the route then `allowFileRoot()`s the target until the server restarts — the grant `/api/cwd/validate` gives any directory, so it widens nothing a caller could not already reach. A target that contains a root or the home folder (`/`, `~`, a parent of the project) is listed with `outsideLinkEncloses`, and the explorer confirms before allowing it.

## When the file tree reloads
- No watcher and no polling: the tree (root, every open folder, git status) reloads when a run ends, at most once a second while a run's tools finish (any top-level tool but the read-only preset's `read`/`grep`/`find`/`ls`: AppShell's `handleToolEnd`, from `useAgentSession`'s `onToolEnd`), when the window gets focus (changes made in an editor or terminal), after an upload, and on the refresh button (#1144). A reload keeps the open folders and shows no spinner. A collapsed folder listed before is only marked: it lists again when next opened, or a file dropped onto its row would be missing when it opens. The **first** listing waits until the files panel is in view (`treeVisible`): the explorer stays mounted with the folded section or the sessions tab, so a reader who only chats spawns no git process for it. The changed-files count is not part of the tree and loads either way.
- `/api/git/status` answers for the tree as it is now: the listing is read from Git on every request, never remembered, because the reloads above are what make a change visible and a listing older than the request is not an answer. The scan itself (`getGitStatus()` in `lib/git-changes.ts`) asks Git three questions at once — the repository root, the status, and the line stats of the tracked changes — since none of them depends on another, and Git names its paths by the repository root however it is asked, so asking from the folder itself answers what asking from the root does. The untracked files' lines are counted from their bytes, and a file that has not changed (its size, times and inode are the same) is not read again: the count is kept per path, and a file changed within the last two seconds is counted again every time, because a filesystem with coarse timestamps can leave a rewritten file's mtime where it was, and a file's own change time is the signal, since a program cannot set it back. The allow-list checks run on every request, so a revoked root is never answered for.
- Open folders are kept per cwd for the page's life (`lib/file-tree-expansion.ts`: a module-level LRU of 20 folders, the one left longest ago dropped first; gone on reload). A cwd change saves the outgoing folder's set and restores the incoming one's (none for a folder not kept), so picking a session in another project and coming back does not fold the tree; an explorer that unmounts saves its set too. Highlights and the upload summary, conflict and error still start over. Nothing is listed ahead: the roots unmount while the new cwd loads, so each restored folder mounts open and lists itself (the explorer's list effect), level by level as its parents list. A folder gone since is never listed, so its path never matches and stays inert; one that fails to list shows the error in place. The set saved is the one last committed (`expandedPathsRef`, synced by an effect declared before the cwd effect), never the state a cwd-change render still holds.
- Only the rows around the viewport are mounted. The expanded tree is flattened into one row list (`flattenFileTree()` in `lib/file-tree-rows.ts`: each row's path, depth, expanded state and, under an open folder that lists nothing, the block that says why — empty, a fetch error, or an unapproved outside link), and the sidebar's own scroller renders a window of it: fixed 24px rows at absolute offsets inside a spacer of the full height, an overscan, and any highlighted or drop-target row kept mounted — the `SessionTree` / `DelimitedTable` approach (`getVisibleRowIndices()`, `revealScrollTop()`). So a folder with thousands of entries mounts a few dozen rows, and because every row is a `memo` on identity-stable props (its callbacks and the drop/mention handlers behind a ref, read at event time), the 2.5 s running poll and a Git refresh re-render none of them. The tree and the changed-files list are mutually exclusive and each window themselves; the search results are capped at a handful of matches and render in full. Scroll position stays the sidebar's own; the fixed content above the list (upload feedback, the search box, the search results above the changed list) is measured so row 0 lands where it did, and a highlighted path is scrolled into view with the source view's reveal.

## A row's own actions

- A row of the file tree, of the search results or of the changed list acts on itself through its right-click menu and through nothing else: **Insert path into chat**, **Download file** (a file only — a folder has nothing to download), **Revert changes** (a file with a change Git can undo; see below) and the OS file manager item (`sidebar.openInFinder` / `openInExplorer` / `openInFileManager`, the same label the project's own button picks). They used to be two absolutely-positioned buttons drawn over the row's name on hover, which is exactly where a reader aims: the name span is `flex: 1`, so its box ran under them and the row's geometric centre fell *inside* the mention button, which is how the file-panel check came to fail with a real pointer click on one engine and get through on another. The file-row bullet in [tests.md](tests.md) keeps what that did to a click.
- One handler serves every row: `FileExplorer`'s root `onContextMenu` reads the closest `[data-file-row-path]`, so the tree, the search results and the changed list say the same thing about themselves and a new kind of row is not left without a menu. A right-click outside any row (the header keys, the upload area) keeps the browser's own menu, and so does an explorer mounted without `onRowMenu`.
- The items are the sidebar's one `SidebarMenu` (state `kind: "file"`, anchor `{ kind: "point" }` at the pointer), built by `fileMenuItems()` from the `FileRowTarget` the row named: mention inserts the same `@path ` text the `@` picker types (`buildAtMentionText()`), download builds an `<a download>` at the URL the hover link used (`?type=download`), and the menu's accessible name is `files.rowActions` so it says which file it acts on. Nothing else in the row opens it: there is no ⋯ button, so a keyboard or touch reader has no path to these actions — the same as when they were hover buttons, which no finger ever produced. Adding that path (a focusable row and the ContextMenu key, or a long-press like `hooks/useGroupDrag.ts`'s 350 ms) is open work, not an oversight to re-discover.
- Reveal posts `/api/open-in-explorer` with `revealFile`; the route's `cwd` form still opens a folder and is unchanged. `open -R` on macOS and `explorer /select,` on Windows select the file, because "查看这个文件" answered with its folder alone is not an answer; no Linux file manager has a reveal-from-terminal command, so `xdg-open` opens the folder that holds it. Same loopback guard and same allowed roots as the folder button (`fileManagerCommand()` takes the view), and the item is disabled with the reason when the browser is not the server's own machine. The e2e never clicks it: raising a real Finder window on whoever is running the suite is not a test. What each platform is asked to run is pinned in `lib/open-in-file-manager.test.mjs`, and what the route refuses before spawning anything is in its own test.

- Git names a repository by its **real** path (`git rev-parse --show-toplevel` says `/private/var/folders/…`, `/private/tmp/…`), while the file listing says the cwd it was handed (`/var/folders/…`, `/tmp/…` — links on macOS). `getGitStatus()` therefore rebases every reported path onto the cwd the caller asked about (`resolveExistingPath()`, `lib/paths.ts`: the nearest existing ancestor resolved, the rest kept as written), because a row carries its changed badge — and the Revert item — by matching the path the listing gave it against the status listing, and a disagreement of one link means no badge, no item, and a row that looks unchanged. A subfolder of a work tree sees the files below it and nothing above; a folder outside the work tree is not in a repository at all. `getGitFileDiff()` compares the same way, and `lib/git-revert.ts` takes the checkout's path from the resolved pair. Pinned in `lib/git-changes.test.mjs` with a repository behind a link of its own, and it is why `e2e/file-row-menu.mjs`'s repository fixture can be a plain `mkdtemp` folder.

### Reverting one file (`Revert changes`)

- `POST /api/git/revert` with `{ cwd, path }` puts one changed file back to HEAD. One command does it — `git checkout HEAD -- :(literal)<path>` — because `checkout <commit> -- <path>` writes the index *and* the working tree, which is what makes a staged change, an unstaged change and a change split between the two all come back with the same action and no `git reset` step. The row's badge goes with it: a success refreshes the explorer the way the refresh button does (`onExplorerRefresh()`, else the sidebar's own `explorerKey`), so the tree, the changed list and an open tab's diff are all refetched. `lib/git-revert.ts` runs the checkout and nothing else: Pi Web writes to Git nowhere else than here and in `lib/worktree.ts`.
- The rule for which row gets the item is `isGitPathRevertible()` in `lib/git-revert-rule.ts`, client-safe because both sides read it — `fileMenuItems()` (`components/SessionSidebar.tsx`) to show the item, `lib/git-revert.ts` to refuse a request. A change is revertible when *both* porcelain codes are in { ` `, `M`, `D` } and at least one of them moved: HEAD already holds that content, so putting it back destroys nothing of the reader's that Git does not also have. Everything else is refused with `not_revertible`, and the reason is the same each time — reverting it would delete something instead of restoring it: an untracked file (`??`), a file staged for the first time (`A`, `AM`), a rename or copy (its new name is what HEAD lacks), a conflict (any `U`: both sides are the reader's work), a type change (`T`), an ignored path (`!`). The item is absent rather than disabled and explained: a row that cannot be reverted says nothing.
- What the item offers and what the server accepts both come from the explorer's own listing: `FileRowTarget.gitStatus` is the `GitFileStatus` from `gitStatusByPath` (the `GET /api/git/status` answer), and the server re-reads that same status rather than trusting the request. A file that stopped being revertible between the badge and the click — edited elsewhere, or staged by a `git add` in a terminal — answers `no_changes` or `not_revertible` and the toast says so (`GIT_REVERT_REFUSAL_KEYS`, the `files.revert*` keys).
- Before the checkout runs, `revertGitPath()` refuses: not a Git repository (`not_git`), a path not inside the repository's working tree (`outside_repository`, checked both lexically and after resolving the links in it, so a link that leads out cannot be written through), no entry for this path in the status listing (`no_changes` — which is also how a directory row and a path inside `.git/` are refused, since Git lists neither), a path that is not a regular file or absent (`not_revertible`: a submodule checkout, a file that became a link since the status read), a repository whose `HEAD` does not resolve (`no_commits`, so an unborn HEAD says that instead of failing with `invalid reference`). The route (`app/api/git/revert/route.ts`) puts the allowed-roots checks first: cwd must be an existing allowed directory, and the file is judged by `isGitWorkingPathAllowed()` (`lib/git-path-access.ts`) — the check the diff route had written for itself, since a deleted file is absent and its nearest existing entry is what the allow-list can judge. A refusal carries its `code` (403 outside the repository, 500 for a git failure, 409 for the rest); `lib/git-revert-request.ts` turns any answer into `{ reverted, code, error }` so the caller never branches on an HTTP status.
- The pathspec is always `:(literal)<path>`. Without it a file whose own name is a glob (`a[1].ts`) matches the sibling it globs to (`a1.ts`) and the revert would rewrite that file too; `lib/git-revert.test.mjs` pins the pair. The literal prefix also makes a leading `:` an ordinary character instead of pathspec magic.
- Nothing is kept of what the revert discards: no stash, no copy, and the file watcher means a later save is the only way back. So the item never acts on the click that asks for it — `askFileRevert` turns the row's menu into `fileRevertBody`, the same question body the project's "Delete all sessions" uses, and the request runs only from its own button. Cancel holds the focus (`data-sidebar-menu-autofocus`, the sheet's Cancel by `focusCancel`), because the answer that changes nothing is the one a stray Enter must never give; `menuWidth` widens to the sentence's measure while it shows. Shift on the item skips the question, the way it answers a session's Delete — a reader who says they know is not asked twice. That is why the item carries the menu's danger styling and why `e2e/file-row-menu.mjs` pins the question, the focus, Cancel writing nothing, Shift acting at once, and the item gone afterwards.
- The row's own menu and the question are the sidebar's one `SidebarMenu`: the state is `{ kind: "file", target, askRevert }`, so the question is the same menu with a different body rather than a dialog above it, and Escape closes either.
- The path Git is given is derived from the status entry (`path.relative(repositoryRoot, entry.filePath)`), converted with `toGitPath()` (`lib/git-changes.ts`, now also exported for this), and compared to the requested path through `resolveExisting()` — the nearest existing ancestor resolved with symlinks — because `/tmp` on macOS is a link and a repository reached through one must still name the file Git names.

## File viewer watches (`components/FileViewer.tsx`)
- Only the active file tab's viewer watches (`?type=watch`, one SSE stream), and only while the right panel is open and the page has not been hidden for `HIDDEN_PAGE_GRACE_MS` (30 s, `usePageHiddenFor()`): such a page lets go of it as of the selected session's idle stream ([sessions.md](sessions.md), #1283). A reconnect's `connected` loads the file again only when its version (`lib/file-version.ts`: size and mtime, from `type=meta`, a text `type=read` and the `change` events) differs from the one on screen, so coming back neither restarts playback, loses a PDF's place, nor drops a text file's Load more chunks, scroll and highlighting. The text viewer reads the git diff again regardless: a commit made meanwhile changes it, not the file. A file never shown yet is read as before.

## Uploads and chat drops
- The explorer's Upload button and a non-image file dropped onto the chat share one client, `uploadFiles()` (`lib/file-upload-client.ts`), and the one endpoint, `POST /api/files/<cwd>?type=upload`; never add a second write path for drops. The explorer asks `upload-check` first and lets the user replace or skip; a chat drop goes straight to `conflict=skip`, so it never replaces a file. It then inserts `@name` for every file the response lists as uploaded *or* skipped (a skipped name is a file already there, often the very file dragged out of the project) and says in a notice that the mention points to the existing file.
- Dropped images still attach to the prompt. Folders are left out with a notice: the endpoint writes flat file names only (`validateUploadFileNames()`), and the browser cannot tell where a dropped file lives on disk, so the copy always lands in the cwd root.
- The composer's attach button (#1101, for phones that cannot drop) is a drop by another route: its file input has no `accept` list (and no `capture`, so phones still offer photos and the camera), and `ChatInput` hands the whole selection to ChatWindow's `onAttachFiles`, which calls the drop handler. Images attach, other files upload and get mentioned, with the same notices; keep one path for both. A `ChatInput` without `onAttachFiles` keeps `accept="image/*"`.
- Files dropped onto the explorer take the Upload button's path (`upload-check`, replace or skip, summary, highlights), aimed at a folder: a folder row takes the drop into that folder (rows stop `dragover` and `drop`, so the deepest one under the pointer wins); anywhere else, file rows included, it lands in the cwd. The hint naming the target is pinned to the bottom of the files box with `pointer-events: none`: above the tree it pushed every row down as a drag came in, moving the target under a still pointer. Folders are left out with the chat's notice.

## Source view languages
- `/api/files ?type=read` names a file's language by its extension (`EXT_TO_LANGUAGE` in the route). `FileViewer` hands it to Prism as is, and a name Prism lacks renders plain with no error, so every value but `text`, `pdf` and `word` must be a language `refractor/all` registers (`app/api/files/language-route.test.mjs`). `html` and `markdown` also turn on Preview and make it the default, so a template that is not a page (`.vue`, `.svelte`, `.astro`) takes `markup`. `.m` stays `text`: Objective-C and MATLAB both use it widely, and either grammar miscolors the other (MATLAB's `%` comments come out as operators); `.mm` is Objective-C++ only. `.conf` stays `text` as well: nginx, Apache and tmux configs are not INI (`.cfg` and `.ini` are). The source view highlights every loaded line, whatever the file's size; see the long-file section below.

## CSV/TSV files open as a table
- `.csv` / `.tsv` (matched by extension, `isDelimitedTablePath()`) open in `FileViewer`'s Preview mode as `components/DelimitedTable.tsx`, the way markdown and HTML open rendered; Source stays one click away and a restored choice wins. No server change: `/api/files ?type=read` still answers `language: "text"` for them.
- `lib/delimited-table.ts` parses RFC 4180 itself (quoted delimiters, `""`, line breaks inside quotes, LF/CRLF, BOM, blank lines skipped) and is lenient where files are not (stray quotes, ragged rows). A `.tsv` always splits on tabs; a `.csv` takes `,` unless its first records split more consistently on `;`, tab or `|` (Excel in many locales writes `;`). The first record is the header.
- The gutter is the file line each record **starts** on (counted by LF, as the source view numbers lines), not the record index, so a quoted field with line breaks does not shift later rows.
- The table also shows a **slice** of a file — a `read` tool call's result, which starts mid-file (see `sessions.md`). `parseDelimitedTable()` and `DelimitedTable` take `firstLine` (the file line the text starts on, so the gutter keeps the file's numbering) and `hasHeader` (default: only text starting at line 1 can carry a header row). A mid-file slice therefore eats no record as a header: every record is a row and the columns are `#1…#N`. A slice cut inside a quoted multi-line field mis-splits for any parser, so the caller warns above the table (the table cannot know where its text came from).
- Large files arrive in 256 KB chunks with "Load more". The table shows a loaded prefix too (`complete: false`): its last record is dropped unless a line break outside quotes ends it, so a record cut mid-field never shows; it appears once the next chunk loads. Markdown and HTML keep their preview off while truncated.
- Rows have one fixed height and only those around the viewport are rendered (`visibleRowRange()`, the SessionTree approach; no virtualization library). The table scrolls inside the viewer's own content box (`scrollRef`), so its scroll position is saved and restored like the source view's; it reads the box in a passive effect because the parent's ref is not attached yet in the child's layout effects. Column widths come from up to 500 sampled rows, clamped to 64–420 px; a cell ellipsizes and its full value is its tooltip. Gutter and header use `--bg-panel`, opaque, so columns scrolling under the sticky strips never show through.
- `FILE_CODE_STYLE` and `FILE_LINE_NUMBER_STYLE` (`components/FileViewer.tsx`) are exported and shared: the source view (now a window of highlighted blocks), the diff view and `components/ReadSnapshotViewer.tsx` all take their type and their gutter from that one pair, so a size change moves all of them together and no view carries its own copy.
- The gutter is `position: sticky; left: 0` against the viewer's own `overflow: auto` scroller (`.file-viewer-content`; the snapshot panel's wrapper). It only has room to travel because every row spans the widest line — `width: max-content` on the `<pre>` or wrapper plus `min-width: 100%` on each `.file-source-line`. Drop either half and a short line's number slides away behind its text again, so that coupling, not the sticky rule, is what a later edit breaks by accident (wrap mode sets `width: 100%` and never scrolls sideways, so nothing travels there).
- The source view keeps the line numbers in their own column beside the code, so the sideways scrollbar is the code column's own and never runs under the numbers: a scroller's native bar spans its whole box, which is why the numbers used to sit under it. `.file-source-columns` is `position: sticky; top: 0` inside the scrollable space with the scroller's visible height, so the code column's native horizontal scrollbar sits at the bottom of the viewport and spans that column only; the outer box never scrolls sideways. Both inner layers (`.file-source-gutter`'s cells and `.file-source-code`'s blocks) ride the scroll with `applySourceScroll()`, a `translateY` written straight to the two nodes in the scroll handler — one write per scroll event, on the compositor, and never through the style prop, which React would reset on the next render. The gutter holds one absolutely positioned cell per rendered line at the line's own offset and height, so a wrapped line's number stays on that line's first row; the scroll range carries `sourceScrollPadding` (12 px, or 48 px beside Load more) so the last line can sit above the code column's scrollbar. `SourceBlock` renders rows with `showLineNumbers={false}`. The Diff view and `components/ReadSnapshotViewer.tsx` keep their inline `position: sticky` gutter and the browser's full-width bar, unchanged.
- The gutter repeats the code line's height in px, so `fontSize` × `lineHeight` in `FILE_CODE_STYLE` and the px `lineHeight` in `FILE_LINE_NUMBER_STYLE` are one fact: 12px on a 1.6 leading means `19.2px` (the font is down from 13px, the gutter from 20.8px). `components/FileViewer.test.mjs` pins the product and the sticky pair.

## Long files: a window of lines and find across all of them

- The source view never renders the whole file. `hooks/useVirtualLines.ts` reports the lines around the scroller's viewport (`visibleLineRange()` in `lib/source-window.ts`, 20 lines of overscan), keeps a map of measured row heights (a wrapped line is taller than one row), and derives line offsets from it. Unknown rows use the average measured height, so the scrollbar is honest before a row has ever rendered. A scroll far past the measured region lands on estimates; once those rows render, the anchor effect shifts the scroll position by the height the space above it gained, so the line you jumped to stays where it was put.
- Highlighting is per block: `highlightBlocks()` hands Prism a block of 200 lines plus 200 preceding context lines (`SOURCE_HIGHLIGHT_BLOCK`, `SOURCE_HIGHLIGHT_CONTEXT`). The context is tokenized but not rendered, so a block that starts inside a multi-line comment or template literal keeps its tokens. The context is a lead-in, not a guarantee: an unterminated construct longer than 200 lines is colored from the block's first line. `SourceBlock` (a `memo` in `components/FileViewer.tsx`) renders only `[start, end)` and numbers rows from `start + 1`; scrolling within a block reuses its token tree. `SOURCE_HIGHLIGHT_MAX_LINES` now caps only `components/ReadSnapshotViewer.tsx`, whose slice is bounded by the read tool.
- Find is the viewer's own, because the browser's find sees only the rendered window. The toolbar's magnifier, or ⌘/Ctrl+F with the pointer, focus or selection inside the viewer, opens `.file-find`; Enter/Shift+Enter step, Esc closes and is captured before the global stop-the-agent shortcut. `lib/source-search.ts` searches every loaded line (literal text, case-insensitive by default, case toggle, a stored-match cap that keeps the total count). A truncated file is completed first: find loads the remaining 256 KB chunks up to `SOURCE_SEARCH_MAX_BYTES` (8 MB) before it answers, then the count reflects all of it. A match jumps with `scrollToLine()`, so it is rendered on arrival even when it was far outside the window; matches are painted through the CSS Custom Highlight API (`::highlight(pi-file-find)`), which leaves Prism's token spans untouched, and a browser without it gets a row tint. Those two rules stay in `app/globals.css`. Tailwind's Lightning CSS pin (`1.32.0`) does not know the pseudo-element and warns on it during `vite build`, so `package.json` overrides `lightningcss` to `1.33.0`, which parses it; keep the rules in the stylesheet and the override in place rather than injecting the CSS at runtime. The Source view only offers find; Diff and Preview draw themselves.
- Diff and Markdown/HTML previews are not windowed, and the diff is capped server-side at `TEXT_PREVIEW_MAX_BYTES` (`lib/git-changes.ts`). The source view's horizontal scroller still comes from the widest rendered block (`width: max-content` on each block's `<pre>` plus the wrapper), and the wrap mode sets `width: 100%` as before.
- `components/FileViewer.test.mjs` pins that a source window maps over blocks and never over `sourceLines`, that `SourceBlock` slices its context off, and that find searches the whole line array rather than the window.

## Which lines wrap

- The wrap choice (`wrapLines` in `lib/file-viewer-state.ts`) belongs to the source view and the diff view; a rendered preview (markdown, HTML, table) has no lines, so `FileViewer` offers the button in those two modes only. The diff box follows the source box's width rule (`100%` wrapped, `max-content` not), which is also the case where the sticky gutter has nothing to travel over (above).
- A file whose reader never pressed the button wraps by its kind: prose (`PROSE_EXTENSIONS` — md, markdown, mdx, mdown, mkd, rst, adoc, txt) opens wrapped and everything else does not. A long prose line is the same sentence going on, so sideways scroll only hides its end; code is read by its columns and indentation, so wrapping it breaks the cue and an editor's habit. `.txt` is on the prose side because it holds prose more often than structure; `.log` is deliberately not — a log line is a column (timestamp, level, message), and wrapping one puts the next line's timestamp where its message was. `wrapsByDefault()` and `resolveInitialWrapLines()` are the only two places knowing that list, and `getLanguage()` (`lib/file-types.ts`) is deliberately not consulted — it maps to a highlighter language, and `txt` and `text` are one value there while a prose default for them is a separate call.
- `FileViewerState.wrapLines` is optional: undefined means never chosen and keeps following the kind, a boolean either way is the reader's own and wins. So `openFileTab()` writes no wrap default at all — a tab opened straight into a diff (a Git-changes click) carries an unmade choice, and its markdown diff wraps. Setting `wrapLines: false` there would look the same on a `.ts` and silently veto the rule on a `.md`.
- A `read` card's slice (`components/ReadSnapshotViewer.tsx`) wraps by the same rule and carries the same key; see `sessions.md` for its Source / Preview switch and where its choices are kept. The table view has no lines, so its panel shows neither control.
- `components/FileViewer.test.mjs` pins both branches of the diff's wrap styles, the button's mode condition, and `lib/file-viewer-state.test.mjs` pins the kind rule (txt in, log out) and that an explicit choice beats it in either direction. The two header controls (`DisplayModeSwitch`, `WrapToggleButton`) and the row renderer (`SourceCodeRenderer`, which takes the slice's `firstLine` so a mid-file read's rows keep the file's own numbers) are exported from `components/FileViewer.tsx` for the snapshot panel to use rather than copy — `components/ReadSnapshotViewer.test.mjs` pins the shared imports.

## Web password throttling
- `lib/auth-throttle.ts` is deliberately global, not per-IP (its header says why). Failures double the delay (1 s → 60 s cap) for everyone; a success or 5 idle minutes resets it. The reset window must stay longer than the max delay, or waiting out one block restarts the burst.
- State lives on `globalThis` under `Symbol.for("pi-web:auth-throttle")`, so it survives hot reload and `proxy.ts` and the route handlers share it under both `vite dev` and `vinext start`. Tests reset it with `recordAuthSuccess()`.
- `POST /api/web-auth` and every `Authorization: Basic` header on `/api/*` share the counter; `proxy.ts` checks Basic before its `/api/web-auth` exemption, so `GET /api/web-auth` is no unthrottled password oracle. A valid session cookie is checked first and never blocked. While blocked, Basic gets `429` even with the right password, and a Basic success never resets the counter (`proxy.ts` explains both).

## Files behind a transparent encryption driver

- Some company machines run a transparent encryption filter driver (corporate DLP) that reports the filesystem inconsistently: `fs.statSync` answers the **ciphertext** length (29,249 for a file whose readable content is 12,865 bytes on one such machine) while reads hand back decrypted bytes and stop at the plaintext end, and the handle-based final-path query `fs.promises.realpath` answers takes `EISDIR: illegal operation on a directory` for a plain file. Which files sit in that state changes over time, so every symptom below looks intermittent and file-specific — which is also why it is never reproduced by a fresh file written here.
- So `stat.size` is not a fact about the data. `readTextPreviewChunk` treats a short read as the end of the file (the request was already capped at `fileSize - offset`) and returns `size` as what the content really reaches, and `streamFile` declares and range-clamps to `getReadableFileSize()` instead: a body shorter than its own `Content-Length` is a download the reader keeps waiting on, and a whole Markdown file called `truncated` is a Preview tab that silently disappears from `FileViewer` (`hasPreview` needs a complete load). `lib/text-preview.test.mjs` pins short-read-is-EOF, that a chunk cut at the 256 KB cap stays `truncated: true` with the file's real size, and that the probe finds the end through a lying size.
- `EISDIR` from `realpath` does not mean directory. `fs.realpathSync` answers the same path correctly — it is a path query the driver does not intercept — while the promise version opens a handle and queries that handle. pi takes the mutation-queue key of every `edit` / `write` through the promise version (`dist/core/tools/file-mutation-queue.js`) and tolerates only ENOENT/ENOTDIR, so the tool dies before it reads a byte.
- `lib/dlp-realpath-compat.ts` answers that EISDIR with the query the driver does answer, rethrows every other error untouched, and does nothing at all where no driver exists. Reaching pi's one import takes two ways in, because a named builtin import is a frozen snapshot (see the table in `tests.md`): `installDlpRealpathCompat()` replaces the property on the shared `fs.promises` object, which every late reader sees, and `registerFsPromisesShadow()` registers an ESM loader hook that answers `node:fs/promises` with a module of our own. The hook runs per import rather than once at module evaluation, so it lands whichever side of the freeze the process is on — which is what makes it the server's way in, since under vinext nothing of ours is evaluated before the framework itself has loaded `node:fs/promises` (measured: `vinext/dist/cli.js` reaches it through `typegen.js`, Vite's CLI through its own chunks). `instrumentation-node.ts` still imports the module first, now so the hook is registered ahead of the pi SDK preimport, which the built server entry evaluates ahead of every route chunk. The shadow re-exports the whole real API (`export *` from the real builtin, which the hook lets through to itself) and replaces only `realpath`, so a newer Node's exports arrive on their own; its fallback is written out a second time because the shadow is a source string the loader thread loads and cannot import the file that builds it, though in the server the object patch is usually in place already and answers first. `lib/dlp-realpath-compat.test.mjs` exercises the hook and the shadow as the loader would — written out and imported — because registering the hook in-process would install it for the whole suite under Bun.
- Bun has no equivalent: `module.register()` accepts the call and runs no hooks, and `Bun.plugin()`'s `onResolve` never fires for a `node:` specifier (both measured). A process Bun is serving therefore gets the object patch only and still fails an edit. `bun run start` is Node even under `bun run` (`node_modules/.bin/vinext` resolves to the `.cmd` wrapper), so the server is covered; `bun run --bun start` really is Bun and needs a preload, which has to be configured outside the app (`bunfig.toml`, or `--import` on the command line). `reportRealpathCoverage()` prints which of the two a process got on the server's first log line, `loaded (transparent encryption driver)` against `reached fs.promises only`; the warning is what a failed edit on such a machine should be read together with, and it names the gap instead of guessing at an import order.
- What it cannot reach is a process that never loads the shim: a bare `node_modules/.bin/next`, the published `pi-web` bin, or the pi CLI on its own. The size fixes above are durable; the per-file way out is rewriting the file through a process the driver does not intercept — `Copy-Item` to a temporary name, delete the original, rename the copy back. A bare `Move-Item` only renames the ciphertext container and changes nothing.
