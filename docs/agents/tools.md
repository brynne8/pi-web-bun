# Tool selection and built-in extensions

## New session tool preset
Tool names are passed at session creation (`POST /api/agent/new` → `toolNames[]`) and persisted in versioned `pi-web:tool-selection` custom entries (ADR 0002). No entry, or a later `cleared: true` one, means no pin: the session follows pi's `defaultTools`, as the `configured` preset ("From Settings", the Built-in tools row of Settings › General) does by sending no `toolNames`. An empty array is Chat only, resolved before services are created: no extensions/skills/prompts/themes, and the ordered contents of Pi's discovered context files replace Pi's base prompt. Crossing the Chat-only boundary or clearing a pin rebuilds the wrapper; changing between nonempty presets updates it in place.

**Chat only has no extension providers** (#804): the model selector's listing loads extensions, the session does not. A model only an extension provides (one `findDeferredModel()` remembers but the Chat-only runtime lacks) is named as such: a start refuses it when the browser chose it, `set_model` refuses it instead of "Model not found", and a prompt in a session that could start on no model at all names the one it wanted rather than pi's "No API key found". With no pick, another model in scope stands in for an extension's default, as for any default out of scope.

**Exact system prompts go through `before_agent_start`.** Chat-only sessions register `lib/exact-system-prompt.ts` as an inline extension factory, and subagents (any profile in replace mode, or one naming `skills:`) the equivalent handler in `lib/subagent-skills.ts`, which appends the named skills or, in replace mode, pi's skill catalog; the handler returns `{ systemPrompt }`, which the SDK sends as the provider's leading system prompt for the run while the transcript keeps Pi's structured sections. Assigning `agent.state.systemPrompt` (a getter replayed from transcript system messages) throws, and patching `prepareNextTurnWithContext` never reaches the model. `get_state.systemPrompt` reports the exact prompt for those wrappers. Subagents persist their tools and the profile's skill / extension switches in `resourceSnapshot`, and extensions never expose the reserved `Agent`, `get_subagent_result`, `steer_subagent`, `abort_subagent` or `list_subagent_runs` to them (ADR 0002; the stop and list tools are [subagents.md](subagents.md#stopping-a-run) and [subagents.md](subagents.md#listing-delegated-runs)).

The last preset the user explicitly selected is kept in browser `localStorage` and initializes fresh-session composers only. Existing sessions never trust it: a pinned one shows its selection (`toolNames` from `GET /api/sessions/[id]`, then its live `get_tools`), an unpinned one `configured`.

**Tool exposure.** pi activates `direct` and `model-only` tools on registration unless their definition sets `defaultActive: false` (`codemode` and `tool_search` do), leaves `codemode` and `deferred` tools undeclared until something activates them, and ignores `hidden` (withdrawn) tools in `setActiveToolsByName()`; `get_tools` leaves hidden tools out.
- Pi Web's environment-sanitizing `bash` (`lib/project-command-env.ts`, ADR 0001), an extension tool standing in for pi's built-in, sets `defaultActive: false` too, so like the built-in it is on only when `defaultTools` (pi's default list included), a preset or `set_tools` names it; registered active, it came back in every session whatever `defaultTools` left out (#1235). A user extension's `bash` still replaces it (`preferUserBashExtension()`) and activates as in the CLI.
- `get_tools` reports an active tool's description from `agent.state.tools`, what the model is sent. Under `codemode.mode: "only"`, while `codemode` is active, the active `direct` tools stay active and callable (`get_tools` reports them so, with `declarationHidden: true` from the AgentSession's private `_hiddenDeclarations`), but codemode's `hiddenDeclarations` leave their declarations out of every request, so the model reaches them only from scripts. The toolbar's Tools panel lists only what requests declare; presets still read `active`. A preset still bounds them: a `direct` tool is callable only while active. `prepareLoadout` hooks rewrite it there on every loadout change (tool registration included): codemode's definition holds only the intro, while the declared one lists the tools scripts can call, MCP namespaces and types, and appends the codemode declaration to the callable `direct` tools.
- A preset replaces only the coding tools. `resolveActiveToolNames()` carries every other tool that is active, registered and not hidden, so what an extension, `tool_search` or a `defaultTools` entry such as `+codemode` activated survives startup, `set_tools` and `reload`, a tool an extension switched off stays off, and a preset never turns `codemode` on. It adds nothing else: pi activates extension tools itself, so re-adding them would override an extension (or a branch's recorded loadout) that keeps a `direct` tool off. `reload` carries the set pi rebuilt after extensions restarted, not the previous one.
- `navigateTree()` restores the target branch's loadout from its transcript (bringing back `write` under a Read-only pin, dropping `codemode`), so a normal session then reapplies its pin (the restored set when unpinned) and carries over from the branch it left the session's own tools: `codemode`, `tool_search` and pi-web's subagent tools. Other extension tools follow the target branch's loadout, as in the pi CLI; since pi 1.4 (#11062) one that branch never added or removed, such as one registered after that branch point, is active unless it is registered with `defaultActive: false`. When pi restores the same set that was active (editing a history message, or going back to a point after the last tool change), the session keeps the order pi restored: pi replays the branch's recorded loadout, so that order is that point's prompt (#1405). Reapplying keeps the carried positions of the survivors and appends newly selected coding tools at the end, so the prompt's `<tools>` section stays byte-identical with the `pi` CLI's for the same set; regrouping the coding tools ahead instead rewrote it and dropped the prompt cache on every harness switch. Chat-only and subagent wrappers keep what pi restored.
- A reopened normal session starts on the loadout its transcript last recorded (pi 1.3, as `pi --resume` without `--tools`: pi-web passes no `tools`), not on today's `defaultTools`, so `+codemode` or another `defaultTools` edit made since reaches only new sessions and transcripts that record no loadout. An unpinned session keeps the recorded tools; a pinned one gets its pin over the coding tools and carries the rest from that loadout. Chat only (`tools: []`) and subagents (`subagentToolOptions()`: an allowlist, or `noTools: "builtin"`) select their tools explicitly, so pi restores nothing for them.

**Built-in extensions** (`lib/builtin-extensions.ts`, ADR 0006). The CLI's built-in `codemode`, `tool-search` and `mcp` are rebuilt from the factories the SDK root exports, under the CLI's names with `replaceable: true, builtin: true`, so `-builtin:<name>`, project overrides, replacement by a third-party extension and `noExtensions` behave as in the CLI. Normal sessions load all three. Subagents load `codemode` through their profile's `codemode` policy, and `tool-search` and `mcp` with an MCP host of their own only under `mcp: on` (see [subagents.md](subagents.md)); they never share the normal session's.
- The MCP extension's `loadConfig` returns no servers (only `autoEnableCodemode`), so it connects nothing, and with `startupWaitMs: 0`, so its first-prompt wait for `direct` servers (which ignores Stop, and since pi 1.0 also sees servers registered right before the prompt) holds nothing; pi-web registers servers itself (**MCP host** in [mcp-runtime.md](mcp-runtime.md)). Servers connect through `createPiWebMcpTransportFactory()`; `openUrl` opens no browser on the server host.
- MCP is off (the `mcp` entry registers nothing) when `PI_WEB_DISABLE_MCP` is anything but empty, `0` or `false`, or `lib/pi-sdk-internals.ts` cannot load; never fall back to the SDK's own transport.
- `codemode` is offered only after a self-test ran a script through the SDK's sandbox (`checkCodemodeSandbox()`, on the first normal session). A pass is kept for the process; a failure only for a minute, then the next session or subagent starting runs it again (Settings keeps showing the failure meanwhile). Its 10 s deadline counts only time the event loop was free, a late tick as at most two (30 s of wall time at most), because a synchronous stall of the busy first session start fired a plain timer before the poll phase delivered the worker's answer, and the cached failure then turned Code mode off until a restart (#1615). A built-in that cannot run keeps its `builtin:<name>` entry with an empty factory, so a setting naming it means the same.
- pi lets at most two codemode workers live per process, across all sessions (`DEFAULT_MAX_CODEMODE_WORKERS` in the SDK's `dist/extensions/codemode/execute.js`); `PI_CODEMODE_MAX_WORKERS` changes it, read on every script. Since pi 1.4 a script at capacity waits for a free worker in arrival order, up to 60 s or its `timeout_ms`, then fails without running (pi 1.3 failed it at once with "Codemode worker limit reached"). A script holds its worker while it waits on its tool calls. The CLI runs one session per process; pi-web runs every session and subagent in one, so two parent scripts waiting on subagents took both workers and every script those subagents ran timed out. `applyCodemodeWorkerDefault()` (`lib/codemode-workers.ts`, from `instrumentation-node.ts` at server start) therefore sets the variable to 8 when it is unset or empty; any other value the user set is kept, even one pi rejects (it then uses 2). Each worker's QuickJS heap is capped at 256 MB. Eight parent scripts waiting on subagents at once still fill it; only pi releasing a worker while its script waits would end that. `lib/codemode-workers.test.mjs` fails if the SDK stops reading the variable per script.

**Read-only MCP policy** (`lib/mcp-read-only-policy.ts`, normal sessions; subagents with `mcp: on` have their own, `createSubagentMcpPolicyExtension()`, which reads the profile's tools instead of a pin). While the pinned selection is read-only (it names tools, none of `bash`, `powershell`, `edit`, `write`; no pin is not read-only), its `tool_call` handler blocks every MCP tool (the MCP extension's, or any named `mcp__`) whose definition lacks `annotations.readOnlyHint: true`, codemode scripts' calls included. It reads the pin from the session entries, which `set_tools` writes before applying it and cannot change mid-run. The hint is the server's word: this guards against model mistakes, not a malicious server.

**A call that names a field the schema does not have is blocked** (`lib/tool-args-strict.ts`, loaded by every normal session and every subagent). pi validates a call's arguments against the tool's TypeBox schema in `validateToolArguments()` (pi-ai), which checks the fields a schema names and passes the rest through untouched, so a call written against a schema the tool no longer has — `Agent` dropped `thinking`, `max_turns`, `inherit_context` and `input_files` ([subagents.md](subagents.md#what-the-model-may-choose-when-spawning-a-subagent)) — used to run with the extra field doing nothing and the model never learning it invented one. The extension's `tool_call` handler reads the tool's schema from `pi.getAllTools()` and blocks the call when the arguments name a field the schema does not declare; the block reason names the unknown fields and points at `GET /api/tool_schema/<tool>`, which serves that tool's definition — the same `getAllTools()` data the tools menu reads — so the model reads the schema instead of guessing from a field list. The URL's port comes from the launcher's own flag (`vinext start -p`, `vite dev --port`), because the port is an argument and not `process.env.PORT`; the definitions are collected from every running session into one table by lowercase name, and a name matches without case. A hidden declaration is only served when no callable one exists. `proxy.ts` lets `/api/tool_schema/` through without the web password (the trusted-host check still runs): the prompt's reader has none, because `lib/project-command-env.ts` strips `PI_WEB_PASSWORD` from the bash environment, and a tool's definition is no secret. Only field names are checked: a declared field's value is left to pi's validator, whatever it is. A schema is checked only when it names at least one field — an object with `properties` (an MCP server's bare `inputSchema` included), `allOf` branches merged into one set — and not when it leaves them open (`additionalProperties: true` or a subschema, `patternProperties`), composes them (`anyOf`, `oneOf`, `$ref`), or names none at all, because pi gives an MCP server's free-form input schema an empty `properties` too and such a tool may well take anything. The hook runs after pi's validation and after a tool's `prepareArguments`, so `event.input` is what the tool is about to receive: the legacy single-edit `edit` call, which `prepareEditArguments()` folds into `edits`, reaches it without `oldText` and `newText`. Codemode scripts' calls pass through the same handler. `lib/tool-args-strict.test.mjs` pins which schemas are checked, what the block reason says, and the URL and port it carries; `lib/tool-args-strict.integration.test.mjs` proves a real session blocks the call, lets an open schema's extra field run, and lets a call naming only declared fields run.

**A `cd` to the working directory comes off the command before it runs** (`lib/bash-command-cd.ts` and `lib/bash-command-normalize.ts`, loaded by every normal session). The bash tool's description states where commands run as a fact — `The working directory is \`<path>\`.` — and never as `Execute a bash command in <path>`, because that pairing of a verb of execution with the path is the shape a model turns into `cd <path> && …`, and the `Never prepend \`cd <cwd>\`` line below it loses to it. A call that carries the prefix anyway has it taken off at `message_end`: pi emits extension events before it persists the message (`_handleAgentEvent`, and `_replaceMessageInPlace` for the returned replacement), and the agent loop reads the message's tool calls after that event drains, so one returned message cleans the session file, the arguments the tool executes, the history the model reads next turn — which is where the prefix was being copied from — and the card the user reads. Only `bash` and `powershell` calls are read, and only a `cd` naming the session's own directory comes off: a `cd` into a subdirectory is the call's own work, a `cd` that is the whole command stays because stripping it would leave nothing to run, and repeats come off with it (`cd <cwd> && cd <cwd> && make` is `make`). Only the literal path is recognized — `.`, `$PWD`, `~` and a symlinked spelling of the same directory are not; on Windows the model's case and separator are as good as the session's own. The rule stands on its own extension rather than beside the bash tool it cleans, because `preferUserBashExtension()` drops Pi Web's tool when a user extension brings its own `bash`, and this is about what the model wrote rather than about which tool runs it. Subagents and Chat-only sessions do not load it: neither registers this tool, and Chat-only registers no extensions of its own. `lib/bash-command-cd.test.mjs` pins which shapes come off and which stay; `lib/bash-command-normalize.test.mjs` pins the replacement, the tools it leaves alone, and that the extension survives a user-owned `bash`.

**A request with no tools declares none** (`lib/omit-empty-tools.ts`, loaded by every normal session, every subagent and every subagent wrapper). pi-ai's chat-completions client adds `tools: []` to a request that declares no tool but whose history already holds tool calls — a workaround it states in its own source for one proxy that wants the field present there — and a stricter relay refuses the body outright: `400 … tools must not be an empty array`. The Chat Completions reference marks `tools` optional and words `tool_choice` around whether tools are present at all, so an absent field is the portable statement and an empty array means nothing. Two pi-web paths build that request: a subagent's tool-less wrap-up turn ([subagents.md](subagents.md#built-in-subagents)) and a chat left on the **No tools** preset after it had used tools. The extension's `before_provider_request` handler drops the field when the array is empty and changes nothing else; pi never sets `tool_choice` on this api, so there is no companion field to drop. No other api pi-ai builds assembles an empty list — its Anthropic client guards `tools.length > 0` on its own — so this only ever answers that workaround. `lib/omit-empty-tools.test.mjs` pins that pi-ai still builds the empty array and that the SDK still passes the hook's return value to the HTTP call; `lib/omit-empty-tools.integration.test.mjs` proves a real session dispatches the event name. Once pi stops sending it, delete the extension, its three registrations and both files.

**`defaultTools` switches.** Code mode is on when nothing is configured; Automatic is `-codemode` in the global `defaultTools`, and Always on is `+codemode` (ADR 0006, and Settings › Tools below for why the default is supplied at session start rather than written). `/api/tools/settings` is the only writer of that key, for this and the PowerShell switch, of the global `codemode.mode` and `codemode.inlineBudget` (Settings › Tools), and of `bgTasksEnabled` — the background-bash opt-in (Settings › General), which is read elsewhere at session setup, so it only affects sessions started afterwards ([background-bash.md](background-bash.md)). All of it goes through `lib/global-settings-file.ts` (the lock pi's `SettingsManager` takes on that file). `lib/codemode-settings.ts` edits only entries naming `codemode` and appends `+codemode`, valid on plain and modifier-only lists; a modifier-only list left empty is removed, since `defaultTools: []` means no tools at all. `defaultTools` may hold `+name` / `-name` modifiers: read it resolved through `SettingsManager.getDefaultTools()`; `lib/powershell-settings.ts` resolves the raw global list by the same rule before editing, since appending a plain name to a modifier-only list drops pi's default tools. A global settings.json that does not parse is never read as an empty configuration and never overwritten: the read and the write both fail, and the failure names the file, because the parser's text alone does not say which file is broken. Upstream's message names the file since [#1349](https://github.com/agegr/pi-web/pull/1349), so this is parity rather than a difference to advertise, and it belongs in this note only. The file is pi's own, and pi reads it too: it stays where it is, so pi keeps reporting the same failure and the user can repair it by hand — moving it aside would leave pi with a valid file that holds one key and none of the user's other settings, and pi would report no error at all.

## Settings › Tools

Code mode's settings (`components/ToolsConfig.tsx`) are their own page, after Models, not part of Settings › MCP: the choice, `codemode.mode`, `codemode.inlineBudget`, the sandbox self-test's result and `-builtin:codemode`, plus the names of the tools the open session offers. PowerShell and background bash stay in Settings › General; MCP server rows keep their own exposure notices ([mcp-settings.md](mcp-settings.md)).

**On by default, supplied where pi reads it.** With no settings layer setting `defaultTools`, a session starts with `codemode` active — the application's default, not a value every install must write. `withCodemodeDefault()` (`lib/codemode-settings.ts`) wraps the session's `SettingsManager.getDefaultTools()` in `lib/rpc-manager.ts` and returns `DEFAULT_SESSION_TOOLS` (pi's default list plus `codemode`, `lib/powershell-settings.ts`) where pi's own answer is `undefined`; a list any layer sets — plain names, `+codemode` or `-codemode` — keeps the last word, exactly as pi resolves it. Subagents that build their own settings are not patched: their profile decides. `codemodePreferenceOf()` reads the same rule for the page: no list, or one that resolves `codemode`, is Always on; a list without it is Automatic.

**The route.** `GET /api/tools/settings?cwd=` answers `{ isWindows, powerShellEnabled, builtinTools, codemode, bgTasksEnabled }`, where `codemode` is a `CodemodeInfo` read by `readCodemodeInfo()` (`lib/codemode-info.ts`, shared with `/api/mcp`'s read-only copy): preference, `mode`, `inlineBudget`, the sandbox's settled self-test, `-builtin:codemode`, and — for a trusted project's `.pi/settings.json` — `projectOverride`. The cwd goes through `validateMcpProject()` (absolute, inside the allowed roots, a directory) and its trust decision through `projectTrustReloadOptions()`, so only a project whose sessions read its settings is reported. A refused folder is that refusal, not a silent global answer. `PUT` takes exactly one change (`{ codemode }`, `{ codemodeMode }`, `{ codemodeInlineBudget }`, `{ bgTasksEnabled }`, or the PowerShell switch) and answers the whole read-back, `?cwd=` included, so what the page shows next is what the route read after writing and no merge helper exists; a save is global whatever the page's project, since a project's own `defaultTools` is the project's to change. Both requests carry the panel's 15 s deadline, and the page re-reads after every save because a timed-out save may still have landed.

**Writing the `codemode` object.** `codemode.mode` is `on` (pi's default) or `only`: `only` is written as itself, `on` removes the key, `codemode.inlineBudget` is kept, and a `codemode` that is not an object is refused with the file untouched. pi reads anything but `"only"` as `on`, so a value that is neither is reported (`invalid`) and choosing either option replaces it. `codemode.inlineBudget` is the estimated tokens (characters / 4) the codemode description spends declaring tools: a whole number from 0 to 1 000 000, or `null` to remove the key and a `codemode` object it leaves empty. `CODEMODE_INLINE_BUDGET_DEFAULT` (3000) copies the SDK's unexported default, pinned by a contract test; a value pi ignores is reported `invalid`, never rewritten. Settings that already hold the value are left alone. A trusted project's own `codemode` key replaces the global one — reported with that file's path — when the SDK's merge under two different global values agrees (`projectCodemodeValue()`), so the page never reimplements pi's merge. The mode and the budget come from one read (`readCodemodeSettings()`), so a file that does not parse sets both `modeError` and `inlineBudgetError`; the preference reads with its own `preferenceError`. Sessions read all of it when they start.

**The page.** `ToolsConfig` takes `cwd` and the open session's `tools` (`ToolEntry[]`, from the page's `systemTools`, asked for once per session through `onRequestTools`), renders each tool's name as a chip — `declarationHidden` marked script only, inactive dashed, the description in `title` only — and says so when there is no session or its tools are not loaded yet. Nothing here starts a session: the list is a read of what the open one offers. Each save holds every control in the page until its answer is in and shows its progress and failure in the row it came from; the budget field stays read-only rather than disabled so it keeps focus, and Save gives focus back. Always on is disabled, with the reason under the switch, while the sandbox self-test failed or the **global** extensions set `-builtin:codemode` (`globalBuiltinSettingsPath`): Always on writes the global `defaultTools`, so whether it is offered must not depend on the folder Settings was opened from — a project-only `-builtin:codemode` keeps it available and is reported as that project's own line. A project override is stated whether or not it agrees with the global choice. Strings are `settings.codemode.*` and `settings.tools.*`, refusals reuse `mcp.reason.*`, and the layout is `.settings-codemode-*` / `.settings-tool-*` in `app/settings.css`.

- **Built-in tools** (Settings › General, #1611): the switches choose the built-ins (`SETTINGS_BUILTIN_TOOLS`) the global `defaultTools` resolves to, which is what the `configured` preset gives new sessions; a per-session choice stays the presets' (or the API's `toolNames`). `withBuiltinTools()` (`lib/powershell-settings.ts`) drops only entries naming a built-in and keeps every other entry and modifier. Without another plain name it writes the built-ins as `-name` / `+name` against pi's defaults, so pi's defaults alone remove the key and all off is `-read -bash -edit -write`; beside a plain name (an extension tool) it writes them plain, or they would drop out. On Windows `bash` is the active shell: `powershell` while the PowerShell switch is on. Turning the shell off there also turns that switch off, since `defaultTools` cannot hold a preference for a tool it leaves out.
