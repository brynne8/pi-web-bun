# oh-my-pi (omp) 调研与 pi-web 功能对比报告

> **调研对象**：`~/develop/oh-my-pi`（下称 **omp**）——Stencil Labs 对 pi 编码代理的深度 fork。它在原 pi 的基础上加了一个约 8 万行 Rust 写的原生内核、31 个内置工具、IDE 级别的代码智能（LSP）、真正的调试器驱动（DAP）、60 多家模型提供商，以及会话共享、跨会话记忆、用量统计等整套功能。
> **对比基准**：`~/develop/pi-web`（下称 **pi-web**）——基于 pi 官方 SDK 构建的 Next.js 网页客户端：在浏览器里驱动 pi 编码代理，带会话侧栏、文件浏览、终端、MCP/技能/插件/模型设置等完整界面。
> **方法**：三组并行调研。第一组正向盘点 omp 有而 pi-web 没有的能力；第二组反向——以 pi-web 已有的每个功能为起点，深入 omp 的同类实现做逐文件对比，回答「同一件事，omp 是不是做得更好、好在哪」；第三组换到交互时间轴做跨域扫查（参数流式期、回合进行中、回合完成后、输入装配），因为前两轮按功能域切分恰好漏掉了这类横切体验。本报告合并三组结论，不区分来源。
> **给读者的阅读指引**：每个条目都先说清「这是什么、为什么值得管」，再给出两边的具体做法和文件位置（`路径:行号` 只是证据，不需要先读过代码）。条目编号（如 S1、R3）在全报告唯一，§0 速览表与正文小节同名同号。

## 0. 结论速览

**一段话总结**：omp 把主要的力气花在了 pi-web 本来就够不着的底层——Rust 工具内核、编辑格式、模型提供商栈，这些抄不了也不必抄。但在两边都有的功能上，pi-web 存在一批**成本极低的正确性缺口**（终端杀进程会留下孤儿进程、自动生成标题会覆盖用户手起的名字、会话删除时改文件不是原子的）；omp 还验证了几个**已被用户验证的产品形态**（子代理总览面板、只读分享链接——但后者站在 omp 官方中继之上，pi-web 自托管无服务端承接点，见 N1 的前提说明、用量仪表盘），存在一处**结构性安全差距**（密钥今天会原样进入模型请求和会话存档）；而按时间轴扫查后收获最大的一类是**进行中的那一刻**的体验：模型正在写文件时，内容其实已经逐字到达浏览器，pi-web 却显示「正在生成参数...」，omp 在同一时刻已经在增量高亮渲染文件正文（R7/R9）——回合完成后的重试入口缺失（E1）、@mention 不注入内容（I1）同属此类。正文按性质分两大部分：**第一部分 bugfix**——已有功能里错的、会丢的、会碎的、会虚报的（10 项，多数是小工程量；截至本次更新 8 项已落地、1 项部分落地、1 项未开工，进度表在第一部分开头）；**第二部分 feature**——今天不存在的能力形态（59 项）。两部分的清单表各放在自己部分的开头。混合性条目已按性质拆分：自动标题拆为 S2（纠错）/S11（自动生成）、后台任务拆为 B4（投递可靠）/B5（枚举取消）、设置文件拆为 M4（损坏留档）/M7（热重载）；回合用量纠错归 T2、其展示增补归 T1/R5，Esc 中断纠错归 T4、取消重试增补归 R3。

## 1. 会话层

<a id="s2"></a>

### S2 · 自动标题覆盖用户手起的名字 — P0，小，无依赖

**这是什么**：用户亲手给会话起了名字之后，任何自动生成标题的流程都会无条件把它盖掉——人写的名字被程序毁掉，这是错的。omp 给每个标题记来源，`titleSource === "user"` 的标题在任何自动流程里被跳过。

**pi-web 现状**：自动标题挂在手动端点上（`POST /api/sessions/[id]/auto-name`），生成后无条件写入，不区分现有名字是人写的还是机器写的。

**omp 做法**：标题记录来源，人写的在任何自动流程跳过（`agent-session.ts:9329`）。

**借鉴方案**：写入前检查会话文件里是否已有用户手写的 `session_info` 命名条目，有则拒绝覆盖并在界面上说明；本能力的另一半——「不用点、首轮后自动生成标题」——是 feature，见 §S11。**工程量小。**

**现状更新**：已落地（`afb7db5`）。判定抽成 `lib/session-name-source.ts`（认 `pi-web:session-name` 命名条目），自动命名与扩展改名都走这套判断；行为记在 `docs/agents/sessions.md`。§S11 的自动触发仍未开工。

<a id="s3"></a>

### S3 · Fork 切点的工具批次闭合 — P0，小，无依赖

**这是什么**：pi-web 侧栏的「Fork」把一个会话的当前分支复制成新会话。复制的终点就是当前最后一条消息——但如果最后一步恰好是「模型发起了工具调用、结果还没落盘」这种中间状态，新会话的结尾就挂着一个永远没有回音的工具调用，模型下次读到它会困惑。omp 在切分时会把这个工具调用连同它已有的结果一起包进来，绝不留下半截批次。

**pi-web 现状**：Fork 按当前分支末端直接复制（`lib/session-fork.ts:74-104`），可能终结在未应答的工具调用上。目前依赖下游模型层在拼上下文时补一句 "No result provided" 兜底（这个已知问题在 `docs/agents/sessions.md` 有记录）。

**omp 做法**：按条目切分时，切点自动延伸，把同一批次里已经记录在案的工具体果一并纳入；实在配不上对结果的调用，会被显式标记成「结果未知」而不是悬空（`docs/session-operations-export-share-fork-resume.md` "Fork at an entry"；`session-manager.ts:3860`）。

**借鉴方案**：Fork 前检查分支末尾有没有悬空工具调用，若源文件里对应结果其实已经存在（分支切点选得不巧时会这样），就把它一并纳入复制范围。**工程量小，纯本地文件操作。**

**现状更新**：已落地（`797f4a8`）。同一提交还做了 S7 的原子写，两处改写都换成仓库现成的原子写工具。

<a id="s7"></a>

### S7 · 会话重写的原子写（reparent） — P0，极小，无依赖

**这是什么**：删除一个会话时，它衍生的子会话要「改嫁」到最近的存活祖先——需要重写子会话的文件。今天这个重写用的是最普通的整文件写入：如果恰好在写的一半时进程被杀或断电，会留下一个截断的、坏掉的会话文件。原子写（先写临时文件再瞬间改名）是这类问题的标准解法，而且 pi-web 的代码库里现成就有原子写工具，只是这一处没用上。

**pi-web 现状**：读取路径的容错很好（跳过坏行、容忍截断的最后一行），但 `lib/session-delete.ts`（约 :205）的改嫁重写用裸 `writeFileSync`。

**omp 做法**：会话文件的一切重写都走「加围栏的原子重写环」：重写期间持续复查有没有并发追加落在改名的时间窗里、有就重做；系统不允许改名时退回 `.bak` 方案；列表扫描时能自愈发现坏文件（`session-manager.ts:871-975,1364-1435`）。

**借鉴方案**：omp 的整套围栏环在 SDK 内部、不适用，但 pi-web 只需要把自己手里那几处整文件重写（改嫁、Fork 手写文件）换成仓库现成的原子写工具，一次改动。**工程量极小，是全部条目里性价比最高的一处。**

**现状更新**：已落地（`797f4a8`）。pi-web 自己手里的会话重写（改嫁、Fork 写新文件）全部改走原子写；SDK 内部的围栏环仍未覆盖，见 §17。

## 2. 终端与工作区的资源治理

<a id="g1"></a>

### G1 · 终端进程树终止、尺寸钳制、输出背压 — P0，小-中，无依赖

**这是什么**：pi-web 网页里嵌着真终端。三个隐患：① 关闭终端标签时只杀了 shell 本身，shell 里跑的 vite、node 等子进程变成孤儿继续占着端口——用户经常遇到「标签关了端口还占着」；② 窗口尺寸没有任何校验，异常的巨大值可以直接撑爆分配给 PTY 的缓冲；③ 终端里跑 `yes` 这类狂吐输出的命令时，所有输出不经合并直接灌进网络推送。omp 的原生终端子系统对这三件事都有明确防御。

**pi-web 现状**：基于 Bun 原生 PTY 的实现整体扎实（流式 UTF-8 解码、退出码重放完备，`lib/terminal-bun-pty.ts:87-155`），但 kill 只对直接子进程（`:151`）、无尺寸钳制、无输出合并/背压。

**omp 做法**：终止走「先发终止信号、等一会、再发强杀信号」的进程组波（子进程优先）；尺寸钳制在合理上下限；输出走有界队列（上限 64 块）合并转发，下游卡住就丢帧不积压；回调三十秒不消费自动断开（`crates/pi-natives/src/pty.rs`、`docs/natives-shell-pty-process.md`）。

**借鉴方案**：① kill 改为对整个进程组依次发 TERM→HUP→KILL（Bun 下 spawn 成独立进程组再组杀）；② resize 钳制上下限；③ 输出块合并 + 简单背压。Rust 实现搬不了，语义全部可在 TypeScript 近似。**工程量小-中。**

**现状更新**：已落地（`fe8d363`）。三件事都做了：Bun 的 PTY 把 shell 作为会话首进程 spawn，负 pid 即真实进程组，kill 按组发信号并容忍表示组已消失的 ESRCH；`spawnBunPty` 把 cols/rows 钳到 2..1000 并拒绝非有限值（管理器与路由早就钳过，这是最后一条没钳的路径）；`TerminalOutputQueue` 按 64 KiB 或 16ms 静默期放行、缓冲不超过一个读取块的余量，不丢字节，退出前先冲刷缓冲。已知遗留：一个自己另立进程组、且对 SIGHUP 与 SIGTERM 都不理的任务仍能活过 shell——没有可移植的 JS 进程树遍历就够不着。

<a id="g2"></a>

### G2 · git status 短 TTL 缓存与并发去重 — P1，小，无依赖

**这是什么**：网页侧栏会显示当前项目改了哪些文件。现在每次刷新/每次组件重新渲染都会现场跑一次完整 git 状态扫描（包括把所有未跟踪文件挨个数行数），仓库大的时候这个查询要秒级，多个标签页同时开同一项目还会重复跑。pi-web 自己在别处（worktree 元数据）已经实践过「短期缓存 + 并发请求合并 + 后台刷新」模式，git 状态是同样的场景却没套上。

**pi-web 现状**：`app/api/git/status/route.ts:31` 每次全量扫描，未跟踪文件逐文件同步数行；无缓存无节流。

**借鉴方案**：套用自家 `lib/worktree.ts:122-165` 的 stale-while-revalidate（先给旧结果、后台刷新）+ 并发去重，秒级 TTL 就能消掉绝大部分重复扫描。**工程量小，omp 无对应项（这是纯 web 场景问题），纯 pi-web 自我修复。**

**现状更新**：已落地（`db8af8a`）。缓存抽成 `lib/git-status-cache.ts`：并发请求共享一次扫描，条目过期即丢弃后重扫（编辑器保存后的重载必须看到新文件），revert 与上传主动失效。

## 3. 投递、聚合与中断的运行链路

<a id="b4"></a>

### B4 · 后台任务完成报告：一次重试后静默丢失 — P1，小-中，无依赖

**这是什么**：pi-web 允许把长跑命令转后台，跑完把结果报告给主代理。这条「交差」链路在接收方正忙时只重试一次，再失败报告就**静默丢失**——用户以为主代理拿到了后台结果，其实没有，且无处追查。omp 那边按指数退避（500ms→30s 抖动）重试直到有回执，屡攻不下的进死信区留档，报告不会消失得无痕。

**pi-web 现状**：交接班语义（120 秒手交、溢出缓冲、报告聚批，`lib/bash-bg-tasks.ts`、`lib/settled-report-note.ts`）比 omp 还精细（防内存与落盘分叉），**保留**；但投递只有一次「对方在处理中」重试（`settled-report-note.ts:148-158`）。

**omp 做法**：投递失败 500ms→30s 抖动重试 + 死信留档、收到回执才缩短保留（`src/async/job-manager.ts:6-19`）。

**借鉴方案**：投递加指数退避重试，重试用尽写死信日志（落盘可查并在界面可见）；另一半——「模型能列出/取消运行中的后台任务」——是 feature，见 §B5。**工程量小-中。**

**现状更新**：已落地（`8f64502`）。投放在 pi 说 already processing 时按 omp 的节奏重试（500ms 翻倍到 30s 上限，抖动 200ms），一次首发 + 七次重试；仍投不进、或因其他原因失败的批次写进 `<tmpdir>/pi-web-dead-letters/<notificationId>.json`（会话 id、报告、尝试次数、错误），不再无声消失。失败时丢弃该条与它的消费监听器，下一批另起一条消息，而不是往一条永远发不出去的尾巴上追加。120 秒交接、溢出缓冲、聚批与落盘后冻结的语义原样未动。§B5 仍未开工。

<a id="t2"></a>

### T2 · 回合页脚的 usage 只算最后一条响应（应为回合累计，虚报） — P1，极小，无依赖

**这是什么**：回合页脚职责是回答「这一轮花了多少」，但 pi-web 显示的是**最后一条响应**的 usage——一个回合跑了多次模型请求（工具循环是常态）时，这个数字低于回合真实花费，属于虚报。omp 的回合累计行还把 input 口径刻意不含 cache-read（免得虚大头），口径决定一并照抄。

**借鉴方案**：聚合回合内所有带 usage 的消息累加显示；回合耗时与可点开的用量明细属展示增补，分别归 §T1（工作行走时计时）与 §R5（各请求用量展开）。**工程量极小。**

**现状更新**：已落地（`af2894f`）。`lib/turn-usage.ts` 累加回合自己的各次请求，四个 token 桶在页脚里仍分开打印（`input` 不含 cache read），没计费的回合照样不出这一行。回合耗时与各次请求明细仍归 §T1 与 §R5。

<a id="t4"></a>

### T4 · Esc abort 吞排队消息与草稿、abort 不停内部转向 — P1，小-中，无依赖

**这是什么**：停止键上的三个失控行为：①**中断时排队的消息被吞**——按了停止，刚才排队的那几句话还留在服务端、下一回合会自动投递，用户想收回得自己发现并点队列条上的 Recall；②**abort 不停内部转向消息**，中断后可能又自动续跑；③有草稿时 Esc 的吞草稿语义不明（pi-web 今天只是偶然不吞）。omp 的 abort 责任链先把队列吐回输入框、丢弃内部转向、绝不碰草稿。

**pi-web 现状**：单层 abort（`ChatInput.tsx:1491-1494` → `useAgentSession.ts:1879-1896`）；队列召回与 abort 两个函数都已存在（`:2337-2352`），只差拼起来。

**借鉴方案**：中断流式时自动先执行现有 recall 逻辑把排队消息收编回输入框；验证服务端 abort 是否支持放弃队列，不支持则前端补发清队列命令；给 Esc 加「有草稿绝不吞」的显式护栏。**工程量小-中。**「Esc 取消重试等待」属控制增补，已并入 §R3。

**现状更新**：第一项已完成并超出预期（`15157b0`、`82c0183`）。abort 先清空 pi 的队列再等任何事——事后清已经太晚，steer 消息那时早已被投递出去，回复会变成一条无人应答的用户消息；队列里取回的文本按原投递模式重发（steer 领跑、follow-up 排队在它后面，顺序仍由 pi 排），没发出去的退回输入框。另外「Stop 后没有回音」的那一回合，会把提示词与那条空回复用 `navigateTreeKeepingToolSelection` 挪到侧枝，词和图片交回输入框、按草稿键恢复；提示词刚按下去就 Stop 的空窗期由 `pendingStopRef` 兜住。仍是缺口：内部转向消息（扩展自己续跑）不随 abort 停，Esc 的「有草稿绝不吞」也只是当前的偶然行为、没有显式护栏。

## 4. 配置与草稿的持久性

<a id="m4"></a>

### M4 · settings.json 损坏时不留档 — P2，极小，无依赖

**这是什么**：pi 的全局配置文件被手改坏（语法错误）时，pi-web 今天直接按空配置运行，没有任何自动留档——用户写下的设置静默丢失而不自知。omp 对解析失败的文件先改名 `.broken-*` 留档再报错。

**借鉴方案**：解析失败时改名带时间戳留档并在界面报告；另一半——「配置改了即时生效（热重载）」——是 feature，见 §M7。**工程量极小。**

**现状更新**：已落地（`fe5a5d9`）。解析失败时把 settings.json 改名成带时间戳的留档再报错，不再按空配置静默继续。§M7 热重载仍未开工。

<a id="i2"></a>

### I2 · 草稿持久化（刷新即丢） — P1，小，无依赖

**这是什么**：写到一半的长提示词存在内存 Map 里（`lib/draft-store.ts:17`），手滑刷新/崩溃标签即全丢。omp 连进程被杀都有兜底：退出钩子把编辑器内容持久化成会话 sidecar，resume 时恢复（`session-teardown.ts`）。web 的等价问题就是 F5。

**借鉴方案**：draft-store 加 localStorage 层（文本必存；图片设体积闸门或走 IndexedDB），按 draftKey 恢复读回。**半天。**

**现状更新**：未开工。`lib/draft-store.ts` 仍是纯内存 Map，刷新即失。

## 5. 会话管理与侧栏（S）

<a id="s1"></a>

### S1 · 侧栏会话生命周期状态徽标 — P0，小-中，无依赖

**这是什么**：一个会话可能因为浏览器关掉、服务器重启或用户中途按停止而停在半路——最后一条消息要么是模型说到一半断掉了，要么是它发起了工具调用却永远没有等到结果。今天这类「半成品会话」在侧栏里和正常完成的会话长得一模一样，用户只有点进去翻到最后才知道它其实没跑完。omp 给每个会话算出一个生命周期状态并显示在列表里，「哪个会话停在半路、点进去可以接着跑」一眼可辨。

**pi-web 现状**：侧栏列表的每行只有消息数和首条消息（`lib/session-list-scanner.ts`），没有状态概念。读取器虽然会探测文件末尾，但只用它对账最后一个节点，不进行分类（`lib/session-reader.ts:121`）。

**omp 做法**：列表扫描时读取每个会话文件末尾至多 32KB 的内容，按最后一条消息的角色、结束原因、有没有未应答的工具调用，把会话分类为 `complete / interrupted / aborted / error / pending / unknown` 六态之一（`session-listing.ts:16-29,162-218`）；同时把既没有标题也没有任何用户输入的空白会话从选择列表里隐藏（置顶的除外，`:675-703`），避免试错留下的空壳污染列表。

**借鉴方案**：pi-web 的扫描器已经有「有界读取文件尾部」的工具函数（`readBoundedTailLines`），照 omp 的判定规则加一个 `status` 字段随会话信息下发，侧栏渲染小徽标、并过滤空壳会话即可。**工程量小-中，无外部依赖。**

<a id="s4"></a>

### S4 · 会话短 id 前缀解析 — P2，小，无依赖

**这是什么**：每个会话有 36 字符的 UUID。日常想从命令行、脚本或另一个标签页快速打开一个会话时，人只会贴前几个字符。omp 接受任何唯一的前缀（连大小写都不敏感，还能匹配文件名里的时间戳段），pi-web 现在必须贴完整 UUID。

**pi-web 现状**：会话定位要求完整 id（正则 `SESSION_ID_PATTERN`）加文件名后缀匹配，短 id 一律「找不到」。

**omp 做法**：`--resume` 与 `/resume` 对 id 前缀、文件名前缀、去掉时间戳的后缀做大小写不敏感匹配，先在当前目录找、再扩到全部项目（`docs/session-switching-and-recent-listing.md`）。

**借鉴方案**：pi-web 的会话列表本来就有全量扫描缓存，在其上做「前缀唯一命中即打开、多个命中就报候选」的解析即可。**工程量小。**

<a id="s5"></a>

### S5 · 会话 cwd 失效时的目录迁移对话框 — P1，中，无依赖

**这是什么**：会话文件里记录着它所属的项目目录（cwd）。项目被改名、整仓搬家、或者在外接盘上——这些都会让目录失效。今天 pi-web 遇到这种情况直接拒绝继续会话（「目录不存在」），用户明知项目就在旁边一个改名后的文件夹里也没有正式出路。omp 提供「换个目录继续」：核实新目录确实就是原来那个之后，把会话文件里的目录记录改掉、把会话文件搬过去。

**pi-web 现状**：cwd 不存在时只拒绝 prompt（`docs/agents/sessions.md` 记录的 #1061 行为），要用户自己手工搬文件、改内容。

**omp 做法**：打开会话发现 cwd 失效时，用设备号/inode 等磁盘证据确认目录身份后执行迁移（改 header 里的 cwd + 移动会话文件）；如果检测到还有活着的进程在写这个会话，就放弃迁移并明确报错，绝不和写进程抢（`session-manager.ts:2457,4184-4196`）。

**借鉴方案**：pi-web 已有「整文件重写会话是安全的」这一前提结论，可做成对话框：「此会话的目录不存在。是否把它迁移到你当前选择的目录？」迁移前先按 omp 的思路排除有活跃包装器的会话。**工程量中。**

<a id="s6"></a>

### S6 · 会话标题/状态持久索引 — P2，中，无依赖

**这是什么**：会话多了以后（几千个文件散在按目录编码的文件夹里），「按 id 找一个会话」和「拿列表标题」都会退化成逐个打开文件读头部。omp 用一张 SQLite 表把「会话 id → 路径/标题」维护起来，查找变成一次哈希命中。

**pi-web 现状**：列表有基于文件大小/修改时间指纹的扫描缓存（`__piWebScanIndex`），日常列表不慢；但按 id 精确定位（`findSessionPathById`，`lib/session-reader.ts`）冷路径仍是逐目录逐文件读头部，改名后取标题也要解析文件内容。

**omp 做法**：history.db 里的 `session_titles` 表，改名即写、列表 O(1) 查表；遇到索引里没有的会话回退到文件扫描并回填索引（`session-index.ts:29-36,103`）。

**借鉴方案**：在改名/自动命名/Fork 这几个写点顺手维护一份轻量的 `会话id → {路径, 标题, 状态}` 索引文件，查找先走索引再验文件头。**工程量中；数千会话规模才显出价值，可以先不做。**

<a id="s8"></a>

### S8 · 导出前的脱敏 pass — P2，中-大，无依赖

**这是什么**：把会话导出成 HTML 发给别人看之前，通常需要抹掉里面的密钥、内部 URL、以及工具的原始数据载荷（这些字段常带完整文件内容或命令输出）。pi-web 的导出就是 pi CLI 的原样产物，没有任何可挂脱敏逻辑的环节。omp 的普通导出不脱敏（文档自己承认），但它的「分享」通道有一套独立的脱敏管线，正好是可以照抄的清单。

**pi-web 现状**：`app/api/sessions/[id]/export/route.ts` 直接调用 pi CLI 的导出函数，产出原始 HTML。

**omp 做法**：分享前逐类型逐字段做删除式脱敏（工具结果里的 `details`、`data`、输出 schema 等不透明载荷整体丢弃），再 gzip、AES-256-GCM 加密；体积超限时按「图片→长字符串→最老的条目」的顺序逐级裁剪（`src/export/share.ts`、`session-anonymizer.ts`）。

**借鉴方案**：在导出路由前加一个可选的「分享副本」开关：按字段白名单/黑名单预处理后再渲染 HTML。与 N1 的加密快照共用一条脱敏管线最省。**工程量中-大。**

<a id="s9"></a>

### S9 · 会话搜索索引化 — P2，小-中，无依赖

**这是什么**：全文搜索会话内容。pi-web 目前每次搜索都现场扫描所有会话文件，靠文件数上限和时间预算防止卡死——会话少时没问题，多了以后要么搜不全要么搜不动。omp 把会话内容灌进 SQLite 的 FTS5 全文索引，搜索是查询级的。

**pi-web 现状**：`app/api/sessions/search/route.ts` 有完整的资源护栏（文件数上限、时间预算、请求中止、字面量转义），这点设计比 omp 严谨（omp 是单用户 CLI，没有资源预算概念），缺的只是索引。

**omp 做法**：`history.db` 的 FTS5 索引 + 文件变更增量跟踪器，搜索直接查库。

**借鉴方案**：建一个轻量全文索引（SQLite FTS5 最省事），复用 S6 的扫描增量更新；现有护栏原样保留。**工程量小-中。**

<a id="s10"></a>

### S10 · 会话树可视化（多分支图） — P1，中-大，无依赖

**这是什么**：pi 的会话本质上是一棵树——改消息、切换分支、从中间 Fork 都会分叉。今天 pi-web 只有一个线性的「上一分支/下一分支」切换器，用户看不到「这个会话一共有几条分支、每条停在哪、哪条是被放弃的实验」。omp 提供完整的分支树视图：图上浏览、模糊搜索定位节点、给分支打标签、被放弃的分支自动摘要。

**pi-web 现状**：`components/BranchNavigator.tsx` 只在当前节点有多个子节点时给左右切换，无全局视图。

**omp 做法**：`/tree` 命令打开树形选择器，支持过滤/标签/模糊搜索，并对被放弃的分支生成摘要供快速判断捡不捡回来（`packages/tui/src/overlays/tree-selector.ts`、`docs/session-tree-plan.md`）。

**借鉴方案**：数据 pi-web 全都拿得到（会话上下文的每个节点都有父指针），缺的是呈现：做一屏图形化的分支树（HTML/SVG 即可，浏览器画这个远比 TUI 擅长），点节点调用现成的分支切换。**工程量中-大，纯前端为主。**

<a id="s11"></a>

### S11 · 会话标题自动生成（首轮后自动触发） — P1，小-中，无依赖

**这是什么**：新会话默认顶着一长串时间戳或 UUID 当标题，起个好名字要用户手动右键点「自动生成标题」——不点就一直丑着。omp 在第一条用户消息后自动生成标题，还有「延迟补名」策略：等助手回完第一轮、结合上下文再生成一个更准的（`agent-session.ts:9329-9540`）。

**pi-web 现状**：生成能力已存在（`lib/session-title.ts` + 手动端点），缺的只是触发环节。

**借鉴方案**：会话包装器在首轮结束时服务端自动跑一次既有标题生成逻辑；用户已手起名的跳过（来源判定与第一部分 §S2 共用同一套检查）。**工程量小-中。**

## 6. 聊天渲染与工具呈现（R）

<a id="r7"></a>

### R7 · write 流式实时文件预览（右面板 + 卡内） — P0 旗舰，小-中，无依赖

**这是什么**：模型写一个文件时，文件内容是一个字符一个字符随网络到达的——在时间线上，用户此刻其实已经能「看着文件成形」。pi-web 在这整段时间里卡头只显示「正在生成参数...」，展开也只有半截 JSON；参数全部结束才看得到写的是哪个文件、写了什么。omp 把这个时间窗做成了整回合信息密度最高的一屏：路径一旦确定就出现在卡头（路径还可能继续变形时干脆不画卡，避免标题抖动），正文对已到达部分**增量语法高亮**，行号栏固定宽度防抖动，折叠态显示尾部窗口加「…（更早 N 行）」，SVG/Mermaid 这类图形文件甚至边流边渲染成图。这是用户直接能感知的体验分水岭：看到文件在眼前生成 vs 看到转圈。

**pi-web 现状**：数据**已经完整到达浏览器**——事件转发层特意保留工具参数的增量（`lib/agent-event-wire.ts:15-20,157-181`），流式 store 把它们累积成 `rawInput`（`lib/streaming-message.ts:86-120`），只是卡片故意不用（`components/MessageView.tsx:1217,1327-1331` 一律显示「正在生成参数...」）。现成的同模式先例就在库内：apply_patch 卡在流式期就用截断容忍解析实时列出被改文件并增长 diff（`lib/apply-patch.ts:51-57` + `MessageView.tsx:1681-1699`）。需要一并修改的是一条现有测试断言（折叠态不得出现任何参数片段，`MessageView.test.mjs:221-237`），把契约细化为「允许路径与摘要、正文留在展开态」。

**omp 做法**：一条专门的「参数揭示」管道——30fps 帧率 + 几何节流 + 逐字符状态机从半截 JSON 里抽长字符串字段（write 的 `content`、edit 的新旧文本、eval 的代码在白名单里，`tool-args-reveal.ts:491-636`）——喂给 write 卡的增量高亮渲染（`packages/tui/src/tools/write.ts:263-330,586-676`）。性能教训也写在它自己注释里：30fps 全量解析一度吃掉 5% CPU（issue #4377）；半截 args 的形状不可信，渲染层必须防御性解析（`todo.ts:537-546`）。

**借鉴方案**：① 写一个容忍截断的 `{path, content}` 抽取器（纯函数）；② path 坐实且 content 开始流后，在右侧面板按 `toolCallId` 打开/就地更新一个临时标签——`ReadSnapshotViewer`（语言识别、行号 gutter、表格/源码双视图、超长自动降级明文）与 AppShell「按 id 就地替换快照并激活面板」的现成形态（`AppShell.tsx:1234-1241`）完全对口，**这是 omp 没有原语、pi-web 有架构优势的地方**；③ 卡内可选加紧凑尾窗预览；④ 着色沿用现成的空闲高亮预算队列（流式期明文、参数完成后入队着色，`MermaidBlock.tsx:277-296` 就是这个策略）。是否自动弹面板需要决策：建议设置开关 + 仅在 content 首次出现时抢一次焦点。**工程量小-中，数据全部已在事件流里，零上游依赖。**

<a id="r8"></a>

### R8 · edit 流式预览（两栏预览 → 真 diff） — P1，小-中，无依赖

**这是什么**：与 R7 同理，但 edit 的「内容」是改动。omp 的 edit 走得更远：参数边流式交给内核、边套在磁盘原文上预计算，**参数流到一半就有真 diff**（Rust 侧在途计算，`packages/coding-agent/src/edit/index.ts:422-458`），卡片直接渲染「旧→新」彩色对照，多文件时只有最后一个文件带 spinner（前面的已冻结）。pi-web 同窗口同样是「正在生成参数...」。

**pi-web 现状**：edit 的参数结构是公开的（`{path, edits:[{oldText,newText}]}`，pi SDK `dist/core/tools/edit.d.ts:5-11`），半截 JSON 就在 `rawInput` 里。

**借鉴方案**：两步走——第一步（小）：对每个已闭合的 oldText/newText 对渲染「将替换 → 替换成」两栏 + 路径，明示「预览」；第二步（中）：path 确定后经现有文件接口取一次当前内容，把已闭合 edits 套上去渲染真 diff（pi SDK 已公开导出 `generateDiffString`/`generateUnifiedPatch` 可直接用），必须标注「预览≠结果」并处理文件在期间被改的竞态。内核的在途 diff 本体见 §17。

<a id="r9"></a>

### R9 · 流式期头部摘要替换「正在生成参数...」 — P0，小，无依赖

**这是什么**：R7/R8 的保底通吃版本：任何工具在参数流式期间，卡头都应显示**已经成形的那部分**——bash 显示命令本身（现成的高亮组件直接可用）、read 显示路径与范围、task 显示将启动的工人占位行、MCP 工具显示 server/tool 名。判断标准是用户在卡片列表扫一眼就能回答「现在在干嘛」，而不是知道「有个东西在生成」。omp 全套工具都有一行式 pending 状态（`bash.ts:165-208,454-470` 命令与环境变量前缀边流边成形、`read.ts:458-480`、`task.ts:2007-2022`、MCP/未知工具统一的单行参数 + JSON 树 `default-renderer.ts:70-100`）；pi-web 该窗口一律显示占位文案——即使命令参数其实早已流完。

**借鉴方案**：一个纯函数（从 `rawInput` 里扫第一个已闭合的字符串字段，按 `command`/`path`/其余键分别处理）+ 一处 JSX（建议放 `lib/tool-fields.ts` 旁的 `tool-fields-partial.ts`）；MCP 卡用 toolCallId→toolName 注册表兜底美化名。**必须配套**：~100ms 级帧率节流 + 防御性部分解析（半截 JSON 形状不可信，omp 在 todo 卡踩过，`todo.ts:537-546`）；更新 R7 提到的那条测试契约。**工程量小，是全表性价比最高的体验修复。**

<a id="r10"></a>

### R10 · 执行期卡片活性（spinner/计时/尾窗/live 自动展开） — P1，小-中，无依赖

**这是什么**：参数流完、结果未回的「执行期」。pi-web 的卡在这段时间与「刚写完参数」完全同形——没有运行标记、没有计时；唯一的活性提示是聊天底部一行脉冲文字，而且流式正文一出现就被挤掉。omp 的卡有三个互相独立的标志（参数完成 / 执行开始 / 部分结果到达），执行期卡有边框色与走表计时；bash 的输出尾窗**在未展开时也常显在卡里**。

**pi-web 现状**：执行期部分输出其实已进前端 map（bash/codemode 的 `activeToolResults`，`useAgentSession.ts:1621-1652`，断线重连恢复有测试），只是被「展开才显示正文」的门挡住（`ChatWindow.tsx:792-800`）；`tool_execution_start/end` 事件完整到达但只喂了 phase 文字（`useAgentSession.ts:1606-1620`）。

**借鉴方案**：① 用 start/end 事件维护运行中 toolCallId 集合 → 卡头 spinner + 走表计时；② bash/codemode 运行态未展开时显示末尾几行尾窗（数据已在手）；③ 抄 omp 的 `streamsBody` 语义（`tool-execution.ts:101-104`）：write/edit 这类正文值得直播的工具在 live 期间临时压过折叠偏好自动展开，结束后回落。**工程量小-中，无上游依赖。**

<a id="r1"></a>

### R1 · read 卡头的读取范围 chip 与继续读 — P1，小，无依赖

**这是什么**：代理读一个大文件时，工具不会把整个文件塞进上下文，而是读一段（比如第 12–40 行，全文共 90 行）。这个「读了哪段、还剩多少」是关键信息。pi-web 的工具卡片目前把这个信息从文案里剥掉了，卡片上看不出读了文件的哪一部分；omp 把「读了 12–40 / 共 90 行、中间省略了几段」直接挂在卡片标题上，还能一键按范围续读。

**pi-web 现状**：`lib/read-snapshot.ts:36` 主动剥掉 pi 文案里的续读提示；右面板查看器能看内容并显示行号（`ReadSnapshotViewer.tsx:103`），但卡片头没有范围信息。

**omp 做法**：read 卡片头显示省略段计数与目标范围（如 `path:13-36`），正文结尾输出机器可解析的一行「还省略了 N 行，按这些范围重读：…」（`packages/tui/src/tools/read.ts:373-376,608-610`；`docs/tools/read.md`）。

**借鉴方案**：pi-web 的正则其实已经能认出 "Showing lines 12-40 of 90" 这句文案——把它结构化成卡片头上的 `12–40/90` 小标签；右面板加「继续读」按钮，直接在文件查看器里跳到下一段偏移（网页面对活文件，比 omp 的「重读命令」更自然）。**工程量小。**

<a id="r2"></a>

### R2 · bash 工具卡的退出码/超时/秒表语义 — P1，小-中，无依赖

**这是什么**：代理跑一条 shell 命令时，用户最关心三件事：跑完了吗、退出码是几、是不是超时了。pi-web 的卡片只有红色/绿色边框加一个总耗时，退出码和「超时被杀」都藏在结果文字里要点开才看到；命令还在跑的时候只显示最后一行输出，也不知道跑了多久。omp 的命令卡有六种明确状态（运行中/失败/超时/取消/转后台/完成），退出码、耗时走表都直接摆在卡脚。

**pi-web 现状**：红绿边框 + `Took`（来自事件的 durationMs）；运行中只显示最新一行进度（`tool-execution-progress.ts`）；退出码只存在于结果文本。

**omp 做法**：六态状态机 + 卡脚常显 `Exit: N`、产物 id、运行中每秒走表的计时（`packages/tui/src/tools/bash.ts:436-439,367-371,656,688-703`）。

**借鉴方案**：从 pi 的结果文案里解析 `exit N` / timeout 关键词做成卡头标签（解析失败就退回现状，容忍脆性）；运行中的卡显示走表秒数和末尾几行输出窗口。**工程量小-中。**

<a id="r3"></a>

### R3 · 重试横幅倒计时与 superseded 灰态卡 — P1，小，无依赖

**这是什么**：模型请求失败时 pi-web 会自动重试，界面上显示「Retrying (2/3)…」。但用户不知道还要等多久、也分不清界面里上一次失败的尝试和最终成功的那次是什么关系——两次尝试的内容会先后都留在屏幕上。omp 的重试提示带剩余秒数倒计时、可以按键打断，并把被取代的失败尝试视觉上降级。

**pi-web 现状**：重试横幅无倒计时（`docs/agents/sessions.md` 记录的行为）；失败尝试的卡片和正常卡片外观无异。pi-web 另有一个针对 HTTP/2 掉流的重试补丁（`lib/retry-http2-stream-drops.ts`）说明重试场景并不罕见。

**omp 做法**：重试加载器显示剩余等待秒、可按键打断；被重试取代的失败工具卡直接撤走防止用户读错（`event-controller.ts:2564-2618`，其 issue #6879）。

**借鉴方案**：横幅加倒计时（等待时长事件里有），重试等待中 Esc 即可取消（控制增补，自原 T4 条目并入；中断语义纠错部分仍在第一部分 §T4）；被取代的尝试**打灰而不是删除**，标注「superseded attempt 1」——网页端以会话文件为事实来源，保留失败存档反而比 omp 的删卡更好，这条是「学它的语义、保持我们的可回溯性」。**工程量小。**

<a id="r4"></a>

### R4 · 工具截断元信息统一词表 + 右面板切页 — P2，中，无依赖

**这是什么**：工具输出太长会被截断。理想界面要能回答：现在显示的是哪一段、总共多大、被省略的能不能找回来。pi-web 只对用户手动输入的 `!` 命令做了完整输出的二段加载，代理工具被截断的输出则找不回来；右面板查看大结果时把整块塞进一个 `<pre>`，很大时会卡。omp 给所有截断定义了统一的结构化元数据（方向、已显示范围、省略字节数、续读偏移、产物 id），渲染层据此统一提示。

**pi-web 现状**：用户 bang 命令有完整输出文件 + 专用路由二次加载（`MessageView.tsx:2232-2288`）；代理工具输出被 SDK 截断后无恢复路径；右面板对大结果整块渲染。

**omp 做法**：输出汇同时做头/尾预算截断，超出部分镜像成可按 id 读回的产物；`output-meta.ts:9-42` 的截断元数据字段驱动统一的警告行（`docs/bash-tool-runtime.md:213-230,275-277`）。

**借鉴方案**：真正找回全文需要 SDK 产出产物文件（见 §17），但**呈现层先行**：把 pi 现有截断文案解析成「显示 a–b / 共 N 行 / 省略 M 字节」的统一标签；右面板改虚拟滚动或分页。**工程量中。**

<a id="r5"></a>

### R5 · 压缩卡片增强（方法/前后对比/per-request usage） — P2，小-中，无依赖

**这是什么**：上下文快满时代理会把旧对话压缩成摘要。pi-web 会把压缩点渲染成一张可展开的摘要卡，这点机制上已和 omp 等价（都是原位显示、不重开会话）；差距在信息量：卡上看不出这次压缩用了什么策略、压缩前后各是多少 token，而一个回合里多次模型请求的各自用量在 pi-web 只汇总成回合级的一个数字。

**pi-web 现状**：`CompactionMessageView` 原位折叠卡 + 全历史懒加载；`TurnFooter` 每回合聚合一次 token 数。

**omp 做法**：压缩事件带方法标签（多种压缩策略可编排，`docs/compaction.md`）；每次请求的用量行按发生顺序保留在对应的工具组内（`read-tool-group.ts:72-76`）；omp 的显示层是内联一条分隔线，pi-web 的折叠卡不输于它。

**借鉴方案**：卡上补「压缩前 → 压缩后」的 token 对比与方法信息（上游事件里已有字段，消费即可）；TurnFooter 增加「展开查看各次请求用量」。**工程量小-中。**

<a id="r6"></a>

### R6 · todo / ask 扩展工具的专属卡片 — P3，中，依赖生态

**这是什么**：如果代理装了「列任务清单」或「中途向用户提问」这类扩展工具，pi-web 目前只会把它们渲染成通用的 JSON/表格卡。omp 为这两类工具做了专门界面：任务清单渲染成带阶段的进度树、同时在屏幕底部挂一条常驻进度条（全部完成后自动消失）；提问工具渲染成真正的单选/多选卡片。

**pi-web 现状**：无内置 todo/ask；任何扩展工具都落通用渲染。

**omp 做法**：todo 的调用与结果合并成一个阶段树卡片 + 屏幕底部常驻 HUD（`docs/tools/todo.md:61,123-128`）；ask 用结果里的结构化 details 渲染 checkbox/radio 卡（`docs/tools/ask.md:36,56`）。

**借鉴方案**：pi 的扩展工具会把结构化 details 写进会话文件，pi-web 可以为已知扩展名定制渲染（阶段树 + 底部进度条、选项结果 chip 卡）。**工程量中；价值取决于生态里是否真有人装这类扩展，先观望。**

## 7. 回合进行中的全局可见性（T）

> 本章与 R7–R10 同属按交互时间轴的横切调研：回合执行的那几十秒里，界面整体（不只是工具卡）在发生什么、用户能做什么。其中 T2（usage 虚报纠错）与 T4（abort 吞队列纠错）在第一部分 §3，它们的展示/控制增补分别在 T1 与 R3。

<a id="t1"></a>

### T1 · 常驻工作行（计时 · tok/s · 可点 Stop · 重试倒计时） — P1，小-中，无依赖

**这是什么**：回合执行中，「已经跑了多久、出字速度如何、能不能停」的常驻指示。pi-web 的「运行中」是消息流末尾一行脉冲文字，**流式正文一出现这行就整行消失**——回合后半程基本没有全局活性指示。omp 的工作行是一等组件：spinner + 走表计时 + 意图文字 + 可点击的 [Esc] Stop，尾部挂 tok/s（空闲后保留最后读数）；重试时同一行变成倒计时环 +「attempt 1 of 3」；压缩时加进度条；连品牌图标都在回合中转动并按分钟/小时计时。

**pi-web 现状**：脉冲文字行（`ChatWindow.tsx:1356-1360`，文案来自 `lib/chat-phase-label.ts`）；Stop 按钮在 composer 里；无计时、无速率。顶栏的成本/context% 骨架已有（`AppShell.tsx:1867-1905`，含 70%/90% 着色阈值）。

**借鉴方案**：把脉冲行升级为常驻 footer 行（流式时也在）：`⠿ 42s · 正在读 src/x.ts · 63 tok/s · [Stop]`。回合开始记起点、1s 刷新；tok/s 用流式字符增量除以时间窗（纯前端）；重试倒计时用自动重试事件里的 delay 画环。**工程量小-中。**

<a id="t3"></a>

### T3 · thinking 的「自动展开 → 完成自动折叠」状态机 — P1，小-中，无依赖

**这是什么**：「模型此刻正在思考」这件事要不要演出来。pi-web 的 thinking 展开/折叠完全由静态偏好决定：偏好为折叠时，思考中只有单行省略号，用户分不清是在想还是挂了；思考结束也不留「想了多久」的凭证。omp 用状态机驱动：开始想→强制展开 + 头部走表计时与速率、正文钳在尾部带淡出；想完→自动折叠成「Thought for 12s」一行（点开可看全文）；用户手动开合过之后以手动状态为准。中断在思考中的回合，两种设计的观感差距最大。

**pi-web 现状**：`MessageView.tsx:1044-1075` 纯偏好开关；时长在结束后才显示。

**借鉴方案**：流式且为尾部块时强制展开（尊重手动状态），头部接现成的流式计时；结束自动折叠成一行。**工程量小-中，一个组件内的状态机。**

<a id="t5"></a>

### T5 · 标签页运行态（标题前缀 + favicon 三态） — P1，小，无依赖

**这是什么**：用户切去别的浏览器标签后，正在跑回合的页面没有残余信号——标题恒为「目录名 - Pi Web」，favicon 不变；通知只在完成时响一次。omp 把终端标题栏当面板用：回合中 spinner 逐帧、等待确认时 `!`、完成未读时 `done`（还有结构化的运行状态协议可被外部工具读）。web 的对应物同样免费。

**借鉴方案**：标题前缀三态 `⠿ 运行中` / `● 完成`（未读时）/ `! 等待确认`（扩展弹窗弹出时，数据源现成）；favicon 换同态 SVG data URL。注意 AppShell 的标题 MutationObserver 防回写，把状态并入统一计算。**工程量小。**

<a id="t6"></a>

### T6 · 回合清单条（todo HUD 近似） — P2，小（聚合版）/中（事件版），无依赖

**这是什么**：长回合中「干到哪一步了」的常驻答案。pi-web 只能向上滚——计划只存在于消息流的工具卡里。omp 把 todo 清单钉在编辑器上方成常驻 HUD，窗口策略有心得：进行中恒居首、已完成行保留一行（否则完成瞬间行消失，用户以为计划没动）、回合结束未完成项自动生成提醒消息。

**借鉴方案**：composer 上方加可折叠「本回合清单」条。数据源先用聚合近似（本回合工具调用序列拼成 `edit x.ts ✓ · test ⏳ · 3/7`，数据都在前端，小）；若上游将来有结构化 todo/plan 事件再切数据源（中）。omp 的窗口策略直接照抄，是便宜的正确性。

<a id="t7"></a>

### T7 · 排队消息逐条取回/删除 — P2，小，无依赖

**这是什么**：回合中可以排队若干条消息，但 pi-web 只能「全部召回」（整坨合回输入框）；omp 的队列项逐条带 Edit 控件（拉回编辑器改）、可就地删除、有编号（可口述「第 2 条」）。注意 pi 官方 RPC 没有逐条操作 API（只有 clear_queue）——变通：全量召回→本地重组→重发剩余。

**借鉴方案**：队列面板每行加「取回」与「×」按钮，走上述变通。**工程量小。**

## 8. 回合完成后的可操作性（E）

<a id="e1"></a>

### E1 · 失败回合 Retry / 换模型重答 — P0，中，无依赖

**这是什么**：一个回合因为网络、限流或模型错误失败后，pi-web 没有任何手动的一键重试入口——用户得自己重新打字或翻历史；「换个模型重新回答这一轮」更没有入口。omp 把 retry 和「临时换模型再试」的动作直接挂在失败回复的错误帧上（另有 `/retry` 命令兜底，`packages/tui/src/chat/assistant-message.ts:1115-1120`、`builtin-lifecycle.ts:487-521`）。这是横切轴上最大的缺口之一，而 pi-web 的零件齐全：分支导航（navigate_tree）与模型选择器都在，Retry 等于「回到错误前的节点 + 重发上一条用户消息」的纯前端组合。

**借鉴方案**：错误回合尾部加 **Retry**；旁边下拉「用其他模型重答」（复用 ModelSelector + 临时模型切换）。**工程量中。**

<a id="e2"></a>

### E2 · 裸 path:line 自动链接与行定位 — P1，小-中，无依赖

**这是什么**：模型输出里的 `src/foo.ts:12` 通常是裸文本。omp 把路径全面贴上带行号的超链接（OSC 8），终端/编辑器接管跳转。这是 web 天然该赢而目前赢得不彻底的点：点一下就在文件面板里跳到那一行并高亮。

**pi-web 现状**：只处理显式 markdown 链接与少数结构化位置的 onOpenFile（`MarkdownBody.tsx:112-134`）；裸路径不成链，行号跳列也没有。

**借鉴方案**：markdown 层加一个 remark 插件识别裸 `path:line`（用现有文件根判定避免误伤普通文本）；FileViewer/ReadSnapshotViewer 补 `#L12` 滚动定位 + 行高亮。**工程量小-中。**

<a id="e3"></a>

### E3 · 复制粒度细化（最后代码块/命令/链接、错误文本、整会话 Markdown） — P2，小，无依赖

**这是什么**：pi-web 的复制粒度已是「预定义」全家桶（每代码块/每消息/整回合/工具卡都有 Copy，这本身比终端强）；缺的是两类：**免瞄准**（omp `/copy code|cmd|link` 直接抓「最后一个代码块 / 最后一条 bash 命令 / 最后一条链接」，把刚跑的命令转手贴给别人时不用瞄准）和**整捆**（错误文本一键复制；`/dump` 把整会话转纯文本上剪贴板——喂给另一个 agent 的高频场景）。omp 还有「复制本次 LLM 请求」导出用于调试。

**借鉴方案**：TurnFooter 菜单加「复制最后的代码块 / 命令 / 链接」；错误帧加 Copy-error；导出菜单加「复制为 Markdown」与「复制本次请求完整上下文」（服务端已有 context 分页路由，序列化即可，这是调试金矿）。

<a id="e4"></a>

### E4 · bash 卡三件套（复制命令 / 发送到终端 / 下载输出） — P2，小，无依赖

工具卡上高亮的命令没有「复制命令」；已有终端标签却没有「把这条命令送进终端跑一下」；大输出没有「下载成文件」。三件套的底子全在（copyText、TerminalPanel、Blob 下载），纯接线活。

<a id="e5"></a>

### E5 · 文件标签右键菜单（关闭其他/全部） — P2，小，无依赖

文件面板的标签已有中键关闭与键盘导航，缺右键菜单：关闭其他 / 关闭右侧 / 全部关闭。半天活。omp 无对应物（终端没有多标签面板），纯 web 自增项。

<a id="e6"></a>

### E6 · 图片与图形操作（下载 / 多图翻页 / mermaid 导出 PNG） — P2，小，无依赖

图片 lightbox 已有（omp 的终端图形是一次性像素，完全不可比），但没有下载按钮、没有同消息多图 ←/→ 翻页；mermaid 已有缩放与 SVG 下载，可补「复制源码 / 导出 PNG」。

<a id="e7"></a>

### E7 · 删除会话的 toast 撤销 — P3，小，无依赖

删除会话即物理删文件，无法反悔。MCP 服务器的 60 秒撤销（原始条目暂存服务端 + 浏览器只拿令牌）是现成的先例，同款思路搬到会话删除（延迟物理删除或移入回收目录 + 侧栏 toast Undo）。文件级 checkpoint/回滚另论——那是内核能力，见 §17。

## 9. 输入与上下文装配（I）

<a id="i1"></a>

### I1 · @mention 自动读取文件内容注入上下文 — P1，中，无依赖（输入轴最大缺口）

**这是什么**：在消息里打 `@src/x.ts`，今天只是把它作为文本原样发出、充当给模型的「路标」——模型要不要看这个文件、用几轮去读它，全看它心情（经查 pi 内核根本没有 mention 展开机制，这不是 pi-web 没接线）。omp 在发送那一刻展开：文件内容内联（体积闸门 + 头截断 + 行数注释）、目录变文件列表、图片自动缩放后转成图像附件——一次 mention 省一轮往返、不会读错文件，上下文装配从「建议模型去看」变成「直接喂到嘴边」。

**pi-web 现状**：mention 的**输入侧**体验其实完整且优秀（模糊匹配菜单、目录逐层下钻、文件查看器整文件/选区生成 `@path:12-30` 行号 mention——后者 omp 都没有，`lib/file-fuzzy.ts`）；断在发送侧：`useAgentSession.ts:1751-1760` 原样拼文本，`rpc-manager.ts:804-832` 原样透传。

**借鉴方案**：在 prompt 准入处移植 omp 的提取器 + 生成器（纯 TypeScript；文件内联 + 目录列表，图片合入现有 images 数组）；展开失败回退原文（复用已有的发送失败恢复机制）；大小闸门照抄。**工程量中（2-4 天）。**

<a id="i3"></a>

### I3 · 跨会话输入历史 + Ctrl+R 搜索 — P2，小-中，无依赖

**这是什么**：pi-web 的「历史」是当前会话消息派生的回声（前 50 条、刷新即失、只有输入框为空时 ↑ 才弹列表）。omp 是跨会话的输入资产库（SQLite：去重 + 使用计数 + 项目溯源；框内有字也能 ↑ 召回、正在打的字存为草稿条目不被吞、Ctrl+R 全历史搜索）。找「上周那句调试提示词」这件事今天无解。

**借鉴方案**：服务端记一张历史表（发送处埋点）+ `/api/history?q=`；放开「空框才能 ↑」、菜单前缀过滤；Ctrl+R 复用现有菜单 UI 加搜索框。

<a id="i4"></a>

### I4 · 大段粘贴降级（落盘引用） — P2，小，无依赖

**这是什么**：两千行的粘贴原样进输入框、原样进模型上下文。omp 把大粘贴折叠成 chip，超过行数阈值弹三选：原样内联 / 包成附件标签 / **存成文件让模型按需 read**（Esc 也不丢内容）。web 轻量版：粘贴 ≥N 行时弹三选提示，「落盘」走现成的文件上传通道后插路径 mention（与 I1 天然协同）。

<a id="i5"></a>

### I5 · Tab 强制路径补全与 slash 参数补全/频次排序 — P2，小，无依赖

已有 @mention 与 slash 菜单，补三个小缺口：无前缀 `@` 的路径形态 token 按 Tab 也触发文件补全（放宽触发条件为路径形态判断，omp `getForceFileSuggestions`）；slash 选中项展示参数说明（与 C1 同源）；命令按使用频次排序（localStorage 计数）。omp 还有 ngram 词预测——列入不做（§18）。

## 10. 子代理与后台任务（B）

<a id="b1"></a>

### B1 · 子代理罗盘（接通已有 steer/abort + roster） — P0 旗舰，小-中，服务端已有

**这是什么**：主代理可以同时派出多个子代理并行干活。今天 pi-web 只有「点开某一条子代理查看它的只读记录」，没有一个总览页告诉你：现在有几个在跑、各自正在做什么、花了多少钱；更不能中途给某个子代理递话（「方向错了，改成只测 Windows」）、或者掐掉一个明显跑偏的——而这两个操作的服务端接口 pi-web **早就写完了**，只是没有任何界面在调用。omp 的 Agent Hub 就是这个总览页：每个工人的实时活动一行摘要、读实时记录、递话、复活停放的、掐掉卡死的，全都不打断主会话。

**pi-web 现状**：`POST /api/subagents/[id]` 已支持 `steer`（递话）和 `abort`（掐掉）两种操作（`app/api/subagents/[id]/route.ts`），但全代码库没有任何组件调用它们；`SubagentViewer.tsx` 只有只读轮询；子代理运行器其实已经在订阅子会话的全部事件、只是只在轮数限制的判断里用了它（`lib/subagent-runtime.ts:578`）——「正在用什么工具」这类实时活动行的数据源是现成的。

**omp 做法**：Agent Hub（`docs/agent-hub.md`、`packages/tui/src/overlays/agent-hub*.ts`）：花名册列出每个子代理的活动摘要/费用/未读消息数，点开可实时读记录、递话、revive（重新拉起已结束的工人）或 kill。其底层编排（强制结构化返回、工人间通信、秒级隔离工作区）属 SDK 层，见 §17。

**借鉴方案**：① 新增一个聚合接口把进行中+已结束的 run 一起列出；② 递话/掐掉按钮直连现有路由；③ 把已有的事件订阅提炼成「当前工具 + 参数摘要 + 最后活动时间」一行写进 run 记录；④「继续这个子代理」复用现有的 resume 路径。**工程量小-中，无外部依赖，是全报告投入产出比最高的一项。**

<a id="b2"></a>

### B2 · 隔离 worktree 的产物保全 — P3，中，无依赖

**这是什么**：子代理可以分配到独立的 git worktree（独立工作副本）里干活，跑完后这个副本会被删除——如果没安排合并，它写的代码跟着一起消失了，用户根本不知道发生过什么。omp 给每次隔离运行留下补丁文件和分支名，跑丢了也能回看、能捡回。

**pi-web 现状**：worktree 只有创建和删除两步（`lib/subagent-runtime.ts:346`、`lib/worktree.ts`），无产物留存。

**omp 做法**：每次隔离运行记录补丁路径与分支名，支持两种回收方式（打补丁或留分支）（`src/task/worktree.ts:119-155`）。

**借鉴方案**：run 记录里保留 worktree 路径与分支；清理前 `git diff` 存成补丁文件，卡片上给「查看/应用补丁」。**工程量中。**

<a id="b3"></a>

### B3 · typed findings 的客户端替身（约定式 JSON） — P3，中，无依赖

**这是什么**：omp 的子代理可以声明一个返回结构（schema），主代理拿到的是校验过的结构化结果（一堆按严重度排序的问题清单），不是一篇要再解析的文章。这个机制在 SDK 层拿不到，但它指向的用户价值——「子代理交付的是表格不是散文」——可以用约定在客户端近似。

**omp 做法**：隐藏的最终产出工具 + 输出 schema 强制校验；还能用 `agent://<id>/findings.0.path` 这样的地址直接取子代理结果里的某个字段（`src/task/structured-subagent.ts`）。

**借鉴方案**：在子代理 profile 层面约定「最后一条输出为 JSON」，前端按 profile 里自定义的 schema 宽松校验，成功就渲染成结构化结果卡（可用现成的 KeyValueTable），失败退回普通文本。**工程量中。**

<a id="b5"></a>

### B5 · 后台任务枚举与取消（bg_task_list / bg_task_kill） — P2，中，pi 扩展

**这是什么**：模型今天没有办法回答「我后台挂着几个任务、各跑了多久」，也没法掐掉一个不再需要的后台命令——任务完全在模型视野外运行。omp 把后台任务当一等公民：持久 job 表（状态/进度/归属），`proc://<id>` 可读状态、可写 kill 取消，`wait` 工具可阻塞等下一个完成（`src/async/job-manager.ts`、`docs/tools/wait.md`）。

**借鉴方案**：任务注册表（id/state/startedAt/logPath）+ `bg_task_list` / `bg_task_kill` 两个小 pi 扩展工具；阻塞式 `wait` 语义可选后置。投递可靠（第一部分 §B4）是这条有意义的前提。**工程量中。**

## 11. MCP、设置与扩展生态（M）

> 前提共识：逐域对比下来，pi-web 的 MCP 设置面板在**产品化程度（防误删、可撤销、掩码、信任确认）上明显高于 omp**，详见 §16。本节只列 omp 多出来的能力点；M4（损坏不留档纠错）在第一部分 §4，它的功能侧另一半 M7（热重载）在本节末。

<a id="m1"></a>

### M1 · MCP OAuth 凭证按 URL 键化复用 — P1，中小，无依赖

**这是什么**：一个 MCP 服务器（比如公司统一的 GitHub MCP 网关）经常同时写在多个项目的配置里，名字还各不相同。登录拿到的令牌今天按「配置里的名字」存——同名才能复用，于是四个项目写同一个网关就要登录四次。omp 按服务器 URL 认令牌：登录一次，所有指向那个 URL 的条目都直接可用。

**pi-web 现状**：存储键其实已经是「名字+URL」（含只按 URL 的历史格式，`lib/mcp-sign-out.ts`），读取登录状态时也已经在找历史 URL 键了，就差「按名字没找到 → 按 URL 再找一次」这一步没接进 Test/Sign-in 流程。

**omp 做法**：OAuth 凭证以 URL 为键存储（`mcp_oauth:profile:<profile>:<url>`，`src/mcp/oauth-credentials.ts`），项目配置文件只放服务器定义，授权跟人走。

**借鉴方案**：把 URL 回退查找接进测试与登录判定。后续可顺路做「后台预刷新过期令牌」，避免会话里第一个请求卡在刷新上。**工程量中小。**

<a id="m2"></a>

### M2 · MCP server `instructions` 开关 — P2，小，无依赖

**这是什么**：MCP 服务器接入时通常会带一段「使用说明」文本，被注入每个会话的系统上下文——有些服务器写得又长又没用，白烧上下文。omp 允许单独关掉某个服务器的说明注入，而工具照常可用。

**pi-web 现状**：没有这个粒度——要么整台服务器启用，要么禁用。

**omp 做法**：配置条目上的 `instructions: false` 字段（`docs/mcp-config.md`）。

**借鉴方案**：配置加一个字段、面板加一个开关。注意：这改的是 `mcp.json` 的字段语义，pi CLI 与 pi-web 必须对同一文件解释一致，落地前先和上游对齐。**工程量小。**

<a id="m3"></a>

### M3 · MCP 断线自愈（host 层轻量重连） — P2，中-大，完全体需 SDK

**这是什么**：远程 MCP 服务器会掉线。今天的恢复方式是「等下一次用户发消息时顺便重建连接」，两次消息之间界面一直挂着红色状态；连接慢的服务器在第一条消息到来时还没连上，那个回合就用不上它的工具。omp 会主动运维：掉线后按越来越长的间隔重连、故障风暴时熔断、对远程服务器做静默探测直到恢复；并且缓存上次成功获取的工具定义，让慢服务器的工具先挂名、真被调用时再等连接。

**pi-web 现状**：连接推迟到首次 prompt、每次 prompt 前同步配置（编辑即生效）、闲置十分钟释放（`lib/mcp-host.ts:40-64`），这些设计都好；缺的正是主动重连与工具定义缓存。

**omp 做法**：连接关闭事件触发 500/1000/2000/4000ms 重连阶梯 + 熔断（30 秒内挂 5 次以上），对远程服务器从 15 秒到 5 分钟指数退避的静默探针；工具定义缓存 30 天、按配置哈希失效；用缓存定义先挂名的延迟连接工具（`docs/mcp-runtime-lifecycle.md`、`src/mcp/tool-cache.ts:11`）。

**借鉴方案**：完全透明的重连归 SDK（§17）；pi-web 可先做 host 层轻量版——观察到连接关闭后退避重建，以及工具定义缓存 + 延迟挂载。**工程量中-大。**

<a id="m5"></a>

### M5 · 插件批量检查/升级 + dry-run 摘要 — P1，小-中，无依赖

**这是什么**：pi-web 的插件面板对每个已装插件各有一个「检查更新」按钮，想全部升级就要点 N 次。omp 的插件市场有一条「升级全部」命令，且支持先预演（dry-run）：看清哪些会升、从哪到哪、哪些要重启才生效，再决定动手。

**pi-web 现状**：`lib/plugin-updates.ts` + PluginsConfig 逐条检查/更新，无聚合、无预演。

**omp 做法**：`/marketplace upgrade` 一键全升、`--dry-run` 预演，装后明确告知生效边界（MCP/skills 热生效、工具/钩子需重启）（`docs/marketplace.md`）。

**借鉴方案**：「检查全部/升级全部」聚合按钮 + 升级前的预演文案清单，复用现有逐个检查的循环。**工程量小-中。**

<a id="m6"></a>

### M6 · 工具审批模式（会话级 opt-in） — P2，中，pi 扩展

**这是什么**：默认代理想写文件、跑命令就直接执行，用户要么全程盯着要么事后后悔。omp 的审批模式让每类操作可以要求「先问我」：删文件、推代码这类破坏性操作弹出确认，用户在会话里选允许/拒绝，还可以「这次会话里都允许」。pi-web 要做这条有个前置约束：项目已有一条架构决定（`docs/adr/0006`）废除了「逐条 MCP 服务器审批」，所以必须做成**会话级模式开关**（默认放手跑 / 写入需确认 / 一律确认），而不是散落各处的逐条放行，并在文档里说明与旧决定的关系。

**pi-web 现状**：没有调用级审批；但扩展对话框队列、扩展 API 兼容性这些地基都在。

**omp 做法**：工具按读/写/执行分级，每级可配「放行/拒绝/询问」，外加命令内容危险模式强制询问；审批发生在扩展改写参数之后，防止参数被换包绕过（`docs/approval-mode.md`、`src/tools/wrapper.ts`）。

**借鉴方案**：pi 官方扩展文档已有「工具调用钩子 + 确认弹窗」范式，不需要改上游；web 侧把扩展对话框升级为专用审批卡（工具名 + 现成的参数扁平表格 + 理由 + 「本会话内允许」）。交互语言可参考 omp 的「预览→接受」流：破坏性改写先挂出「(proposed)」卡、附一行理由再落盘，理由文本供用户审计（`docs/resolve-tool-runtime.md`）。**工程量中。**

<a id="m7"></a>

### M7 · settings.json 热重载 — P2，中，无依赖

**这是什么**：pi 的全局配置文件被 pi CLI 或别的会话在 pi-web 运行期间改掉时，pi-web 各面板不知道，继续用内存里的旧值。omp 监听配置文件变化即时生效（某层解析失败时保留该层旧值而不是清零）。

**pi-web 现状**：无变化监听（`lib/global-settings-file.ts` 只有锁与原子写）；MCP 的每-prompt 同步天然吃到新值，内置开关面板与模型面板不吃。

**借鉴方案**：监听 settings.json 变化，刷新内存视图与相关面板。omp 的六层设置深合并模型属 pi CLI 共享语义，须上游（§17）。**工程量中。**

## 12. 终端、git 与工作区（G）

<a id="g3"></a>

### G3 · hunk 级部分暂存与提交建议 — P1 结构，中，无依赖

**这是什么**：一个文件里经常混着两件事的改动（功能 + 顺手改的日志）。专业 git 客户端允许只暂存文件里的某几块（hunk），把一次改动拆成干净的提交。pi-web 的 git 卡片只能整文件看 diff；omp 给代理（也顺带给界面）提供了按 hunk 访问工作区的能力。

**pi-web 现状**：`app/api/git/diff/route.ts` 只有整文件 diff，无任何暂存操作。

**omp 做法**：三个只读工具把工作区结构化到 hunk 粒度（概览/单文件 diff/单 hunk），供按块操作（`src/commit/agentic/tools/`）。

**借鉴方案**：新增按文件返回 hunk 数组的路由（解析现成 diff 即可），UI 在 diff 卡上支持勾选、按勾选调 `git apply --cached` 部分暂存；再加一个「建议提交信息」的轻量子任务。**工程量中。**

<a id="g4"></a>

### G4 · 原子提交拆分（omp commit 式） — P2，中，无依赖

**这是什么**：一次会话里代理可能顺手改了五个不相干的东西：修 bug、补测试、格式化、改配置、升级锁文件。一股脑提交成一个又大又杂的 commit 还是拆成五个干净的提交，是代码评审体验的分水岭。omp 的提交流程让代理把工作区的改动按「谁依赖谁」排好，拆成一串原子提交：源文件在前的提交是主角、锁文件干脆不参与拆分分析、检测到循环依赖就拒绝动笔。

**pi-web 现状**：有 status/diff 只读卡片，无任何提交组织功能。

**omp 做法**：在 hunk 级工作区访问之上做拆分器：按文件依赖拓扑排序、源文件权重高于测试/文档/配置、循环依赖拒写、锁文件整体排除（`src/commit/agentic/tools/split-commit.ts`、`topo-sort.ts`）。

**借鉴方案**：在 G3 的 hunk 数据上加一个「拆分为原子提交」流程：先出拆分提案让用户确认，执行交给会话里的代理或本地 git，二选一并写明。**工程量中。**

<a id="g5"></a>

### G5 · worktree 快速创建（reflink/clonefile） — P1，小-中，无依赖

**这是什么**：为代理开一个独立工作副本（worktree）时，git 会把整个仓库的文件完整抄写一遍——三万文件的仓库要等几分钟（代码注释自己承认这点，超时设到 5 分钟）。omp 用文件系统级的「写时复制克隆」（macOS 的 clonefile / Linux 的 reflink）：新副本指向原有磁盘块、只有被修改的文件才真正占新空间，分钟级变秒级。

**pi-web 现状**：`lib/worktree.ts:265-309` 走 `git worktree add` 全量检出，注释自认大仓库要几分钟（WORKTREE_TIMEOUT 5 分钟）。

**omp 做法**：`PI_SMART_GIT` 把 worktree 创建交给原生 VCS 模块做写时复制克隆+登记+对账；更激进的是隔离层直接秒级克隆整个工作区（`docs/native-crates.md`）。

**借鉴方案**：不必写 Rust 也能拿八成收益：macOS 用 Node `fs.copyFile` 的 `COPYFILE_FICLONE` 标志、Linux 用 `cp --reflink=auto` 克隆主检出目录，然后修正 `.git` 指引文件并用 `git worktree add --lock` 登记；保守方案：`--no-checkout` 先登记、后台增量检出并推进度条。克隆后与 git 索引的一致性要重点测。**工程量小-中。**

<a id="g6"></a>

### G6 · `conflict://` 式对话式解决冲突 — P2，中，部分需扩展

**这是什么**：git 合并冲突是代理（和人）都头疼的场景：一个文件里散着好几处 `<<<<<<<` 标记，靠字符串替换去修很容易改坏。omp 把每个冲突块变成一个可寻址的小对象：代理（或用户）对它写一个词——`@theirs`（用对方的）、`@ours`（用自己的）、`@base`——文件就干净地解掉这一个冲突，还有批量模式一次处理全部。

**pi-web 现状**：diff 卡片遇到冲突文件只能整文件展示，无冲突操作。

**omp 做法**：读文件时顺带注册冲突块为 `conflict://N` 地址，对地址写入三选一拍即解；`conflict://*` 批量（`src/tools/conflict-uri.ts`、`docs/tools/write.md`）。

**借鉴方案**：网页端先做 UI 侧价值：检测到冲突文件后在卡片里列出各冲突块，每块三个按钮（采用对方/保留我方/共同保留）直接落盘；代理侧的协议等扩展层跟进。**工程量中。**

<a id="g7"></a>

### G7 · 内部 URL scheme 子集（`pr://`、`issue://`） — P3，中-大，无依赖

**这是什么**：omp 把一堆远程资源也做成了「路径」：读 GitHub 的 PR 用 `read pr://1428`，和读一个本地文件用完全一样的工具、完全一样的语法；issue、技能定义、子代理结果都各有一个 scheme。对模型来说只有一个「路径」概念要学，对界面来说这些路径就是天然的可分享、可跳转链接。

**pi-web 现状**：文件路由只服务本地目录；GitHub 资源没有任何一等公民表示。

**omp 做法**：一个内部 URL 路由表把 16+ 种 scheme 挂到同一套按路径读写的工具上，grep 甚至能像走目录一样走一遍 PR 的 diff（`src/internal-urls/router.ts`）。

**借鉴方案**：先做子集（`pr://`、`issue://`）：pi-web 服务端可实现「按路径取资源」的一半（渲染、跳转、可分享链接），工具面的一半（模型能 read/grep）需要 pi 扩展配合。**工程量中-大，观望。**

## 13. 安全与凭据（K）

<a id="k1"></a>

### K1 · 密钥全链路可逆混淆 — P1 结构，中-大，pi 扩展

**这是什么**：代理跑一条带凭据的命令（`curl -H "Authorization: Bearer sk-…"`、连接字符串里的密码），命令输出和完整命令行会**原样**写进会话存档文件、并作为上下文发给模型提供商——离开你的机器之前没有任何东西拦它。pi-web 现有的防护都朝着「别让自己浏览器里显示出来」：面板掩码、子进程环境变量消毒、登录节流。omp 补的是另一头：所有离开本机的文本先扫描替换成可逆占位符，要执行命令时再换回来——模型看到「这里有个密钥」但不知道密钥是什么，存档里也永远没有明文。这是全报告最大的单项安全差距，对「会话会被持久化、会被渲染、可能接第三方提供商」的 web 客户端尤其对症。

**pi-web 现状**：只防本地显示：面板级掩码（`lib/mcp-secrets.ts`，密钥值从不出服务端）、stdio 子进程环境消毒并拒绝传递登录口令本身（`lib/mcp-transport.ts:80-83`）、命令环境变量剥离（`lib/project-command-env.ts:57-64`）、登录爆破节流（`lib/auth-throttle.ts`）。模型方向的内容通道不设防。

**omp 做法**：环境变量名启发式 + 项目级密钥声明文件 + 内置二十多种凭据格式的正则 + 连接串口令回收；命中内容替换为带 HMAC 摘要的占位符（每个安装生成随机密钥文件，防别人从存档反推；占位符保留大小写提示）；三段式管线：工具执行前深度还原、本地查看/恢复会话时还原、重发给提供商前再混淆（`docs/secrets.md`、`src/secrets/`）。

**借鉴方案**：纯 TypeScript 可复刻为 pi-web 宿主扩展，密钥文件写法（独占创建、0600 权限、坏值清理）直接照抄 omp。两条纪律必须守住：只影响显示属零风险改动；影响发给模型的流量则是行为改变，必须默认关闭 + 面板明示。**工程量中-大。**

<a id="k2"></a>

### K2 · provider 用量缓存与重置时间预警 — P1，小，无依赖

**这是什么**：Settings 里的用量页每次打开都现场挨个请求各提供商的配额接口；查到的用量也不记「什么时候重置」，用户无法预判、额度耗尽时也不会有任何预警。omp 会缓存配额查询、解析重置时间、对「额度耗尽」做专门分类，并配合自动换 key。

**pi-web 现状**：`app/api/provider-usage/query/route.ts` + `lib/provider-usage.ts:42-53`：十个固定端点的一次性查询，无缓存、无重置时间概念。

**omp 做法**：每 key 轮询配额窗口 → 分类（含 QUOTA_EXHAUSTED）→ 自动轮换凭据，并给会话固定账号亲和（`docs/providers.md:57`、`docs/auth-broker-gateway.md:320`）。

**借鉴方案**：查询结果短缓存 + 把解析到的重置时间持久化，界面显示「N 小时后重置」；额度逼近上限的模型在选单里置灰。多 key 自动轮转属 pi 内核的凭据层，pi-web 不做（§17）。**工程量小。**

## 14. 分享、协作与可观测（N）

<a id="n1"></a>

### N1 · 只读观看链接（限同信任域；加密快照作前置） — P1，中，前提：实例对观看者网络可达

**这是什么**：「把这次会话给同事看看」目前没有任何正式通道——导出的 HTML 只能当文件传，实时事件流只服务已登录同一个服务的浏览器。

**必须先核对的前提（初稿曾把这条错标为 P0 旗舰）**：omp 的「发个链接就能看」之所以成立，是因为背后站着官方基础设施——零知识中继与 blob 端（`packages/collab-web/`、`docs/collab.md`、`src/collab/crypto.ts`）。pi-web 是**自托管应用，没有任何分享服务端**；「发给任何外部的人」在当前产品形态里不成立，需要一次「是否服务化」的产品决策，已列入 §18。剥掉服务依赖后，真正可做的只有两件事：① **加密单文件快照**——脱敏后的会话 AES-256-GCM 加密成自带解密器的 HTML（密钥只进文件内的 `#` 片段），对方浏览器本地解密阅读；但它仍是**文件传递、不是链接**，省掉的只是「对方不敢开明文 HTML」的信任问题；② **同信任域只读观看**——给现有 SSE 加一条只读令牌通道（能看、不能发命令），复用现有鉴权栈（`proxy.ts` + 口令保护）；前提是对方网络能到达这个实例（局域网 / VPN / 已反代暴露）。

**pi-web 现状**：导出 HTML 是本地明文文件（§S8 还指出它不脱敏）；实时事件只服务同源已登录浏览器（`GET /api/agent/[id]/events`）；已有整站口令保护可作只读令牌的鉴权底子。

**借鉴方案**：② 优先（同域团队是真用户），① 作配套；两半共用 S8 的脱敏管线。外部「发链接」形态依赖中继/blob 服务，见 §18；真·多人实时写协作同样不做（§18）。**工程量中。**

<a id="n2"></a>

### N2 · Stats 用量仪表盘 — P1，中，无依赖

**这是什么**：一个看自己「用代理用得怎么样」的页面：每天烧了多少 token、每分钟输出多少、提供商的缓存命中率省了多少钱、失败率趋势。omp 专门做了一个本地统计工具（解析会话日志 → SQLite 小时级汇总 → 网页仪表盘），相当于替 pi-web 把这类页面设计好了一遍。

**pi-web 现状**：token 数只出现在每个回合的页脚，无任何跨会话/跨天聚合视图。

**omp 做法**：`packages/stats/`：JSONL 会话日志 → SQLite 小时汇总 → 流式更新的 web 页（吞吐、缓存命中/节省率、错误率），增量跟踪器同步新会话。

**借鉴方案**：Settings 加一个 Stats 页，数据管道复用 S6 的扫描索引做增量。**工程量中。**

## 15. 交互控制与记忆（C / D）

<a id="c1"></a>

### C1 · slash 命令参数提示（ghost text）与被遮蔽标注 — P2，小，无依赖

**这是什么**：pi 的 `/` 命令可以接受参数，但命令面板只列出名字和说明——「这条命令收什么参数」用户要么会背要么试错。omp 的命令定义可以声明一句参数提示，面板选中该命令时直接以灰色幻影文字显示在输入框里（如 `/deploy <环境> [--dry-run]`）；另外 omp 汇聚多个来源的命令，同名相撞时会把被高优先级顶掉的那条打上「被遮蔽」标记，面板里能看清「这条被那条盖了」。

**pi-web 现状**：命令信息含名称/说明/来源/作用域（`hooks/useAgentSession.ts:151`），面板已按来源分组——「来源」这半边其实已有；缺参数提示，也没有同名遮蔽提示。

**omp 做法**：命令文件 frontmatter 的 `argumentHint` 字段驱动输入框内的灰色参数提示（`docs/slash-command-internals.md` §3、`packages/tui/src/autocomplete.ts`）；每条命令算一个展示用的来源串，低优先级同名命令打 `_shadowed` 标记供面板显示。

**借鉴方案**：pi 上游不提供这个字段，pi-web 可自行解析 prompt 模板的 frontmatter、或从模板正文的 `$1`/`$ARGUMENTS` 占位符推导出参数形态，补进现有面板；再加同名冲突标注。**价值中等、工程量小。**

<a id="c2"></a>

### C2 · `/annotate` 式行级批注流 — P2，中，无依赖

**这是什么**：「这个 PR 的 42 行并发有问题、87 行少个空检查」——今天这类反馈要么打成一大段文字凭记忆描述位置，要么切到别处截图圈注。omp 的批注流程让用户先在 diff（或一段回复、一个文件）上逐行钉批注，然后一键把这些批注组装成带回原文引用的反馈发给代理——引用精确到行，行内容变了会报错而不是贴错位置。

**pi-web 现状**：有单文件 diff 路由和带行号的文件查看样式（FileViewer），但 diff 只是只读卡片，没有反馈通道。

**omp 做法**：`/annotate` 打开批注界面，逐行/整文件添加批注、可编辑可撤销；组装时给每条批注锚定原文行或 diff 块位置，锚点对不上就点名报错；批注永远贴进输入框由用户发送、绝不自动提交（`docs/slash-command-internals.md` §12）。

**借鉴方案**：在现有 diff 标签上做逐行钉批注，产出两种去向：拼进输入框（默认）或一键发送。这是网页界面比 TUI 明显更有优势的场景。**工程量中。**

<a id="c3"></a>

### C3 · APPEND_SYSTEM 系统提示编辑面板 — P2，小，无依赖

**这是什么**：pi 已支持用磁盘上的文件追加全局或项目级的系统提示词（往「代理必须知道的规矩」里加一段），但编辑入口完全在文件系统里。加一个设置面板：编辑全局与项目的追加提示文件，并展示当前实际生效的完整系统提示——代理的行为规则从此可见可改。

**pi-web 现状**：没有相关界面。pi 本身已支持这些文件（pi 文档 `docs/configuration.md`）。

**omp 做法**：系统提示定制文档化 + 相应管理（`docs/system-prompt-customization.md`，含若干文件变体）。

**借鉴方案**：Settings 加一节，编辑全局与项目文件（项目文件的写入走既有信任机制和原子写工具），旁边给一个「当前生效提示」的只读展开。**工程量小。**

<a id="c4"></a>

### C4 · Advisor 第二模型逐轮监督卡片 — P3，中，pi 扩展

**这是什么**：给主配一个第二模型当审阅搭子：主代理每干完一轮，审阅模型在自己的独立上下文里看一眼这一步，有不同意见就在对话流里插一张便签——从「小声提一句」到「这一步我有异议」。干活的和把关的用不同的模型和上下文，能发现当事人自己看不见的坑。

**omp 做法**：配对了审阅角色后，每轮结束审阅模型拿到本轮增量，产出按严重度分档的提示注入对话；有发射守卫防止刷屏，还有追补机制处理积压（`docs/advisor-watchdog.md`、`src/advisor/runtime.ts`）。

**借鉴方案**：pi 扩展层可实现：订阅回合结束事件，用扩展 API 的轻量模型调用起审阅请求，把意见作为自定义类型的隐藏消息注入；网页端已有自定义消息的折叠渲染，加上按严重度的配色和侧栏开关即可。只做不打断的便签（pi 没有中断通道），不动上游。**工程量中。**

<a id="d1"></a>

### D1 · 跨会话课训轻量注入（lessons.md） — P3，中，无依赖

**这是什么**：代理今天对「上一次会话学到了什么」完全失忆：这个仓库的测试必须用哪个 runner、哪个接口有已知的坑，每个新会话都要重新踩一遍。omp 有整套跨会话记忆（写入/回忆/反思工具、可插拔记忆后端、每个会话收尾时压缩出「心智模型」在下次开局注入）。这套运行时能力拿不到，但核心价值可以轻量复刻。

**omp 做法**：回合中主动记条目、会话收尾提取「课训」并去重脱敏（有条数上限、绝不改当前会话的提示前缀以保护缓存）、下次会话首轮注入（`docs/memory.md`、`src/memories/`）。

**借鉴方案**：极简版三件套：回合结束后后台用小模型把本次的教训追加到项目级 `lessons.md`（条数上限、去重）→ 新会话创建时把该文件注入系统提示 → 面板可见可清空（即 D2）。全部在 pi-web 包装器层，不动 SDK。omp 的两条工程纪律直接照抄：不动当前会话提示前缀（保提供商缓存）、百条上限+去重+脱敏。**工程量中。**

<a id="d2"></a>

### D2 · 记忆/课训可视化面板 — P3，小，依赖 D1

**这是什么**：「代理记住了我什么」必须随时可查、可删——注入的规则不能悄悄生效。omp 有统一的记忆查看/统计/清空命令。D1 落地后 pi-web 配一个面板：显示当前注入了哪些条目、各自来自哪个会话、一键清空。也符合 pi-web 一贯的透明性风格。**工程量小。**

## 16. pi-web 反而做得更好的地方（明确不动）

反向逐域核对后确认，以下均为 pi-web 领先、omp 无对应或更差，调研中逐条给出过双方文件证据：

**会话层**
- 多客户端服务器语义：列表缓存带世代号、并发请求合并、允许返回旧值后台重建；跨进程加锁的界面状态文件 + 乐观更新重放（omp 是单进程终端程序，没有这个问题域）。
- 会话查看缓存有三重预算（条数 + 总字节 + 单文件超限旁路）。
- 列表载荷治理：首条消息截 500 码元、长内容折叠。
- 搜索资源护栏：文件数/时间预算/请求中止/字面量转义一体（omp 的搜索没有资源预算概念）。
- Fork 命名：源标题 + 随机后缀，且防止在 fork 的 fork 上叠后缀（omp fork 后与源同名）。
- 置顶/归档/项目排序等界面状态外置于会话文件之外——会话文件保持纯洁，Fork 和 CLI 不受污染。
- 删除会话的级联语义完整（家族 + 保活在跑的 + 孤儿改嫁到最近存活祖先），omp 的删除是尽力删单文件。
- Web 攻击面防护：路径限制在允许根内、请求头校验防目录逃逸。

**渲染层**
- 回合分段「答案常驻、过程自动折叠」的阅读模型优于 omp 的全局展开/收起。
- read 快照的右面板标签页（同一份内容三种视图：渲染/表格/带行号源码）omp 没有对应物。
- 流式性能工程：每条流式回复的订阅者级定向重渲染、语法高亮的空闲预算队列、回合视图缓存。
- 小地图跨分页的回合编号、回合改动文件可点击直达。
- 失败尝试永久留档在会话文件里（omp 重试时直接删卡，可回溯性更差）——R3 借鉴其语义但保留我们的存档。

**MCP / 设置**
- 删除服务器 60 秒撤销，含明文密钥的原始条目只存服务端内存、浏览器只拿令牌。
- 信任对话框对未信任项目的命令**不掩码**展示（掩码恰恰能藏住 `npx -y 恶意包` 这类陷阱）；只读检查永不触发凭据存储的建锁副作用。
- 配置写入门槛：原子写 + 锁 + 类型化拒绝 + 符号链接/越根规则；omp 的配置文件写入器没有这套防御。
- 测试结果按「配置内容哈希」记账，改过配置立即显示未测——旧结果贴新配置这类错误从结构上杜绝。
- 「测试连接」有完整边界学（20 秒总死线、串行队列、按入口合流、全链路脱敏）。
- stdio 子进程环境消毒并拒绝传递登录口令；omp 的 `!cmd` 配置值直接在项目目录跑 shell 且无环境白名单。
- 面板级掩码：密钥值从不出服务端；omp 的 `/mcp list` 直显配置原文。
- 每次发消息前同步配置即热生效（omp 要手动 reload）；闲置十分钟释放连接（omp 无空闲断开）。
- 启用模型开关列表用「最小编辑」策略，防止误删其他提供商的条目。

**终端 / 后台 / 平台**
- 「在文件管理器中打开」只允许环回地址访问（omp 没有 web 面，无此问题也无此防护）。
- 登录爆破节流（全局计数 + 闲置复位）。
- 前后台交接语义（溢出缓冲标记、报告引用增长式聚批、落盘后冻结）比 omp 的任务投递更精细地防止内存/文件分叉——B4 只补投递可靠性，不动这套语义。
- 浏览器推送通知（含 iOS 的适配）：omp 完全没有。
- worktree 的项目身份缓存与已删除 worktree 的推断归组，贴合 web 列表场景（omp 只关心隔离跑，不做归组）。

**横切轴（流式期 / 回合中 / 完成后 / 输入装配）**
- 事件线的**瘦身转发**是深思过的：不转发整消息快照、`tool_execution_update` 按 toolCallId 合并、超大结果不进事件流、codemode 快照只留最新 200 条——omp 的 30fps 全量 args 对象分配 + ANSI 反复重建是它自己注释里反复赎罪的性能债（R7 落地时沿用 pi-web 的瘦身基座，别把债抄过来）。
- apply_patch 卡**已经有**流式期截断容忍的 split-diff 实时预览（`lib/apply-patch.ts:51-57`）——R7 要走的模式在库内有现成先例。
- 右面板快照的「每个调用一个标签、内容可就地替换并激活」是 omp 完全没有的原语（R7 的架构地基）。
- 滚动跟随体系（rAF 级 live-follow、双容差附/脱、发送后 prompt-anchor、移动端键盘抖动规避）——终端的 scrollback 模型没有这个问题域，无从对照。
- 回合可见性的传输可靠性：SSE + 15s reconcile + visibility/online 钩子 + 执行期部分输出的断线重连恢复（有测试）。
- Steer/FollowUp 投递时机菜单与队列可视化面板（比 omp 的裸 Alt+Enter 心智负担低；逐条编辑的缺口见 T7）。
- 输入装配的 web 天然优势：剪贴板图片零配置（omp 需原生模块 + 平台分支补丁）、真文件拖放 + 自动插 mention、富文本粘贴转 Markdown、IME/移动端工程密度、行号 mention（`@path:12-30`，omp 输入框没有）、图形化模型/思考/工具档常驻选择器。
- TurnFooter 的位置学（明确解决「折叠组里够不着的 footer」）；后台完成 Notification + chime/holdAudio 的音频合规。

## 18. 明确不做

- **真·多人实时协作（访客可发命令/抢占）**：omp 的 host 权威 + 加密中继协议与 pi-web 的进程内会话模型不匹配，成本远超收益；N1 只取同信任域的只读观看。
- **Claude/Cursor/Cline 等八种规则格式兼容层、兼容 Claude 插件清单的市场**：与「pi CLI 扩展在这里必须行为一致」的项目原则冲突；只借它的目录浏览体验与预演升级文案（M5）。
- **魔法关键词（正文里的暗语触发隐藏行为）、全局暂停闸门**：pi 没有输入拦截事件，属运行时缺口，等上游。
- **集中凭证代理网关服务**：独立服务级工程，对单机 web UI 收益低；只取其中「令牌后台预刷新」小切面并入 M1 后续。
- **Rust 原生全家桶**（内容哈希编辑格式、内嵌 shell、文件系统隔离后端、进程内 jq、语音、桌面操控）：harness 层，只借鉴设计语义（G5 只取写时复制一个切面、G1 只取杀树/背压语义的 TypeScript 近似）。
- **公共分享中继 / blob 服务（「发外部一个链接」形态的基础设施）**：omp 的快照分享与实时观看都站在官方中继与 blob 端之上；pi-web 是自托管形态，没有任何服务端承接点，「发给任何人」需要先做是否服务化的产品决策。决策前只做 §N1 的两件无服务依赖的事（加密单文件、同域只读令牌）。
- **子代理之间的兄弟消息**：pi 无总线，自建要引入模型可见的投递前缀协议，项目在这上面有过教训。
- **输入编辑器的 ngram 词预测与 shell 草稿语法高亮叠层**：误触发代价高、隐私面大，textarea 叠层成本不值。
- **终端机制家族**（原生剪贴板模块、`$EDITOR` 子进程、OSC 序列族、终端图形协议）：web 各有自己的等价物（ClipboardEvent / 大号 modal 编辑器 / 标题+favicon），不要模仿形态只取语义。
